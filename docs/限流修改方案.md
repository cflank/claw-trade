# 限流修改方案

## 0. 2026-06-02 修订结论：统一预提取 + 任务级限流排程

状态：已完成首版实现，仍未完成 live 四市场验收。`/report` 统一预提取已接到 worker 资料包入口：runner 在 `/report` frontline 调度时传入 `ReportDataPrefetchManifest` 路径，OpenClaw plugin 只转发该路径，Python 资料包桥直接读取 manifest；manifest 缺失、错 run、错 market、错 domain 时 fail closed，不再回退到 DataAPI 重取。

已实现范围：

- UI / `.env.local` / Mongo 数据源设置支持 provider 限流字段。
- `RateLimitPolicyResolver` 从数据源设置解析 provider 限流策略。
- Coinglass/Tushare/Finnhub 等已映射到 UI/env 的数据源，未配置限流时不做本地限流。
- `RateLimiter` 支持以本次数据运行开始时间作为窗口锚点。
- `DataRunScheduler` 会把 `DataPlan.created_at` 写入 provider batch 的限流窗口。
- `/report` 真实 runner 接入 `ReportDataPrefetcher`，在 worker 调度前一次性调用 `DataAPI.get_data_batch()` 预提取 frontline 数据。
- HTTP 429 / provider `rate_limited` fetch 结果会写入 cooldown，后续同最终数据源在 cooldown 内不继续出网。
- `/report` frontline 资料包入口已直接消费 `ReportDataPrefetchManifest`；非 `/report` 或无 manifest 的普通资料包调用仍保留 DataAPI 路径。
- `/select` 已通过公开 `src/claw_trade/data_gateway/selection_api.py` 进入统一 `DataAPI.get_data_batch()`；具体批量实现位于私有 `src/claw_trade/data_gateway/_selection_batch.py`。本地预打包全市场日线行会先用仓库结果闭环，不再因为补充 provider 的单标的接口要求而触发旧 `symbol_required` 缺口。

未完成范围：

- `/select` 还没有真实完成候选池数据验收：当前用户本地包只有日线和因子，缺公司名/行业身份文件，也缺定增或公告事件覆盖；系统按缺事实字段 fail closed，不能把股票代码伪装成公司名，也不能把缺失事件伪装成“无定增”。
- 未跑 Coinglass 10/min live 验收。
- 未跑修复后的四市场 fresh/full-chain collect-first 验收。

本节优先级高于后文历史方案。后文仍保留为背景和已知问题记录，但实施以本节为准。

### 0.1 人话结论

要改的不是“Coinglass 多等几秒”，而是两件事：

1. **report/select 一开始先把本次任务需要的数据统一列出来。**
   不让每个 worker、每个资料包各自临时去打接口。先收集需求，再去重、合并、排队、提取。

2. **从任务开始时间就启动限流窗口。**
   例如 Coinglass 配置为 `10 次 / 60 秒`，那么从本次 `/report` 或 `/select` 开始那一刻起，第 0-60 秒最多放 10 次，第 60-120 秒再放下一批。超出就等待或记录限流缺口，不能继续硬打。

一句话：

```text
先统一计划，再统一取数，再按配置限流排队。
```

### 0.2 当前事实

当前已经有的能力：

- `DataAPI.get_data_batch()` 可以一次接收多个数据需求。
- `DataService` 会按固定流程执行：查仓库、选 provider、合并需求、生成批次、进执行闸门、fetch、入库、recheck。
- `RequestCoalescer` 已能把同 provider / endpoint / market / data_type / granularity / source_role 的请求合成组。
- `ProviderBatchPlanner` 已能按 provider 的 batch policy 拆分 symbol、日期和字段。
- `ExecutionGate` 已有 cache / rate-limit / single-flight 顺序。
- HTTP 429 已能识别为 `rate_limited`，不会写成成功。
- HTTP 429 / provider `rate_limited` 后会登记 cooldown。
- 限流 bucket 已按最终数据源聚合，例如 US/HK Finnhub 共用 `finnhub`，Coinglass 使用 `coinglass`，不再按 endpoint 单独放行。
- `/report` 入口会在 worker 前统一预提取 market / fundamental / news / social。
- UI、`.env.local`、Mongo 已有统一 provider 限流配置字段。
- `settings_projection` 已把 env 限流字段导入 Mongo 数据源设置。
- ProviderBatchPlanner 会优先使用 `RateLimitPolicyResolver`，不再只吃 provider capability 默认值。
- `/report` worker 资料包入口已直接消费本次预提取 manifest；manifest 不可用时 fail closed，不再偷偷重打远端。
- `/select` data job 已走统一 DataAPI bridge；当前真实本地包 smoke 不再出现 `symbol_required`，但因为缺公司名和定增覆盖，候选池仍为 0 并按真实缺口失败。

当前没有完成的能力：

- `/select` 当前真实本地包缺公司名/行业身份和定增/公告事件覆盖，不能生成 approved candidate pack。
- live 证据尚未证明 Coinglass 同一分钟远端调用不超过 UI/env 配置。

### 0.3 目标边界

`claw-trade` 可以在 report/select 开始时做数据预提取，因为这是 workflow 控制面的数据准备，不是 worker 私自调用工具。

但必须遵守边界：

- Python 只能收集数据需求、执行数据层、保存证据和缺口。
- Python 不能替 worker 写分析结论。
- Worker 看到的仍是批准后的自然语言资料包和证据摘要。
- 缺失数据必须明确进入 data gaps，不用 fallback 或假数据补齐。
- Provider 配额来自 UI / `.env.local` / Mongo 设置，不来自 provider 代码硬编码。

### 0.4 目标执行流程

#### report

目标流程：

```text
/report command
  -> ReportDataRequirementPlanner
       收集 market / fundamental / news / social 所需数据
       生成本次 report 的完整 DataRequest 清单
  -> DataRunScheduler
       以 report_run_started_at 作为限流窗口起点
       读取 UI/env/Mongo 的 provider 限流配置
       对所有 provider batch 做排队
  -> DataAPI.get_data_batch(all_report_requests)
       QueryPlanner
       Warehouse.check
       ProviderSelector
       RequestCoalescer
       ProviderBatchPlanner
       ExecutionGate
       FetchEngine
       IngestPipeline
       Warehouse.recheck
  -> ReportDataPrefetchManifest
       按 domain 保存 dataset_refs/raw_refs/attempt_refs/data_gaps
  -> frontline workers
       资料包入口直接读取对应 domain 的 manifest 结果
```

效果：

- 同一份日线、同一个新闻源、同一个 provider endpoint，不会因为多个 worker 需要就重复打远端。
- 一个 report run 里的数据缺口在 worker 开始前就可见。
- 后续 worker 不再临时把相同数据源打多次。

#### select

当前目标流程：

```text
/select command 或定时选股
  -> SelectionDataJob / SelectionRunPlan
       根据市场、策略、全市场 universe、字段需求生成 DataRequest 清单
  -> DataRunScheduler
       以 selection_run_started_at 作为限流窗口起点
  -> DataAPI.get_data_batch(all_selection_requests)
  -> SelectionProviderBatchResult + selection_data_api_batch_bridge.v1 evidence
       保存全市场候选池需要的数据证据和缺口
  -> selection engine
       只消费已入库/已批准的数据和缺口
```

效果：

- 选股不再每个策略字段单独临时取数。
- 全市场数据按 provider 批量能力合并，例如支持批量 symbol 的接口按最大 symbol 数拆批。
- 缺字段时按策略规则扣分、剔除或失败，而不是现场补假数据。

当前实现状态：

- `SelectionDataJob.run()` 在选股数据作业开始阶段调用一次 `provider_fetch_batch(plan)`。
- `provider_fetch_batch` 现在进入统一 `DataAPI.get_data_batch()`，先取全市场日线；如果命中本地预打包 direct rows，就直接用仓库结果闭环，不再继续打需要单标的的补充 provider。
- 如果日线行完整，直接生成候选输入；如果缺公司名、行业、定增覆盖或策略必需字段，则写 data gaps 并 fail closed。
- 当前用户本地包 smoke 的失败原因是缺事实输入，不是旧 `symbol_required` 调用链。

### 0.5 限流配置所有权

限流配置归 UI / `.env.local` / Mongo 设置，不归 provider 代码。

每个需要 API key 的数据源设置应保存这些字段：

| 字段 | 人话含义 | 示例 |
| --- | --- | --- |
| `rate_limit_max_calls` | 一个窗口最多调用几次 | `10` |
| `rate_limit_window_seconds` | 一个窗口多少秒 | `60` |
| `rate_limit_safety_margin` | 安全余量，实际少打几次 | `1` |
| `rate_limit_overflow` | 超额后等待还是直接记缺口 | `wait` / `fail_fast` |
| `rate_limit_wait_timeout_seconds` | 最多等多久 | `75` |

`.env.local` 使用统一命名：

```text
COINGLASS_RATE_LIMIT_MAX_CALLS=10
COINGLASS_RATE_LIMIT_WINDOW_SECONDS=60
COINGLASS_RATE_LIMIT_SAFETY_MARGIN=1
COINGLASS_RATE_LIMIT_OVERFLOW=wait
COINGLASS_RATE_LIMIT_WAIT_TIMEOUT_SECONDS=75
```

其他 API 数据源按同样模式：

```text
TUSHARE_RATE_LIMIT_MAX_CALLS=
TUSHARE_RATE_LIMIT_WINDOW_SECONDS=

FINNHUB_RATE_LIMIT_MAX_CALLS=
FINNHUB_RATE_LIMIT_WINDOW_SECONDS=

ALPHA_VANTAGE_RATE_LIMIT_MAX_CALLS=
ALPHA_VANTAGE_RATE_LIMIT_WINDOW_SECONDS=

FRED_RATE_LIMIT_MAX_CALLS=
FRED_RATE_LIMIT_WINDOW_SECONDS=

COINGECKO_PRO_RATE_LIMIT_MAX_CALLS=
COINGECKO_PRO_RATE_LIMIT_WINDOW_SECONDS=
```

配置优先级：

```text
UI/Mongo 保存值
  > .env.local 导入值
  > provider 通用安全默认
  > 未配置时不做本地限流
```

注意：

- provider 代码可以声明“这个 provider 需要限流”。
- provider 代码不能写死某个账号的真实额度。
- 对 Coinglass、Tushare、Finnhub 这类需要 API key 的数据源，没填限流次数/时间就是不做本地限流；填了以后才按 UI / `.env.local` 的额度执行。
- 如果远端真的返回 429，再按 429 冷却逻辑记录并暂停对应数据源。

### 0.6 启动计时器的定义

“启动计时器”不是在后台开一个无限循环线程。

目标语义是：

```text
本次 report/select 开始时间 = run_started_at
第一个限流窗口 = [run_started_at, run_started_at + window_seconds)
第二个限流窗口 = [run_started_at + window_seconds, run_started_at + 2 * window_seconds)
```

实现方式：

1. report/select 开始时创建 `DataRunScheduleContext`。
2. 记录 `run_started_at`。
3. 对本次需要的 provider/source 初始化 rate-limit window。
4. 所有 provider batch reserve 都使用同一个 `run_started_at` 作为窗口锚点。
5. 当窗口额度用完：
   - `overflow=wait`：等待到下一窗口再继续。
   - `overflow=fail_fast`：不出网，写 `rate_limited` 缺口。

这样可以保证：

```text
从任务开始的一分钟内，只调用配置允许的次数。
```

### 0.7 429 后冷却

如果 provider 返回 429：

1. HTTP evidence 记录 `status_code=429` 和 `quota_signal=http_429`。
2. 如果响应有 `Retry-After`，按它计算 cooldown。
3. 如果没有 `Retry-After`，按该 provider 的窗口长度或默认冷却时间。
4. 写入 `provider_rate_limits` 的 cooldown 字段。
5. 本次 run 后续同 provider/endpoint 请求不继续硬打。
6. 结果进入 `data_gaps`，状态为 `rate_limited` 或 `cooldown_skipped`。

不能做：

- 429 后立刻换别的接口假装成功。
- 429 后继续把同一个 provider 的 optional/expensive 子请求打完。
- 把 `rate_limited` 写成 `remote_success`。

### 0.8 统一预提取如何减少请求次数

减少请求次数靠三层：

第一层：业务入口统一收集。

```text
report/select 一开始收集完整 DataRequest 清单。
```

第二层：同源合并。

```text
RequestCoalescer 合并同 provider、endpoint、市场、数据类型、粒度、source_role 的需求。
```

第三层：按 provider 能力批量切分。

```text
ProviderBatchPlanner 按 max_symbols_per_call、max_days_per_call、mergeable_fields 生成最少 provider batch。
```

例子：

```text
market worker 需要 BTC 日线
fundamental worker 也需要 BTC 基础行情字段
news/social worker 需要同一个时间窗口的相关市场上下文

目标：
  先合成 DataRequest 清单
  仓库已有的不打远端
  同 provider 可合并的只打一次
  不可合并的按限流排队
```

### 0.13 停止条件

遇到以下情况必须停下来问人：

- 为了统一预提取，需要让 Python 代替 worker 写分析结论。
- 为了让报告继续，需要把缺数据写成成功。
- 为了减少调用次数，需要把不同 source_role 的数据混成同一个事实源。
- 为了绕过限流，需要换未授权 provider 或创建隐藏 fallback。
- Tushare/AKShare SDK 或其它 provider SDK 内部 HTTP 无法审计，且实现需要宣称它已经完全受 managed HTTP 控制。

## 1. 结论

本次要修的不是 Coinglass 单点问题，而是所有外部数据源的统一出网控制问题。

人话版：

> 所有外部接口前面必须有一个公共闸门。  
> 同一轮报告里，同一个数据不要重复打远端；有人正在取，就等结果；刚被限流，就进入冷却；provider 内部拆出来的子请求也不能绕过闸门。

最终目标：

- 防止同一 run、同一资料包、同一 provider 参数被重复请求。
- 防止多个 worker 或多个 pack 并发打同一个外部接口。
- 防止 provider 内部一个逻辑调用拆成多次 HTTP 请求后绕过限流。
- 保留真实失败和真实缺口，不用缓存、fallback 或假数据伪装成功。

## 2. 上次修了什么，为什么没修好

上次实际完成了几块基础能力：

| 时间 | 修复内容 | 实际覆盖 |
| --- | --- | --- |
| 2026-05-16 | CRYPTO 共享 provider cache 和单一资料包入口 | 主要减少 worker 可见工具重复调用 |
| 2026-05-17 | Mongo cache / attempt / run plan / single-flight 合同 | 落了模型、状态、存储语义 |
| 2026-05-21 | `MongoRateLimitStore` | 有了持久化限流 reserve 能力 |
| 2026-05-18 | Coinglass 字段映射与 BTC live 验证 | 证明 BTC 路径能取到部分 Coinglass 数据 |

没有修好的地方：

1. **没有把所有真实出网请求强制接入公共闸门。**  
   现在 `ProviderExecutionEvidenceHelper.execute()` 会记录 raw、normalized、attempt、HTTP evidence，但它本身仍直接调用 `adapter.fetch()`。执行结果里仍大量出现 `single_flight_role="none"`。

2. **run plan 里有 `rate_limit_plan`，但 pack 执行层没有严格消费它。**  
   memory 里已经写过“后续 pack 执行层需要复用冻结的 call specs/cache keys/rate-limit plan”，说明当时只是计划和合同层闭合，不是所有 runtime 请求都已受控。

3. **provider 内部子请求绕过了 call spec 粒度的保护。**  
   例如一次 `onchain_signals` 内部会连续请求交易所余额、余额图、鲸鱼转账、USDT 稳定币净流、USDC 稳定币净流。外层看似一个 provider call，实际上是多个 HTTP call。

4. **测试样本太窄。**  
   BTC live 能过，不代表 AR/USDT、WIF/USDT、非主流币或高限流接口能过。之前没有证明“所有外部 HTTP 请求都会经过统一闸门”。

## 3. 设计原则

1. **公共层优先，不做单 provider 补丁。**  
   Coinglass、CoinGecko、DefiLlama、Yahoo、Tushare、AKShare、Tavily、LunarCrush、Polymarket、Reddit、SEC、FRED 等都要走同一套约束。

2. **两层闸门。**  
   第一层保护 provider call spec，例如 `market:coinglass:onchain_signals`。  
   第二层保护真实 HTTP 子请求，例如 `GET /spot/coin/netflow?symbol=USDC`。

3. **只减少请求，不伪造数据。**  
   命中缓存、共享结果、限流冷却、cached empty 都必须进入 attempt/readiness/data gaps，不能变成假 `remote_success`。

4. **限流失败后停止继续撞同源接口。**  
   同一 provider 在当前 run 中已经 429 或进入冷却后，后续低优先级子请求应直接跳过并记录缺口。

5. **缓存必须可解释。**  
   worker 看到的是自然语言资料包；审计层必须能看到 cache receipt、single-flight owner/consumer、rate limit reserve、HTTP evidence。

6. **OpenViking 不做 provider cache。**  
   OpenViking 继续做 approved material、manifest、lineage 和证据索引；provider cache / rate-limit / single-flight 继续由 Mongo/data_gateway 层负责。

## 4. 目标架构

目标数据流：

```text
worker 调用 claw_get_*_pack
  -> data_gateway pack service 加载本 run 的 DataRequest/ProviderCallSpec
  -> DomainPackService 选择当前 domain 的 ProviderCallSpec
  -> ProviderExecutionGate
       1. 查 call-spec cache
       2. 查 provider/run 冷却状态
       3. 申请 rate-limit reserve
       4. 进入 single-flight owner/consumer
       5. owner 执行 adapter.fetch
  -> ManagedHttpClient / HTTP 子请求闸门
       1. 子请求 cache
       2. 子请求 rate-limit reserve
       3. 同 provider 429 冷却
       4. HTTP evidence
  -> raw/normalized/attempt/cache 写入
  -> reader_brief + data_gaps
```

新增或改造的核心组件：

| 组件 | 作用 |
| --- | --- |
| `ProviderExecutionGate` | provider call spec 级别的缓存、限流、single-flight 总入口 |
| `ManagedHttpClient` | 所有显式 HTTP 请求的统一入口 |
| `HttpRequestKey` | 用 provider、method、url path、normalized params、body hash 生成子请求 key |
| `ProviderCooldownStore` | 记录 provider 或 endpoint 进入冷却的原因和过期时间 |
| `SubrequestCacheStore` | 缓存 provider 内部 HTTP 子请求结果，避免同 run 或短 TTL 内重复打远端 |
| `RateLimitPolicyResolver` | 从 run plan、provider metadata、默认策略中解析限流窗口和成本 |

## 5. 第一层：provider call spec 闸门

第一层解决“多个资料包或 worker 重复调用同一个 provider spec”的问题。

### 5.1 改造点

在 `ProviderExecutionEvidenceHelper.execute()` 外层增加 `ProviderExecutionGate`，由 `DomainPackService` 构造并注入。

当前执行方式：

```text
pack builder -> ProviderExecutionEvidenceHelper.execute -> adapter.fetch
```

目标执行方式：

```text
pack builder -> ProviderExecutionGate.execute -> cache/rate-limit/single-flight -> ProviderExecutionEvidenceHelper.execute -> adapter.fetch
```

### 5.2 执行规则

1. 先按 `ProviderCallSpec + PackRequest` 查 `MongoCacheStore`。
2. fresh cache 命中：返回 `CACHE_HIT` / `FRESH_CACHE`，不出网。
3. stale/cache error：写清楚状态，不伪装成功；是否继续远端取数由策略决定。
4. 查 `ProviderCooldownStore`：如果 provider 或 endpoint 处于冷却，直接返回 `RATE_LIMITED` 或 `REMOTE_ERROR` 类缺口，不出网。
5. 从 `RunProviderPlan.rate_limit_plan` 找当前 call key 的限流预算，调用 `MongoRateLimitStore.reserve()`。
6. reserve 失败：不出网，写 attempt 和 data gap。
7. reserve 成功：进入 `MongoSingleFlightCoordinator.run()`。
8. owner 执行真实 fetch；consumer 等 owner 结果，写 `SHARED_RESULT`。
9. owner 成功后写 raw、normalized、cache receipt。
10. owner 失败后 consumer 共享失败，不独立再打一次远端。

### 5.3 必须修正的现状

`ProviderAttempt.single_flight_role` 不能继续默认写死为 `none`。目标状态：

| 场景 | single_flight_role | status |
| --- | --- | --- |
| 真实远端 owner | `owner` | `remote_success` / `remote_error` / `empty` 等 |
| 同 run 共享成功 | `consumer` | `shared_result` |
| cache hit | `none` 或 `consumer`，按最终实现统一 | `cache_hit` |
| 限流未出网 | `none` | `rate_limited` 或现有最接近状态，必要时扩展枚举 |

如果现有枚举没有 `rate_limited`，实施时应新增明确状态；不要把限流写成普通 `remote_error`。

## 6. 第二层：HTTP 子请求闸门

第二层解决“一个 provider call 内部拆出多个 HTTP 请求”的问题。

### 6.1 问题样例

`coinglass/onchain_signals` 外层是一个 call spec，但内部至少可能请求：

- `/exchange/balance/list`
- `/exchange/balance/chart`
- `/chain/v2/whale-transfer`
- `/spot/coin/netflow?symbol=USDT`
- `/spot/coin/netflow?symbol=USDC`
- BTC 专属指标若 asset 为 BTC，还会请求多条 `/index/*`

如果只在 call spec 层限流，内部子请求仍会连续撞接口。

### 6.2 改造规则

所有 provider 内部显式 HTTP 请求必须改为 `ManagedHttpClient`：

```text
managed_http.get(provider="coinglass", endpoint="/spot/coin/netflow", params={...})
```

不能继续散落使用：

- `requests.get(...)`
- `urllib.request.urlopen(...)`
- provider 文件内私有 `_http_get_json(...)`
- provider 专属 `_coinglass_get(...)` 直接出网

Tushare/AKShare 或其它 provider SDK 内部出网不一定能完全替换为 `ManagedHttpClient`，但至少要通过 HTTP capture 拿到 evidence；能显式替换的本仓 provider HTTP 调用必须替换。OpenBB 本体已删除，不再作为需要验收的 SDK/runtime 目标。

### 6.3 子请求 key

`HttpRequestKey` 至少包含：

```text
provider
method
normalized_url_host
normalized_url_path
normalized_query_params
body_hash
provider_config_version
```

不得包含 secret、api key、token。  
query 参数需要排序和脱敏。

### 6.4 子请求缓存

子请求缓存只用于减少重复请求，不替代 provider normalized cache。

建议 TTL：

| 类型 | 默认 TTL |
| --- | --- |
| 同 run 子请求 | run 内有效 |
| 高频行情/盘口/清算 | 30-120 秒 |
| 新闻/搜索 | 5-15 分钟 |
| 基本面/filing/协议资料 | 30 分钟到数小时 |
| 429 冷却 | 按 `Retry-After`，没有则 60-300 秒 |

cached empty 必须显式记录，不能当成功。

### 6.5 provider 冷却

当子请求返回 429、明确限流文案、或 provider 返回全局 quota exceeded：

1. 写入 `ProviderCooldownStore`。
2. 后续同 provider 或同 endpoint 的低优先级请求直接跳过。
3. 如果有 `Retry-After`，按响应头冷却。
4. 没有 `Retry-After`，按 provider 默认冷却窗口。
5. 冷却结果进入 data gaps。

对于复合接口：

```text
如果核心子请求已经 429：
  不继续请求低优先级子接口。
  例如 Coinglass 余额接口已经限流，就不要继续打 USDT/USDC 稳定币净流。
```

## 7. Provider 优先级与短路规则

每个复合 provider call 需要给子请求分级：

| 等级 | 含义 | 行为 |
| --- | --- | --- |
| core | 当前资料包核心字段必需 | 失败后记录缺口，可继续少量同源必要请求 |
| optional | 增强字段 | provider 已限流或 core 失败时跳过 |
| expensive | 高成本或易限流字段 | 只有预算充足、无冷却时请求 |
| not_applicable | 标的不适用 | 不出网，直接写不适用 |

例子：

| provider | 子请求 | 等级 |
| --- | --- | --- |
| Coinglass | funding / OI / long-short | core |
| Coinglass | liquidation heatmap | core |
| Coinglass | exchange balance | core |
| Coinglass | USDT/USDC stablecoin netflow | optional/expensive |
| Coinglass | AHR999 for non-BTC | not_applicable |
| CoinGecko | coin market data | core |
| DefiLlama | protocol details | optional，且对非 DeFi 协议允许 not_applicable |
| Tavily | catalyst search | optional |
| LunarCrush | social metrics | optional，缺 key或限流不阻断 market |

## 8. 状态与 evidence 要求

新增或明确以下状态：

| 状态 | 语义 |
| --- | --- |
| `cache_hit` | 使用缓存，不出网 |
| `shared_result` | 使用 single-flight owner 结果，不出网 |
| `rate_limited` | 限流闸门阻止出网，或远端返回 429 |
| `cooldown_skipped` | provider 已处于冷却，主动跳过 |
| `cached_empty` | 缓存确认空结果 |
| `not_applicable` | 标的不适用，例如 AR/USDT 的 AHR999 |

如果现有枚举没有这些状态，应补枚举、模型验证和 exporter/readiness 映射。

每个被闸门处理的请求必须能回答：

- 为什么没有出网？
- 如果出网，谁是 owner？
- 有没有 consumer 共享？
- 命中了哪个 cache key？
- 用了哪个 rate-limit window？
- 是否进入 provider cooldown？
- 哪些子请求被跳过？
- reader brief 应该如何自然语言说明？

## 9. 实施步骤

### 阶段一：只做公共执行层，不动 provider 业务逻辑

目标：先让 call spec 级别真正受控。

改动：

1. 新增 `ProviderExecutionGate`。
2. `DomainPackService` 构造 gate，并让 market/fundamental/news/social/policy/hot_money/lockup 都通过 gate 执行 provider。
3. gate 接入 `MongoCacheStore`、`MongoRateLimitStore`、`MongoSingleFlightCoordinator`。
4. `RunProviderPlan.rate_limit_plan` 必须被消费；缺 plan 或 call key 不匹配显式失败。
5. `single_flight_role` 不再无条件写 `none`。

验收：

- 同一 run 内两个相同 call spec 只有一个 owner 出网。
- 第二个调用返回 `shared_result` 或 cache hit。
- reserve 失败不会调用 `adapter.fetch()`。
- reader brief 写清楚限流/共享/缓存状态。

### 阶段二：统一显式 HTTP 出网

目标：本仓 provider 文件里的 HTTP 请求都走 `ManagedHttpClient`。

改动：

1. 新增 `ManagedHttpClient`。
2. 迁移 `market_adapters.py`、`fundamental.py`、`news.py`、`social.py`、`policy.py`、`hot_money.py`、`lockup.py`、`polymarket.py` 中直接 `requests.get` / `_http_get_json` 的路径。
3. 保留 `http_capture.py` 做兜底 evidence，不把它当限流主机制。
4. 子请求返回 429 时写 provider cooldown。
5. 复合接口增加 core/optional/expensive 短路规则。

验收：

- `rg "requests.get|urlopen|_http_get_json"` 只允许出现在 `ManagedHttpClient`、HTTP capture、或明确豁免文件。
- Coinglass `onchain_signals` 在核心子请求 429 后不继续请求 USDT/USDC 稳定币净流。
- 同一 run 内相同 HTTP 子请求只真实出网一次。

### 阶段三：provider 级策略补齐

目标：不同 provider 有不同预算和短路策略。

改动：

1. 建立 provider rate-limit metadata：
   - provider
   - endpoint
   - window_seconds
   - max_requests
   - cost
   - cooldown_seconds
   - priority
2. Coinglass、CoinGecko、DefiLlama、Yahoo、Tushare、Tavily、LunarCrush 先补最小策略。
3. provider catalog / run plan 生成时把策略冻结到 run plan。
4. UI 设置页的“测试数据源”也要走同一闸门，不能测试页自己绕过。

验收：

- UI 测试数据源连续点击不会连续打远端。
- run plan 中能看到每个 provider 的预算。
- live run 后 Mongo 中能查到 rate-limit reserve 记录。

### 阶段四：真实样本回归

目标：用真实容易出问题的标的验证。

样本：

| 市场 | 标的 | 验证点 |
| --- | --- | --- |
| CRYPTO | AR/USDT | 非 BTC、Coinglass 子请求、CoinGecko/DefiLlama 缺口 |
| CRYPTO | BTC/USDT | BTC 专属 AHR999、BTC onchain 指标 |
| CRYPTO | WIF/USDT | provider 不支持或覆盖不足时不重复撞 |
| US | AAPL | Yahoo/SEC/FRED 等 data_gateway provider 路径不重复 |
| HK | 00700.HK | Yahoo/Tencent/Sina 多源不互相污染 |
| CN_A | 600519 | Tushare/AkShare/东方财富限流状态清晰 |

验收每个样本必须输出：

- provider attempts
- cache receipts
- single-flight owner/consumer
- rate-limit reserve
- HTTP evidence
- data gaps
- reader brief 中自然语言缺口说明

## 11. 不做什么

本方案不做：

- 不把 Python 变成 worker。
- 不让 Python 预取并改写业务报告。
- 不把 OpenViking 当 provider cache。
- 不新增 fallback provider 来掩盖失败。
- 不把限流、缓存命中或共享结果伪装成真实远端成功。
- 不为了减少缺口而删除 reader brief 中的数据缺失说明。

## 12. 风险与取舍

| 收益 | 代价 |
| --- | --- |
| 明显减少重复请求和 429 | 初期实现比单点修 Coinglass 大 |
| 所有 provider 行为可审计 | 需要补状态、测试和 evidence 映射 |
| 后续新增 provider 自动受保护 | provider 内部直接 HTTP 需要迁移 |
| 真实缺口更清楚 | 报告可能更频繁显示 `rate_limited` / `cooldown_skipped` |

最大风险：

如果只做第一层，不做第二层，Coinglass 这类内部多子请求问题还会复发。  
如果只做第二层，不做第一层，多个 worker/pack 之间仍会重复调用。  
所以必须两层都做。

## 13. 停止条件

出现以下情况必须停下来问人：

1. 需要改变 worker 调度或 OpenClaw/worker 权限边界。
2. 需要用 fallback provider 代替真实失败。
3. 需要把限流失败降级成成功来让报告更好看。
4. 需要放松 truthfulness hard gate。
5. 同一类 gate 修复两次后仍在 live run 中失败。
6. 某 provider 的官方限流规则不清楚，且默认保守策略会严重影响报告覆盖。

## 14. 完成标准

只有同时满足以下条件，才能说限流修复完成：

1. `ProviderExecutionGate` 已覆盖所有 pack domain。
2. 显式 HTTP 出网路径已迁移到 `ManagedHttpClient` 或有记录在案的豁免。
3. `RunProviderPlan.rate_limit_plan` 在 runtime 被实际消费。
4. Mongo 中能看到 cache、single-flight、rate-limit、cooldown 证据。
5. AR/USDT live run 中 Coinglass 429 后不继续连打低优先级子接口。
6. BTC/USDT live run 中 BTC 专属指标仍能正常取数。
7. CN_A/US/HK 至少各一个样本证明没有因新闸门破坏资料包。
8. reader-facing 报告只说明真实缺口，不出现假数据、假成功、假来源。
