# 数据层总体设计

状态：当前代码不代表已经全部完成；本文只描述当前目标合同和已拆除的边界，不保留历史方案。

## 1. 一句话

数据层是全市场统一取数、入库、限流和证据层。它不服务某个页面，也不决定投资结论。

## 2. 总流程

```text
worker/tool/report/select
  -> 业务数据项请求或内部仓库读取
  -> 项目必需数据清单
  -> 数据层内部 DataNeed
  -> 精确接口映射
  -> ProviderCallSpec
  -> Scheduler
  -> 执行闸和滑动窗口限流
  -> Fetch
  -> raw_payloads / normalized_datasets / provider_attempts
  -> DataResult
```

## 3. 上下游边界

上层只表达“要什么数据”，不能表达“叫哪个 provider、哪个 path、哪个 api_name”。

数据层内部先查项目必需数据清单，再查 provider 接口事实目录。项目清单来自 report、select、维护任务和 UI 探针的真实数据需求；provider 目录只是接口库存和实现依据。

数据层只返回：

- 数据行。
- raw/normalized/attempt 证据。
- 明确缺口。

数据层不做：

- report 是否继续。
- select 是否成功。
- worker 文案。
- 投资判断。

## 4. 远端入口

唯一远端入口是：

```text
DataAPI.request_data(...)
```

它接收业务数据项请求，返回 DataResult。数据层内部先把请求落到项目必需数据清单，再转换为 DataNeed 和 ProviderCallSpec。

已删除的公开入口：

- `DataAPI.get_data`
- `DataAPI.get_data_batch`
- `DataAPI.get_data_needs`

## 5. 本地仓库入口

内部本地仓库读取只允许：

```text
DataService.read_warehouse_batch(...)
```

它只读仓库，不出网，不选择 provider。

## 6. 项目必需数据清单

项目必需数据清单是唯一需求来源。它回答“项目需要什么数据”，不是回答“provider 有什么接口”。

每个市场都必须按这个顺序维护：

```text
项目需要的数据项
  -> 精确业务数据编号
  -> 标准输出合同
  -> 真实 provider API
  -> 参数映射
  -> parser/normalizer
  -> fallback 顺序
  -> 测试和 live 证据
```

worker 只看到业务数据项，例如日线、财报、公告、宏观、资金费率、OI、清算地图。worker 不知道 provider，也不知道内部业务数据编号。

## 7. 接口事实目录

每个 provider 必须有接口事实目录。目录记录接口本身能产出什么，不记录 worker 使用范围。

接口事实目录不能反向生成项目需求。一个 provider 有很多接口，只表示库存；只有进入项目必需数据清单并完成精确绑定、参数映射和 parser 的接口，才能进入 report/select/maintenance 的实际调用链。

保留密钥源：

- Tushare
- Coinglass
- Finnhub
- FRED
- Glassnode
- CoinGecko Pro

公共源也必须按同样方式登记接口事实，例如 AkShare、EastMoney、mootdx、Yahoo、Binance。

## 8. Provider 选择

planner 根据项目必需数据清单里的精确业务数据编号匹配接口。worker/tool 不能传内部编号。

禁止：

- 按 worker/report/select/domain 限制接口。
- 按 fields 或 字段覆盖声明 否决 provider。
- 上层直接指定 provider/path/api_name。
- 用 provider 接口目录反推项目需求。
- 把“项目绑定未完成”说成“provider 没有能力”。

优先级：

1. 已配置密钥的付费源。
2. 官方免费源。
3. 内置公共源。
4. 其它可用兜底源。

执行时必须按来源成组尝试，不能把不同来源交错撒网。同一来源可能包含多个互补接口；同一来源已经满足需求后，可以继续执行该来源剩余互补接口，但不得再打低优先级来源。

满足判定以项目精确业务数据编号为准。`public_api_id` 已绑定当前需求且字段/质量校验通过时，即使标准化 `data_type` 名字不同，也算满足。`data_type` 只表示归一化后的数据形态，不得变成新的白名单。

`planned_calls` / `scheduled_calls` 只表示候选和调度审计；真实调用以 attempt 证据为准。

## 9. 限流

所有真实出网统一走滑动窗口限流。

同一来源共用同一桶。任意连续窗口内不得超过设置值。

## 10. Mongo Collection

授权 collection 只有 8 个名称：

- `normalized_datasets`
- `raw_payloads`
- `provider_attempts`
- `provider_rate_limits`
- `single_flight_calls`
- `provider_result_cache`
- `dataset_manifests`
- `maintenance_jobs`

不允许按 provider 增加存储集合。

## 11. 事件数据

事件数据必须结构化。新闻、公告、政策、研报、日历、宏观发布、互动问答等不能只作为 raw 保存。

最低结构字段：

- `event_id`
- `source_type`
- `event_type`
- `title`
- `published_at` 或 `event_date`
- `instrument`
- `market`
- `url`
- `summary`
- `raw_ref`

## 12. 停止条件

需要停下来问人的情况：

- 要新增 provider 范围限制表。
- 要让 worker 指定 provider/path/api_name。
- 要让 worker 指定内部业务数据编号、api_id 或 provider 参数。
- 要从 provider 目录反推新的项目需求。
- 要新增 Mongo collection。
- 要把缺口隐藏成成功。
- 要绕过限流。
- 要用 mock/stub/fake 证明 live 数据完整。
