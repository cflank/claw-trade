# 加密币选币讨论纪要

状态：讨论纪要，未进入实施设计。  
日期：2026-05-29  
范围：记录本轮关于 CRYPTO `/select`、外部参考项目、历史数据下载、每日增量接口的讨论结论。

## 1. 背景问题

本轮讨论围绕一个核心问题：

```text
claw-trade 是否可以参考 A股选股模式，为加密资产建立 /select 流程：
先下载历史数据并离线批处理，用策略选出 20 个候选币，再交给 OpenClaw selection workers 评审。
```

涉及的外部参考项目：

- `CryptoSignal/Crypto-Signal`
- `Drakkar-Software/OctoBot`
- `Drakkar-Software/OctoBot-AI`

涉及的数据问题：

- 网上是否有类似 A股历史数据的预打包加密币历史数据。
- 是否存在类似 baostock 的每日增量下载接口。
- 是否能按 A股 `/select` 的方式，先由确定性策略压缩到 top 20，再由 worker 评审。

## 2. 总体结论

### Verdict

同意建设 CRYPTO `/select` 的方向，但只能复用 A股 `/select` 的架构模式，不能复用 A股策略本身，也不能直接搬用 CryptoSignal 或 OctoBot 的系统架构。

推荐形态：

```text
每日固定时间后台任务
  -> 构建 CRYPTO universe
  -> 下载/更新历史行情和补充数据
  -> 硬过滤低质量资产
  -> 策略打分压缩到 top 20
  -> 生成 approved candidate pack

用户 /select CRYPTO
  -> selection_strategist / selection_skeptic / selection_manager / selection_portfolio_manager 评审 top 20
  -> 输出 top 1-3 / 观察 / 放弃
  -> 用户确认后再进入 /report
```

## 3. 对 CryptoSignal 和 OctoBot 的判断

### CryptoSignal

CryptoSignal 更像技术指标扫描和提醒工具。

可参考：

- 指标扫描思路。
- RSI、MACD、均线、Ichimoku、MFI、OBV、VWAP 等技术规则组织方式。
- 配置化技术分析和提醒模式。

不适合直接参考：

- 完整投资研究流程。
- 多 worker 决策流程。
- claw-trade 的 artifact、provider payload、approved material 边界。

结论：CryptoSignal 适合参考“技术面 signal 规则”，不适合作为 CRYPTO `/select` 总架构。

来源：

- https://github.com/CryptoSignal/Crypto-Signal

### OctoBot

OctoBot 是完整交易机器人生态，覆盖交易所接入、策略自动化、回测、纸交易、实盘交易、UI、通知等。

可参考：

- 交易所接入。
- 回测和纸交易链路。
- 策略执行和交易所适配边界。

不适合直接参考：

- 把 OctoBot 当作 claw-trade 运行时。
- 把交易机器人执行框架放进 `/select`。
- 让外部 bot 框架拥有选币或投研 workflow authority。

结论：OctoBot 可以作为后续“交易执行/回测/纸交易”的参考，不应作为第一版 CRYPTO `/select` 的主架构。

来源：

- https://github.com/Drakkar-Software/OctoBot

### OctoBot-AI

OctoBot-AI 方向更接近“加密多智能体投研”，但当前仓库仍较新，不能直接当作稳定生产依赖。

结论：可以观察，不作为第一版设计依赖。

来源：

- https://github.com/Drakkar-Software/OctoBot-AI

## 4. 是否有预打包历史数据

明确结论：有。加密币历史数据有多个预打包下载来源，而且很多来源比 A股更容易获取。

### 推荐数据源

| 来源 | 是否预打包 | 内容 | 本轮判断 |
|---|---:|---|---|
| Binance Public Data | 是 | spot/futures/option 的 daily/monthly zip，K线、成交、聚合成交等，带 checksum | 第一优先 |
| Kraken Historical CSV | 是 | all pairs 历史 OHLCVT zip 和季度增量包 | 适合交叉校验 |
| Binance.US Historical Data | 是 | zip 文件，历史 K线、成交、聚合成交 | 可补充 |
| CryptoDataDownload | 是 | 免费 CSV，日线/小时/分钟 OHLCV | 适合探索，不建议唯一权威源 |
| Kaggle crypto datasets | 是 | top 200/250 等历史 OHLCV 数据集 | 只适合原型，不适合正式证据链 |
| CoinAPI Flat Files / Tardis.dev | 是 | gzip CSV、tick、order book、OHLCV、衍生品数据 | 商业级，后续评估 |

### 关键判断

可以像 A股那样先下载历史数据，离线批处理，再策略选 20 个币。

但两者有差异：

- A股通常是统一市场的全市场日线。
- 加密币通常按交易所、交易对、市场类型、时间粒度拆包。
- 第一版必须先定义 universe，例如 `Binance spot USDT pairs`，不能默认扫所有链上 token。

来源：

- Binance Public Data: https://github.com/binance/binance-public-data
- Binance Data Collection: https://data.binance.vision/
- Kraken Historical CSV: https://support.kraken.com/articles/360047124832-downloadable-historical-ohlcvt-open-high-low-close-volume-trades-data
- CryptoDataDownload: https://www.cryptodatadownload.com/
- CoinAPI Flat Files: https://www.coinapi.io/products/flat-files
- Tardis.dev: https://docs.tardis.dev/

## 5. 是否有类似 baostock 的每日增量接口

明确结论：有，但形式不是“一个 baostock 式 Python 包统一提供全市场增量”。最接近的是：

```text
Binance Public Data daily zip
+ Binance REST Kline startTime/endTime 增量拉取
```

### 首选组合

#### 1. Binance Public Data

适合作为主增量源。

已确认特征：

- 提供 `daily` 和 `monthly` 预打包文件。
- 新的 daily 数据通常次日可用。
- 新的 monthly 数据通常每月第一个周一可用。
- 每个 zip 有 `.CHECKSUM` 文件，可校验完整性。

用途：

```text
每日下载昨日 daily zip
  -> 校验 checksum
  -> 解压/归一化
  -> 写入本地 parquet/csv/cache
  -> 更新 selection feature snapshot
```

来源：

- https://github.com/binance/binance-public-data

#### 2. Binance REST API

适合作为缺口修复和小范围增量补拉。

已确认特征：

- `GET /api/v3/klines`
- 参数包括 `symbol`、`interval`、`startTime`、`endTime`、`limit`
- `limit` 默认 500，最大 1000。
- 可以记录本地最后 K 线时间，然后拉 `last_time + 1` 之后的数据。

用途：

```text
如果 daily zip 未到、缺文件或需要补缺口：
  -> 用 REST Kline 按 symbol + interval + startTime/endTime 拉增量
  -> 对齐 zip 数据
  -> 记录 provider attempt 和 data gap
```

来源：

- https://raw.githubusercontent.com/binance/binance-spot-api-docs/master/rest-api.md

#### 3. CoinGecko API

适合作为币种元数据、市值、成交额、供应量和聚合历史数据补充。

已确认特征：

- `/coins/markets` 可取支持币种的 price、market cap、volume、supply 等。
- `/coins/{id}/market_chart/range` 可按时间范围取历史 price、market cap、volume。
- 日线历史数据在 UTC 00:35 左右可用，具体受计划和缓存影响。

用途：

```text
补充 Binance 交易所行情无法直接提供的：
  -> market cap
  -> FDV
  -> circulating supply
  -> total supply
  -> coin id / metadata
  -> category
```

不建议：

- 不要用 CoinGecko 聚合价格替代 Binance 原始交易所 K 线作为主行情源。

来源：

- https://docs.coingecko.com/reference/coins-markets
- https://docs.coingecko.com/reference/coins-id-market-chart-range

### 其它可用但不作为第一主源

| 来源 | 增量能力 | 本轮判断 |
|---|---|---|
| OKX history candles | 支持 `after` / `before` 分页，最多 300 条/次 | 可做补充和交叉校验 |
| Coinbase candles | 支持 start/end/granularity，但每次最多 300 candles | 可做补充，不适合第一主源 |
| Kraken OHLC API | 有 `since`，但官方说明只返回最近 720 条 | 不适合作完整历史回补主源 |
| CoinAPI | 商业 API，可取 OHLCV、trades、order books | 后续商业级数据评估 |

来源：

- OKX API: https://app.okx.com/docs-v5/en/
- Coinbase candles: https://docs.cdp.coinbase.com/exchange/reference/exchangerestapi_getproductcandles
- Kraken OHLC: https://docs.kraken.com/api/docs/rest-api/get-ohlc-data
- CoinAPI OHLCV: https://www.coinapi.io/products/market-data-api/docs

## 6. 第一版 CRYPTO select 建议

### Universe

第一版建议只做 CEX 主流现货 universe。

建议初始范围：

```text
Binance spot USDT pairs
```

硬过滤建议：

- 排除稳定币。
- 排除杠杆代币。
- 排除明显包装币或锚定资产。
- 排除成交额过低资产。
- 排除历史太短资产。
- 排除交易状态异常资产。

不要第一版就做：

- 全链 token 扫描。
- DEX 新币扫描。
- meme 新币冲刺榜。
- 自动交易。

### 数据层

第一版建议：

```text
主行情:
  Binance daily/monthly zip

缺口修复:
  Binance REST Kline

元数据和市值:
  CoinGecko coins/markets + market_chart/range

交叉校验:
  Kraken CSV 或 OKX candles
```

后续增强：

- CoinGlass：funding、OI、liquidation、多空比、ETF。
- DefiLlama：TVL、fees/revenue、hacks、unlocks、treasury。
- Glassnode / CoinMetrics / Tardis.dev：商业级链上、微结构和高质量历史数据。

### 策略层

第一版可以先做确定性策略压缩，不让 LLM 扫全市场。

建议策略组：

- 流动性：成交额、成交额稳定性、交易所覆盖。
- 相对强度：多周期收益、相对 BTC/ETH 强弱。
- 趋势：均线结构、突破、回撤后修复。
- 波动和回撤：最大回撤、ATR、波动收敛或扩张。
- 成交量结构：放量突破、量价背离。
- 衍生品风险：funding、OI、清算簇，后续接 CoinGlass 后启用。
- 协议基本面：TVL、收入、FDV、解锁，后续接 DefiLlama 后启用。

输出：

```text
top 20 candidate pack
```

candidate pack 只放事实、指标、数据质量、来源摘要，不写自然语言投资理由。

### Worker 层

复用 A股 `/select` 的控制面模式：

```text
selection_strategist
selection_skeptic
selection_manager
selection_portfolio_manager
```

限制：

- worker 只评审已批准 top 20 candidate pack。
- worker 不直接调用交易所、CoinGecko、OpenBB 原子接口。
- LLM 不决定下一个 worker。
- `/select` 不自动触发 `/report`。
- 用户确认后，才对确认 ticker 启动现有 `/report`。

## 7. 关键风险

### 7.1 幸存者偏差

不能用“今天仍在交易的 top 300/top 500 币”去回测过去几年，然后声称策略有效。

需要记录：

- 每日 universe 快照。
- 上市/下架状态。
- 交易对上线时间。
- 数据缺失和停牌/暂停交易状态。

### 7.2 资产身份映射

加密资产 ticker 会重名。

正式路径不能只用 `BTC`、`ETH` 这种代码作为唯一主键。

建议至少记录：

```text
exchange
market_type
symbol
base_asset
quote_asset
coingecko_id
contract_address 可选
chain 可选
```

### 7.3 数据口径冲突

Binance 交易所 K 线、CoinGecko 聚合价格、CoinMarketCap 聚合价格、DEX 价格可能不一致。

处理原则：

- 主行情源必须固定。
- 补充源只能补字段或校验，不得静默覆盖主源。
- 冲突必须记录到 data gap / conflict / evidence。

### 7.4 不是所有币都有基本面

BTC、ETH、L2、DeFi 协议、meme、CEX 平台币的基本面框架不同。

不能把 A股 PE/PB/ROE 语言迁移到 CRYPTO。

CRYPTO report 已有项目规则：

- 不使用 PE/PB/ROE。
- 不把加密资产当股票。
- 缺少链上、解锁、TVL、FDV、治理、安全事件等证据时必须保留缺口。

## 8. Stop Conditions

以下情况应停止并重新设计：

- 想直接扫所有链上 token。
- 想用 LLM 直接全市场选币。
- 想把 A股策略或 A股阈值 fallback 到 CRYPTO。
- 想把 CoinGecko 当前 top N 当成历史 universe 回测。
- 想让 `/select` 输出最终买卖建议或自动交易。
- 想把 OctoBot 直接嵌进 claw-trade 当运行时。
- 想让 Python 直接写自然语言入选理由、投资判断或最终结论。
- 没有明确 CRYPTO 策略和数据源批准，却将 `/select CRYPTO` 伪装成已可生产运行。

## 9. 后续需要确认的问题

在进入正式设计前，需要人类确认：

1. 第一版 universe 是 `Binance spot USDT pairs`，还是 top N 市值币，还是多交易所交集。
2. 第一版数据频率是只做日线，还是日线加 4h。
3. 第一版 selection 目标是“选 1-3 个进入 `/report`”，还是输出可交易组合。
4. 是否允许接入 CoinGlass 作为第一版衍生品数据源。
5. 是否允许接入 DefiLlama 作为第一版协议基本面数据源。
6. 是否需要先做历史回测，还是先做每日候选包生成和人工评审。

## 10. 本轮明确推荐

第一版最短路径：

```text
CRYPTO /select v1
  -> Binance spot USDT universe
  -> Binance Public Data daily zip 主增量
  -> Binance REST Kline 缺口修复
  -> CoinGecko metadata / market cap / supply 补充
  -> 本地确定性策略选 top 20
  -> 复用 selection workers 评审
  -> 用户确认后进入 /report
```

该路径只读、可审计、可离线重算，符合 claw-trade 当前“确定性层压缩候选池，OpenClaw worker 评审候选包”的架构边界。
