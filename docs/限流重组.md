# 限流重组

状态：当前实施合同。

## 1. 目标

数据层只做三件事：

1. 接收上层的数据需求或工具调用。
2. 按项目必需数据清单找到已经登记的真实接口。
3. 统一限流、出网、入库、返回证据或缺口。

上层 worker、report、select、UI 只提交业务数据项（例如“日线”“资金费率”“公告”）和用途，不传 provider、path、api_name、url、token、header、api_id、内部需求类型字段 或字段清单。

项目必需数据清单是唯一需求来源。不能从 provider 官方接口目录反推“产品应该要什么数据”，也不能因为某个 provider 有一批接口就自动暴露给 worker。正确顺序是：

```text
项目/report/select 需要的数据项
  -> 精确业务数据编号
  -> 一个或多个真实 provider API
  -> 参数映射
  -> parser/normalizer
  -> 标准输出合同
  -> fallback 顺序和证据
```

provider 接口目录只是库存和实现依据，不是产品需求表。

## 2. 数据入口

远端取数只有一个入口：

```text
业务数据项请求 -> 项目必需数据清单 -> 数据层内部 DataNeed -> 精确接口映射 -> ProviderCallSpec -> Scheduler -> 执行闸 -> Fetch -> Ingest -> DataResult
```

本地仓库读取只有内部入口：

```text
DataService.read_warehouse_batch(...)
```

它只查本地仓库，不触发远端 provider。

已删除的旧入口：

- `DataAPI.get_data`
- `DataAPI.get_data_batch`
- `DataService.get_data`
- `DataService.get_data_batch`
- 旧远端组装链路

## 3. 项目必需数据清单

数据层必须先维护项目需要的数据项清单。清单由当前 report、select、维护任务、UI 探针真实需要驱动，不由 provider 目录驱动。

每个数据项必须至少说明：

- 市场：`CN_A`、`US`、`HK`、`CRYPTO`。
- 业务数据项：例如日线、实时价、盘口、财报、估值、公告、宏观、事件日历、资金费率、OI、清算地图。
- 使用方：只作为审计标签，不能改变 provider 候选。
- 标准输出字段。
- 是否允许本地计算派生，例如 MA、MACD、RSI、ATR。
- 是否需要结构化事件输出。
- 已绑定的真实 provider API 和 fallback 顺序。
- parser/normalizer 状态。
- 测试和 live 证据状态。

缺少项目数据项登记时，不能临时去 provider 目录里“猜一个相近接口”。必须补项目数据项、接口绑定、参数映射和 parser 合同。

## 4. 接口事实目录

每个 provider 的接口事实来自官方文档、SDK 文档、已验证公共接口或本地 provider 实现证据，不来自 worker 范围表。

目录里的每个接口必须至少说明：

- `source_type`
- `endpoint_id`
- 官方路径或 SDK 方法名
- 请求方法
- 参数模板
- 鉴权范围
- 限流桶
- HTTP 可见性
- 输出合同
- 结构化解析状态
- 文档来源

输出合同必须写清这个接口的真实输出。planner 只能用项目必需数据清单里已经绑定的精确业务数据编号匹配接口；业务数据编号不是 worker/tool 的输入。

接口目录允许比项目当前需要更大，但这些额外接口只表示库存，不能自动成为 worker 可请求的数据项，不能自动进入 report/select fallback。

禁止事项：

- 不能按 report/select/worker/domain 限制 provider。
- 不能按 fields 或 字段覆盖声明 否决 provider。
- 不能让 worker 传具体 provider/path/api_name。
- 不能把测试失败当成接口无能力；测试失败只能形成调用证据或缺口。
- 不能用 provider 接口目录反向生成项目需求。
- 不能把“接口目录里未登记”说成“provider 没有这个能力”；只能说“项目精确绑定未完成”。

## 5. 调用规则

同一个需求下，数据层按来源优先级尝试：

1. 已配置密钥的付费源。
2. 官方免费源。
3. 内置公共源。
4. 其它可用兜底源。

尝试单位是“来源组”，不是把不同来源交错撒网。一个来源下可能有多个互补接口；同一来源已经开始并产出满足当前需求的数据时，可以继续执行该来源剩余互补接口，但不得再调用低优先级来源污染结果。

判断“满足需求”以项目精确业务数据编号为准。只要 planner 生成的调用绑定到当前 `public_api_id`，且返回结果通过字段和质量校验，即使标准化后的 `data_type` 名字不同，也可以满足需求。`data_type` 是标准化存储类型，不是新的 provider 白名单或否决条件。

`planned_calls` / `scheduled_calls` 是审计用候选和调度清单；真实出网以 attempt 证据为准。高优先级来源已满足后，低优先级候选可以仍出现在计划里，但不能产生 attempt。

失败接口保留 attempt 证据；只有当前来源组不能满足时，才继续试下一个来源组。

缺口只能来自真实原因：

- 凭证缺失
- 权限不足
- 限流或任务预算不足
- 远端报错
- 远端空结果
- 结构化解析缺失
- 项目数据项没有精确接口绑定
- 证据写入失败

## 6. 事件结构化

事件类数据不能只保留 raw。

新闻、公告、研报、政策、日历、宏观发布、互动问答等接口必须有结构化输出合同。最低结构字段：

- `event_id`
- `source_type`
- `event_type`
- `title`
- `published_at` 或 `event_date`
- `instrument`
- `market`
- `url`
- `summary`
- `raw_ref`

如果 provider 返回了原始数据但没有结构化解析，结果必须标记为 parser_missing，不能伪装为完整数据。

## 7. 合并

合并只发生在 planner 生成的调用规格之后。

允许合并的条件：

- 同一个 provider。
- 同一个真实接口。
- 同一个鉴权范围。
- 同一个限流桶。
- 同一个 HTTP 可见性。
- 参数可以被该接口官方支持的 batch 方式表达。

不同 Tushare `api_name`、不同 Coinglass `path`、不同 catalog endpoint 不能合并。

## 8. 限流

所有出网请求必须经过共享限流桶。

同一个真实来源共用同一个桶，例如：

```text
ratelimit:tushare
ratelimit:coinglass
ratelimit:finnhub
ratelimit:fred
ratelimit:glassnode
ratelimit:coingecko_pro
```

限流是滑动窗口，不是自然分钟。

规则：

- 任意连续 60 秒内真实 HTTP 请求数不能超过配置值。
- 配置值来自数据源设置，不硬编码。
- structured provider 和 official raw call 共用同一个来源桶。
- 如果等待会超过任务 deadline，返回 `rate_limited_by_tool_budget`。

## 9. 调度

Scheduler 负责跨 worker、跨工具、跨重复需求合并待执行调用。

输入：

- DataNeed 列表。
- 当前任务 deadline。
- provider 限流配置。
- 已有缓存/仓库命中信息。

输出：

- 可执行调用。
- 因预算或限流跳过的需求。
- 合并证据。

Scheduler 不决定投资结论，不决定 report/select 是否通过。

## 10. 验收

必须同时满足：

- worker 工具入参不含 provider/path/api_name/url/header/token。
- worker 工具入参不含 api_id、内部需求类型字段、params、fields、字段覆盖声明。
- provider/API/path 只在数据层内部出现。
- 项目必需数据清单先于 provider 接口目录；接口目录不能反推产品需求。
- 同一需求在 report/select/ui_probe/maintenance 下 provider 候选一致。
- fields/字段覆盖声明 不参与候选否决。
- official catalog 不含 allowed_worker/domain/report_section。
- raw official call 只能由 planner 从 catalog 生成。
- 不同真实接口禁止误合并。
- 任意连续 60 秒限流不超过配置值。
- BTC market 不再一次生成固定多类请求。
- SDK 内部 HTTP provider 有风险登记，不能声称子请求级限流完成。
