# 限流重组与数据源能力释放设计

## 结论

本次要解决的不是单个 provider、单个接口或 BTC 单点问题，而是整条数据获取链路的问题。

目标是把当前的：

```text
worker 调固定资料包 -> 资料包按手写清单取数 -> provider selector 按字段/范围过滤 -> 出网
```

改成：

```text
worker 提数据需求 -> 数据层 planner 选源/合并/排队 -> 统一限流 -> 官方接口真实调用 -> 留证据 -> 返回结果或真实缺口
```

核心原则：

1. worker 不知道 Tushare、Coinglass、Finnhub、FRED、Glassnode、CoinGecko Pro 等具体 provider。
2. 数据层不再用 worker、domain、report/select、市场范围去限制 provider 能力。
3. 官方接口目录只说明接口怎么调，不说明哪个 worker 或哪个业务范围能不能用。
4. 每次真实出网前都必须进入同一个 provider 滑动窗口限流桶。
5. 缺数据必须来自真实调用结果、凭证状态、权限、限流、远端错误、解析缺失或任务预算，不再来自手写白名单。
6. 远端请求入口必须是 `DataNeed`，不是固定 pack 生成的 `DataRequest(data_type, fields)`。
7. `fields` 只能用于结果解析和质量校验，不能用于 provider 候选否决。
8. provider 限流只定义窗口和次数；等待多久由当前 worker/tool 的 `deadline_at` 决定。

## 已确认现状

### 1. 白名单复发的根因

历史设计里，worker 被限制为只看自然语言资料包。后来资料包逐渐变成固定数据清单。

当前报告链路仍存在这些边界：

- 前线 worker 主要暴露 `claw_get_market_pack`、`claw_get_fundamental_pack`、`claw_get_news_pack`、`claw_get_social_pack`。
- `src/claw_trade/reports/data_pack_bridge.py` 中存在 `_CN_A_DOMAIN_DATASETS`、`_CRYPTO_DOMAIN_DATASETS` 等固定清单。
- 固定清单会生成 `DataRequest(data_type, granularity, fields)`，因此请求集合仍由 pack 决定。
- CRYPTO market 仍可能一次生成多类 market 请求；150s partial 只是超时保护，不是请求模型修复。
- `ProviderSelector` 仍按 `data_type`、`granularity`、`fields` 匹配 provider capability。
- 当前 `coverage_fields`/`fields` 参与候选筛选，仍可能变成新的字段白名单。
- 2026-06-11 已新增 official raw API 通道，但 memory 明确记录：旧结构化 provider 能力表继续用于报告/入库字段选择。
- 当前 official raw API 是调用方传 `path` 或 Tushare `api_name` 的 raw pass-through，还不是机器可读的官方接口目录。

因此，之前修复只是让底层“能显式调用官方接口”，没有让报告链路真正“按需释放 provider 能力”。

### 2. 限流现状

当前已有能力：

- `RateLimiter.reserve()` 已有滑动窗口逻辑。
- Mongo 中保存 provider 限流状态和请求时间戳。
- `managed_http` 出网前会 reserve。
- 429 后会写 cooldown。
- settings/env 可配置 `rate_limit_max_calls`、`rate_limit_window_seconds`、`rate_limit_safety_margin` 等。

当前缺口：

- `DataRunScheduler.schedule()` 当前基本是空实现，没有真正提前排队、重排、降级。
- 不是所有 SDK 内部请求都能证明走了真实 HTTP 子请求级限流。
- pack 会一次制造很多请求，尤其 CRYPTO market pack 之前一次拉 17 类数据。
- 现有 full-chain 证据还不能证明所有 provider、所有 worker、所有真实 HTTP 都进入同一个动态限流桶。

## 非目标

本设计不做这些事：

1. 不允许 worker 直接指定 provider、URL、path、api_name 或 header。
2. 不开放任意 HTTP。
3. 不把 provider 官方文档塞进 prompt。
4. 不让 bull/bear/trader/risk/PM 默认直接出网取数。
5. 不用“补更多 pack 字段”的方式解决白名单。
6. 不因为没有 parser 就说 provider 没能力。
7. 不让 worker/tool input 携带 provider、path、api_name、url、header、token。
8. 不把 `data_type`、`fields`、worker、domain、consumer 当 provider 候选否决条件。

## 目标架构

### 1. Worker 只表达数据需求

前线 4 个 worker 可以请求数据：

- market_analyst
- fundamental_analyst
- news_analyst
- social_analyst

worker 不能说：

```text
调 Tushare daily
调 Coinglass funding
```

worker 只能说：

```text
我要 A股资金流
我要 A股公告
我要盘口
我要 BTC 资金费率
我要 BTC 期权未平仓量
我要链上交易所净流入
```

provider 选择权属于数据层。

### 2. 新增统一数据需求工具

前线 worker 暴露高层工具，语义是“请求某类数据”。

这个工具的机器合同是 `DataNeed`。

`DataNeed` 是远端取数的唯一入口。固定 pack 不得直接生成远端 `DataRequest`。

`DataNeed` 最小字段：

```text
need_id
need_kind
market
instrument
time_range
granularity
priority
requested_by_worker
purpose
freshness_policy
deadline_at
```

含义：

- `need_kind` 是业务事实需求，例如 `capital_flow`、`official_filing`、`funding_rate`、`options_open_interest`。
- `instrument` 是标的，例如 `600519.SH`、`BTC/USDT`。
- `priority` 用于预算不足时排序，不用于 provider 范围限制。
- `deadline_at` 是本次 worker/tool 的截止时间，用于决定还能不能等限流窗口。

输入示例：

```text
need: capital_flow
market: CN_A
symbol: 600519.SH
time_range: 300 trading days
granularity: daily
purpose: market_analysis
```

```text
need: funding_rate
market: CRYPTO
symbol: BTC/USDT
time_range: 30 days
granularity: hourly
purpose: derivatives_crowding
```

工具输入不包含：

- provider
- path
- api_name
- URL
- header
- token

如果 tool schema、OpenClaw provider payload、worker prompt 中出现这些字段，属于合同失败。

输出必须包含：

- status
- readable_summary
- normalized_refs
- raw_refs
- attempt_refs
- gaps
- provider_attempts_summary

worker 只基于结果和缺口写报告，不接触密钥、URL 和内部执行计划。

### 2.1 DataNeed 到 DataRequest 的边界

`DataRequest(data_type, fields)` 只能由数据层 planner 在内部生成。

禁止：

```text
worker/pack -> 固定 data_type/fields 清单 -> DataRequest -> provider selector
```

允许：

```text
worker -> DataNeed -> planner -> ProviderCallSpec/DataRequest -> executor
```

这里的关键区别：

- `DataNeed` 表达“我要什么事实”。
- `DataRequest`/`ProviderCallSpec` 表达“本次准备怎么取”。
- worker 和 pack 不能直接决定后者。

### 3. 默认资料包降级

保留默认资料包，但它只做三件事：

1. 常用数据预热。
2. 本地缓存读取。
3. 已结构化摘要。

更严格地说：

```text
pack 可以读缓存/摘要。
pack 不能生成远端请求清单。
pack 不能作为 DataNeed 的替代入口。
```

资料包不能再做这些事：

1. 决定 provider 能力。
2. 阻止额外数据需求。
3. 用 `no_candidate` 作为终局。
4. 因字段没登记就不尝试。
5. 因 consumer 是 report/select 就改变 provider 候选。
6. 用 `_CN_A_DOMAIN_DATASETS`、`_CRYPTO_DOMAIN_DATASETS` 这类清单决定本轮要远端拉什么。

实施目标不是“保留固定 pack，再给 worker 多一个 need 工具”。

实施目标是：

```text
远端请求集合只来自 DataNeed planner。
pack 只负责读取已存在的缓存/摘要，或展示 DataNeed 结果。
```

### 4. 官方接口目录

每个 provider 按官方文档登记接口调用事实。

目录必须是机器可读 catalog，建议位置：

```text
src/claw_trade/data_gateway/providers/official_catalog/
```

每个保留 provider 一个 catalog 文件或模块：

```text
tushare
coinglass
finnhub
fred
glassnode
coingecko_pro
```

目录字段：

```text
provider
endpoint_id
official_path_or_api_name
method
required_params
optional_params
auth
rate_limit_bucket
batch_policy
parser_status
official_doc_ref
http_visibility
request_template
response_shape
```

目录禁止出现：

```text
allowed_worker
allowed_domain
allowed_report_section
provider_scope
only_for_market
only_for_fundamental
```

人话：

```text
目录只说明这个接口怎么调，不说明它只能给谁用。
```

`endpoint_id` 必须是官方接口粒度，不能所有 raw call 都叫 `official_api_call`。

示例：

```text
provider: tushare
endpoint_id: tushare.daily
official_api_name: daily
```

```text
provider: coinglass
endpoint_id: coinglass.futures_funding_rate_history
official_path: /...
```

真实 call spec 的合并键必须包含：

```text
provider
catalog_endpoint_id
official_path_or_api_name
auth_scope
normalized_params_shape
```

这样可以防止不同 Tushare `api_name` 或不同 Coinglass `path` 被错误合并。

### 4.1 Planner-only call spec

worker/tool input 永远不能传：

```text
provider
path
api_name
url
header
token
```

只有 planner 可以从 official catalog 生成 `ProviderCallSpec`。

`ProviderCallSpec` 最小字段：

```text
call_id
need_ids
provider_id
catalog_endpoint_id
official_path_or_api_name
method
params
auth_scope
rate_limit_bucket
http_visibility
parser_status
batch_key
official_doc_ref
deadline_at
```

`official_api.py` 这类 raw executor 只能消费 planner 生成的 `ProviderCallSpec`，不能继续让上层直接手写 path/api_name。

没有 parser 时，仍必须能返回 raw：

```text
status: success_raw
raw_ref: ...
parser_status: parser_missing
```

不能因为没有 parser 就写成：

```text
no_candidate
source_unavailable
provider_not_capable
```

### 5. 数据层 planner

planner 接收数据需求后负责：

1. 把数据需求翻译成候选官方接口。
2. 按已配置 provider、凭证、付费优先级、缓存、新鲜度、成本排序。
3. 去重。
4. 按官方 batch policy 合并。
5. 按 provider 限流桶排队。
6. 执行真实调用。
7. 返回 raw、normalized、attempt 和可读摘要。

这里允许存在“数据需求到接口”的解析索引，例如：

```text
capital_flow
  -> Tushare moneyflow
  -> EastMoney fund flow
  -> AkShare compatible fund flow
```

但这个索引不是业务白名单。它不能说：

```text
Tushare 只能用于 capital_flow
Coinglass 只能用于 derivative
```

它只回答：

```text
为了拿 capital_flow，哪些官方接口可能可用。
```

如果一个 provider 有官方接口但 resolver 暂时不知道如何把某个自然语言需求映射过去，状态必须是“需求解析未覆盖”，不能说 provider 没能力。

### 5.1 Selector 禁止项

provider 候选选择只能使用这些约束：

```text
market
need_kind
instrument identity
time_range/granularity compatibility
credential availability
source enabled/disabled
source_role priority
provider health/cooldown
official catalog endpoint availability
```

不能使用这些条件否决 provider 候选：

```text
worker_id
domain
consumer=report/select/ui_probe/maintenance
report section
data_type
fields
coverage_fields
```

`fields` 的作用只能是：

1. parser 输出校验。
2. normalized rows 质量检查。
3. readable summary 中说明字段缺失。

`fields` 不能用于：

```text
这个 provider 没声明该字段，所以不进入候选。
```

同一个 `DataNeed` 在以下 consumer 下，provider 候选集合必须一致：

```text
report
select
ui_probe
maintenance
```

除非只是审计标签不同，不能改变候选集合。

### 5.2 Resolver 未覆盖语义

如果 planner 无法把 `DataNeed` 翻译成任何 official catalog endpoint，返回：

```text
resolver_mapping_missing
```

含义是：

```text
当前 resolver 没有把这个需求映射到接口。
```

它不能表达：

```text
所有 provider 都没有能力。
```

也不能替代 live attempt。

## 请求合并

### 合并位置

请求合并在数据层 planner 完成，不由 worker 决定，也不写死在某个 worker prompt 里。

流程：

```text
worker 数据需求
-> planner 生成候选接口请求
-> 去重
-> 按 batch_policy 合并
-> 限流排队
-> 出网执行
```

### 合并依据

只按官方接口目录里的 `batch_policy` 合并。

可声明：

```text
supports_symbol_batch
supports_field_batch
supports_time_range
max_symbols
max_days
mergeable_params
```

默认规则：

1. 同 provider、同 endpoint、同鉴权、同参数结构，才可能合并。
2. 不同 provider 不合并。
3. 不同 endpoint 不合并。
4. Tushare 不同 api_name 不合并。
5. Coinglass 不同 path 不合并。
6. 官方未声明支持批量，不合并。

合并失败不是数据缺口，只是多次请求。

### 合并验收

1. 同一 run 内两个 worker 请求同一数据，只允许一次真实出网。
2. 同 provider、同 endpoint、官方支持批量时必须合并。
3. 官方不支持批量时必须分开发，并记录不能合并的原因。
4. 合并后每个原始数据需求仍能追踪到自己的结果、raw ref、normalized ref 或缺口。

## 动态限流

### 基本规则

provider 限流配置只表达远端规则：

```text
provider: coinglass
max_calls: 10
window_seconds: 60
```

含义：

```text
任意连续 60 秒最多 10 次真实出网。
```

不再把 `wait_timeout_seconds` 作为 provider 限流核心字段。

provider 配置中不再允许用 `rate_limit_wait_timeout_seconds` 决定等待行为。

历史字段如仍存在，只能在迁移期被忽略或迁移到任务预算配置；实现层不得继续从 provider settings 读取它来决定是否等待。

### 为什么必须是滑动窗口

错误做法是固定自然分钟：

```text
12:00:00 - 12:00:59 允许 10 次
12:01:00 - 12:01:59 又允许 10 次
```

这样可能出现：

```text
12:00:55 打 10 次
12:01:01 又打 10 次
```

6 秒内 20 次，远端仍会限流。

正确做法：

```text
每次真实出网前，查过去 60 秒内该 provider bucket 已有几次请求。
少于 10 次，放行。
等于 10 次，等待最早一次请求过期。
```

### Provider bucket

同一个真实 provider 共用同一个桶。

例如 Coinglass：

```text
funding
open_interest
long_short_ratio
options
liquidation
onchain
```

都扣同一个：

```text
ratelimit:coinglass
```

Tushare：

```text
daily
moneyflow
fina_indicator
anns_d
```

都扣同一个：

```text
ratelimit:tushare
```

不能每个 endpoint 各算 10 次。

### 等待由任务预算决定

provider 限流只定义：

```text
10 / 60s
```

是否等得起，由当前任务预算决定。

例如：

```text
tool_budget_seconds: 180
```

第 11 次请求需要等 22 秒：

- 剩余预算够，排队等。
- 剩余预算不够，不出网，返回 `rate_limited_by_tool_budget`。

provider 限流规则不能被突破。

### 任务 deadline 合同

每个 `DataNeed` 必须携带 `deadline_at`，或者由当前 worker/tool runtime 注入。

`deadline_at` 必须传递到：

```text
DataNeed
-> NeedPlan
-> ProviderCallSpec
-> ScheduledCall
-> ExecutionGate
-> ManagedHttp
```

执行层等待限流窗口时，不能读取 provider 的 wait timeout。

它只能比较：

```text
next_available_at <= deadline_at
```

如果成立，等待后 reserve。

如果不成立，不出网，返回：

```text
rate_limited_by_tool_budget
```

### RateLimiter 合同

`RateLimiter` 不应该把“等待多久”写死在 provider policy 里。

需要提供等价能力：

```text
peek(provider_bucket, now) -> next_available_at / available_now
reserve(provider_bucket, now) -> reserved / retry_after
```

或者：

```text
reserve(provider_bucket, now, deadline_at)
```

但语义必须是：

```text
provider policy 只管 max_calls/window_seconds。
deadline_at 决定能不能等。
```

### 出网执行规则

每次真实 HTTP 前：

1. 读取 provider bucket 过去 `window_seconds` 内的请求时间戳。
2. 如果数量 `< max_calls`，写入当前请求时间戳并放行。
3. 如果数量 `>= max_calls`，计算最早时间戳过期时间。
4. 如果任务预算够等，等待后再次 reserve。
5. 如果任务预算不够等，返回限流缺口，不出网。
6. 如果远端返回 429，写 cooldown。
7. cooldown 期间不继续撞同一 provider 或可确认的 endpoint。

### Scheduler 要补齐

当前 `DataRunScheduler.schedule()` 基本是空实现。重组后 scheduler 必须：

1. 收集本轮所有数据需求。
2. 合并重复请求。
3. 按 provider 分桶。
4. 查询每个 bucket 剩余额度。
5. 按优先级排序：
   - 基础行情优先。
   - 多个 worker 共同需要的数据优先。
   - 用户明确需要的数据优先。
   - 高成本、低优先级数据靠后。
6. 在预算不足时返回明确缺口，不硬冲远端。

### Scheduler 输入输出合同

输入：

```text
run_id
worker_id
stage
data_needs
official_catalog_snapshot
provider_settings_snapshot
rate_limit_snapshot
cache_snapshot
deadline_at
```

输出：

```text
NeedPlan
  planned_calls: ScheduledCall[]
  shared_results: SharedNeedResult[]
  skipped_needs: DataNeedGap[]
  merge_evidence: MergeEvidence[]
  rate_limit_evidence: RateLimitEvidence[]
```

`ScheduledCall` 最小字段：

```text
call_id
need_ids
provider_id
catalog_endpoint_id
params
batch_key
rate_limit_bucket
earliest_start_at
deadline_at
priority
```

`skipped_needs` 用于预算不足或 resolver 未覆盖：

```text
need_id
reason
evidence_refs
```

### 跨 worker 聚合

同一个 report run 内，多个 worker 请求同一个语义需求时，必须共享。

需要 run-scoped plan/store：

```text
semantic_need_key = market + instrument + need_kind + granularity + normalized_time_range
```

规则：

1. 如果同一 `semantic_need_key` 已经有 fresh result，直接返回 shared result。
2. 如果同一 `semantic_need_key` 正在执行，走 single-flight 等待/共享。
3. 如果需要新取数，scheduler 只生成一次远端 `ScheduledCall`。
4. shared result 必须保留每个 worker 原始 `need_id` 的 evidence 映射。

这样才能解决“market/fundamental/news/social 各自重复拉同一 provider”的问题。

### 预算不足处理

如果 provider bucket 当前满了，下一次可用时间超过 `deadline_at`：

```text
不出网
写 DataNeedGap(reason=rate_limited_by_tool_budget)
写 rate_limit_evidence
返回 partial
```

不得：

```text
继续撞远端
等待超过 deadline
把未执行写成 provider_error
```

## 证据模型

每个数据需求必须能追踪：

```text
需求是什么
planner 选了哪些候选接口
哪些请求被合并
哪些请求排队
真实调用了哪些接口
每次 reserve 的 provider bucket 是什么
返回了什么
raw 在哪里
normalized 在哪里
缺口原因是什么
```

允许的缺口原因：

- credential_missing
- source_disabled
- permission_denied
- rate_limited
- rate_limited_by_tool_budget
- cooldown_skipped
- provider_empty
- provider_error
- parser_missing
- date_range_missing
- resolver_mapping_missing

这些 reason 必须在模型层闭合。

如果当前 `DataGap` / `GapReason` / `DataResultStatus` / `FetchStatus` 没有对应枚举，实施时必须先扩 enum 和合同测试，不能退化成：

```text
provider_error
empty_result
no_candidate
```

### 状态映射

`success_raw` 不是缺口。

含义：

```text
官方接口成功返回 raw。
raw_ref 已保存。
暂时没有 normalized rows。
```

实现时应映射为：

```text
DataResultStatus: partial 或 ready_raw
FetchStatus: success
DataGap: parser_missing only if worker 需要结构化字段但当前没有 parser
```

如果当前模型没有 `ready_raw`，必须明确扩展或使用现有 `partial`，并用 `parser_missing` 说明结构化缺失。

`provider_empty` 表示 provider 真实返回空结果；它不同于：

```text
resolver_mapping_missing
credential_missing
rate_limited
```

`permission_denied` 表示 provider 返回权限/套餐不足；不能混成普通 `provider_error`。

`rate_limited_by_tool_budget` 表示：

```text
provider 限流规则可以等待，但当前 task deadline 不够。
```

它不同于远端 429，也不同于本地 fail_fast。

禁止的缺口原因：

- provider 被 worker 范围禁止
- provider 被 report/select consumer 禁止
- provider 不属于 market/fundamental/news/social
- 字段未登记所以不试
- no_candidate 作为最终结论

`no_candidate` 禁止范围限定为数据层终局缺口。

如果某个内部分析模块使用 `no_candidate` 表示“没有找到技术形态候选”，例如 CryptoLens 内部指标状态，不属于本设计禁止范围。

## 验收标准

验收必须包含 contract tests 和 live/focused tests。不能只靠一次 full-chain happy path。

### A股 600519

运行 A股全链或 focused live：

worker 请求：

- 资金流
- 公告
- 盘口
- 财务指标

验收：

1. worker prompt/tool input 不出现 Tushare、AkShare、mootdx、EastMoney 作为调源指令。
2. 数据层自己选择可用 provider。
3. report/select consumer 不改变 provider 候选。
4. 缺口必须来自真实 provider attempt。

### BTC

运行 BTC focused live：

worker 请求：

- 资金费率
- OI
- 多空比
- 期权未平仓量
- 链上交易所净流

验收：

1. worker 不指定 Coinglass、Glassnode、CoinGecko Pro。
2. 数据层自己选源。
3. 不再通过一个 market pack 开局全拉 17 类。
4. 缺口必须来自真实 provider attempt、限流、权限、空结果、parser_missing 或预算。

### 合并

验收：

1. 同一 run 内两个 worker 要同一数据，只出网一次。
2. 同 provider、同 endpoint、官方支持批量时必须合并。
3. 官方不支持批量时分开发，并记录不能合并的原因。
4. 合并不丢 evidence。

### 限流

配置：

```text
coinglass: 10 / 60s
tushare: 10 / 60s
```

制造超过 10 个同 provider 真实请求。

验收：

1. 任意连续 60 秒真实 HTTP 不超过 10 次。
2. 第 11 次必须排队，或因任务预算不足返回 `rate_limited_by_tool_budget`。
3. Mongo 中可查 reserve 时间戳、provider bucket、attempt、cooldown。
4. final report 中的数据缺口来自真实证据，不来自白名单。

### SDK 内部 HTTP 风险

每个 `http_visibility=sdk_internal_unknown` 的 provider 必须进入强制清单。

清单字段：

```text
provider_id
endpoint_id
official_or_sdk
why_sdk_internal_unknown
outer_gate_covered
subrequest_visibility
migration_priority
live_evidence_ref
residual_risk
```

规则：

1. 外层 provider call 必须进入 provider bucket。
2. SDK 内部 HTTP 不可见时，不能声称子请求级限流完成。
3. 能迁移到 `managed_http` 的接口必须给迁移优先级。
4. 不能用“SDK capture only”冒充完整限流证据。

## 实施顺序建议

### Phase 1：合同冻结

1. 写 `DataNeed` 机器合同。
2. 写 worker 数据需求工具 schema，禁止 provider/path/api_name/url/header/token。
3. 写 official provider catalog 合同，禁止 allowed_worker/domain/report_section。
4. 写 planner-only `ProviderCallSpec` 合同。
5. 写 selector 禁止字段/consumer/domain/worker 否决合同。
6. 写滑动窗口限流和 `deadline_at` 合同。
7. 写 gap reason/status 枚举合同。
8. 写禁止白名单回流合同。

### Phase 2：数据层 planner

1. 实现数据需求到候选接口解析。
2. 实现去重。
3. 实现 batch_policy 合并。
4. 实现 provider 优先级和凭证过滤。
5. 保证 resolver 不按 worker/domain/consumer 限制 provider。
6. 保证 `fields` 只做结果校验，不做候选否决。
7. 生成 planner-only `ProviderCallSpec`，禁止上层手写 path/api_name。

### Phase 3：限流重组

1. 删除 provider 限流里的 `wait_timeout_seconds` 核心语义。
2. 把等待决策移到任务预算。
3. 将 `deadline_at` 传入 scheduler/gate/managed_http。
4. 补齐 scheduler 输入输出合同。
5. 所有 managed_http 出网进入 provider bucket。
6. structured provider 和 official raw call 共用同一 provider bucket。
7. SDK 内部不可控请求进入强制风险清单，并优先改为 managed_http。

### Phase 4：worker 工具接入

1. 前线 worker 增加高层数据需求工具。
2. 默认资料包降级为缓存/摘要入口，不再生成远端请求清单。
3. 后线 worker 不直接出网。
4. 缺数据时由前线补取或写真实缺口。
5. OpenClaw provider payload 验证 worker 不知道 provider/path/api_name。

### Phase 5：live 验收

1. A股 600519 focused live。
2. BTC focused live。
3. provider 限流压力测试。
4. full-chain report 检查 final report、provider attempts、raw refs、normalized refs、rate-limit refs。
5. contract tests 全部通过后，再跑 live；不得用 live happy path 替代合同测试。

## 停止条件

出现以下情况必须停止，不允许继续局部补丁：

1. 需要让 worker 直接知道 provider/path/api_name。
2. 需要新增 worker/domain/provider 业务白名单。
3. 需要绕过 provider 限流桶。
4. 需要把未真实调用写成缺口结论。
5. 需要用 parser 缺失证明 provider 没能力。
6. 需要用 happy-path 单测证明 live 全链完成。
7. 需要让 `fields`/`coverage_fields` 继续否决 provider 候选。
8. 需要继续让 pack 固定清单生成远端请求。
9. 需要让 provider 配置决定等待上限，而不是 task `deadline_at`。
