# 工控机第一版签名更新与回滚实施计划

日期：2026-06-26
状态：部分实施

当前分支状态：已完成生产包、路径、systemd、kiosk、最小 rescue 服务、恢复出厂入口、manifest 校验、Ed25519 签名验证 helper、updater 状态文件、对象存储 signed manifest 检查 API、signed archive 下载/hash/签名校验、设置页手动安装入口、root-owned apply-update systemd 一次性服务、root helper 复验 signed manifest/archive 后安全解压/preflight、`current` 原子切换、服务重启健康检查和失败回滚代码路径；尚未完成 systemd updater service/timer、VM/systemd/真实 Chrome 验收。

## 目标

在正式工控机生产版中交付单一 `stable` 通道的签名更新能力：

- 设备从对象存储读取静态更新清单；
- 只安装签名和 hash 都通过的 release 包；
- 新版本安装到独立 release 目录，不覆盖当前版本；
- `current` 原子切换后运行健康检查；
- 健康检查失败时回滚到上一可用版本；
- 更新过程不覆盖客户配置、授权、API KEY、报告、日志和本地数据。

本计划承接 `工控机生产部署设计.md` 的“远程更新”章节。它不是远程运维系统，不提供远程 shell、远程命令、设备任务拉取或自建更新后台。

## 一句话边界

第一版远程升级不需要自建服务器，但至少需要一个只读对象存储。

升级对象是 `claw-trade` 应用，不是 Ubuntu 系统。它不执行 `apt upgrade`，不升级内核，不重装系统，不改客户机器上的 OS 基线。

Ubuntu 只提供承载能力：`systemd` 管服务，`/opt/claw-trade` 放应用，`clawtrade` 用户运行后台和 UI，`clawkiosk` 用户运行 kiosk 浏览器。

实施准备：

- 云端准备一个 HTTPS 可访问的只读对象存储目录，例如 S3/OSS/COS/MinIO 的 `updates/stable/`。
- 发布机保存对象存储写权限和离线签名私钥；目标机不保存这两类密钥。
- 目标机只配置更新源 HTTPS URL 和 root-owned 更新公钥，默认路径是 `/etc/claw-trade/update-signing-public.pem`。
- 发布时先上传 release 包和包签名，最后上传 `manifest.json` 和 `manifest.json.sig`。
- 当前分支已完成 Task 0 基线，以及 manifest 校验、签名验证 helper、updater 状态文件、远程 signed manifest 检查 API、signed archive 下载/hash/签名校验、设置页手动检查/安装更新入口、最小 rescue 服务、恢复出厂入口、root-owned apply-update 服务、root helper 复验签名后解包并切换 `current`、服务重启健康检查和失败回滚代码路径；自动定时更新和 VM 验收尚未实现。

## 范围

### 交付

- release manifest 格式和签名校验。
- release archive hash 与签名校验。
- updater 状态文件、锁文件和审计日志。
- 手动检查更新、自动定时检查更新。
- staging 解压、preflight、原子切换、服务重启、健康检查。
- 上一可用版本保留和失败回滚。
- UI 展示当前版本、最新版本、更新状态、失败原因和上一可用版本。
- 救援页可手动导入签名完整包；未授权设备可导入更新包，但不能解锁报告生成或数据刷新。

### 不交付

- 多更新通道。
- 自建更新后台。
- 远程命令执行。
- 设备主动拉取运维任务。
- 签名密钥轮换和私钥泄露应急。
- 最低安全版本和强制安全更新。
- 构建 provenance、透明发布记录和对象存储回滚防护。

## 架构边界

- `claw-trade` 仍拥有产品运行状态、授权判断、报告工作流和 UI。
- updater 只负责版本包验证、安装、切换、健康检查和回滚。
- updater 不能改写 worker prompt、报告结论、PM 决策或数据网关行为。
- 前端只展示更新状态和触发允许的本机操作，不能决定签名是否有效、版本是否可安装或回滚是否可执行。
- 设备上只保存更新公钥，不保存签名私钥。
- 所有本机状态变更 API 必须有后端鉴权、来源校验和 CSRF 防护；kiosk 允许访问的外部网页不能触发更新、安装、导入或回滚操作。

## 更新源合同

对象存储路径：

```text
updates/stable/
  manifest.json
  manifest.json.sig
  claw-trade-production-<version>-<stamp>.tar.gz
  claw-trade-production-<version>-<stamp>.tar.gz.sig
```

对象存储可以是 S3、OSS、COS、MinIO 或等价的静态文件服务。设备端不保存云账号密钥，只读 HTTPS 文件；安全性来自 manifest、archive hash 和签名校验。

发布顺序：

1. 构建 `claw-trade-production-<version>-<stamp>.tar.gz`。
2. 计算 archive sha256。
3. 用离线私钥签名 archive。
4. 生成 `manifest.json`，其中 `archive` 只能是同目录 basename。
5. 用离线私钥签名 manifest。
6. 先上传 archive 和 archive 签名。
7. 最后上传 `manifest.json` 和 `manifest.json.sig`。

禁止把签名私钥、云存储写密钥或后台管理口令放到目标机上。

`manifest.json` 最小字段：

```json
{
  "product": "claw-trade",
  "channel": "stable",
  "version": "1.2.3",
  "arch": "linux-x86_64",
  "archive": "claw-trade-production-1.2.3-20260626T120000Z.tar.gz",
  "sha256": "<archive sha256>",
  "created_at": "2026-06-26T00:00:00Z",
  "min_current_version": "0.1.0",
  "notes": "release note"
}
```

第一版规则：

- `product`、`channel`、`arch` 必须匹配本机；
- `version` 必须高于当前版本，默认拒绝降级；
- `archive` 必须是同目录下的 basename，不能包含 `/`、`\`、URL、空字节或规范化后变化的路径；
- `min_current_version` 必须小于或等于当前版本；不满足时拒绝安装；
- manifest 签名先通过，才允许读取 archive 字段；
- archive 下载后必须同时通过 sha256 和签名校验；
- manifest 和 archive 签名必须使用 root-owned 更新公钥验证，默认路径 `/etc/claw-trade/update-signing-public.pem`；发布私钥和对象存储写密钥不得进入目标机；
- 自动 timer 在未授权、过期或吊销状态下不得静默安装；第一版只允许本机手动导入签名完整包，且更新后仍按 Virbox 授权状态锁定报告生成和数据刷新；
- 安装前必须检查授权状态、磁盘空间和 schema/data 兼容性；不兼容时拒绝更新或执行已批准的迁移/回滚策略；
- 验证失败写审计日志，不进入 staging。

第一版不实现最低安全版本、透明发布记录和对象存储回滚防护。残余风险必须记录：如果对象存储被回滚到仍高于当前版本的旧签名 manifest，设备可能接受该版本。不能接受该风险时，必须先补最高已见版本或最低安全版本机制。

## 安全解压合同

签名有效只证明发布者认可该包，不代表解压可以信任 archive 内路径。

解压到 staging 前必须逐项审计 archive：

- 只允许普通文件和目录；
- 拒绝绝对路径、`..`、路径分隔异常、规范化后变化的路径；
- 拒绝 symlink、hardlink、device、fifo、socket；
- 拒绝 setuid/setgid、异常 owner/group 和会改变 release 外权限的 metadata；
- 每个条目规范化后的目标路径必须位于 staging 根目录内；
- 解压完成后再审计 staging 树，确认没有 release 外写入、没有源码禁区、没有签名私钥、没有 `.env.local`。

## 本机目录

```text
/opt/claw-trade/
  releases/
    <version>/
    <version>.staging/
  current -> releases/<version>
  shared/
    updates/
      manifest.json
      downloads/
      updater-state.json
      updater.lock
      apply.lock
      apply-request.json
      logs/
    config/
    data/
    license/
    reports/
    logs/
```

`shared/` 是运行期状态，更新不得覆盖。

## 状态机

```text
idle
-> checking_manifest
-> update_available | up_to_date | check_failed
-> downloading
-> verifying
-> staging
-> preflight
-> switching
-> restarting
-> health_checking
-> installed
```

失败分支：

```text
download_failed
verify_failed
preflight_failed
switch_failed
health_check_failed
rollback_started
rollback_succeeded
rollback_failed
```

失败必须保留：

- 当前版本；
- 目标版本；
- manifest hash；
- archive hash；
- 失败阶段；
- 用户可见失败原因；
- 脱敏详细日志路径。

当前分支已落地的 Task 1 局部范围：

- `UpdateManifest` 解析和字段校验。
- product、channel、arch、version、`min_current_version`、archive basename、sha256 格式校验。

- 对象存储 `manifest.json` 和 `manifest.json.sig` 拉取、签名校验和状态写入。

- Python 更新服务只写入 apply 请求并启动 apply service，不直接解压 release，不直接切换 `/opt/claw-trade/current`。
- root-owned `/usr/local/lib/claw-trade/claw-trade-apply-update` 由 `claw-trade-apply-update.service` 调用，使用 `/etc/claw-trade/update-signing-public.pem` 复验 manifest/archive 签名，安全解压到 root-owned release，运行 preflight，复验 manifest version/min version 约束，切换 `current`、重启 control/UI、检查 `127.0.0.1:5175/healthz`，失败时回滚并触发 rescue takeover。
- 生产 control 运行目录、MongoDB PID、factory seed normalized 输出必须写入 `/opt/claw-trade/shared/...`，不得写入 root-owned release 内 `.runtime`。

- 如果 apply service 启动失败，Python 更新服务不切换 `current`，并删除 `apply-request.json` 与 `apply.lock`，允许修复 sudoers/systemd 后重新安装。
- `rescue-current` 不随浅健康检查自动推进，避免坏版本污染救援入口；初装时指向已安装基线版本。

## 停止条件

- 签名校验只能通过前端或 shell 字符串拼接完成。
- 设备需要保存签名私钥。
- 更新包会覆盖 `shared/config`、`shared/data`、`shared/license`、`shared/reports` 或 `shared/logs`。
- 健康检查失败后无法保留或恢复上一可用版本。
- 本机状态变更 API 能被外部网页触发。
- archive 解压能写出 staging 根目录或生成 symlink/hardlink/special file。
- 为了通过验收加入未签名 fallback、降级 fallback、远程 shell 或 mock 成功。
