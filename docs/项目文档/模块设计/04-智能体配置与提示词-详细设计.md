# 智能体配置与提示词模块详细设计

## 1. 目录结构

报告链路 worker 典型结构：

```text
agents/<worker>/
  AGENTS.md
  IDENTITY.md
  USER.md
  STAGES.yaml
  SKILLS.md
  prompts/
    CN_A.md
    US.md
    HK.md
    CRYPTO.md
  skills/
    manifest.yaml
    ...
```

非报告 agent 结构可能不同，例如：

- `selection_*`
- `market_data_maintenance_worker`
- `price_alert_scan_worker`
- `scheduled_report_runner`
- `ui_chat`
- `ui_worker_chat`

不能用报告 worker 文件要求检查所有 agent。

## 2. 配置读取

相关代码：

```text
src/claw_trade/config/profiles.py
src/claw_trade/config/stage_policy.py
src/claw_trade/config/workspace.py
src/claw_trade/config/tool_names.py
src/claw_trade/runtime/request_builder.py
```

读取顺序：

1. `require_profile()` 校验 profile。
2. `validate_worker_workspace_for_control()` 校验 workspace。
3. `load_stage_policy()` 读取 `STAGES.yaml`。
4. `validate_stage_policy_matches_worker()` 校验 stage。
5. `load_tool_registry()` 和 `resolve_tools()` 解析工具。

## 3. Stage policy

`STAGES.yaml` 应表达：

- stage。
- profile。
- 当前 turn 允许的工具。
- prompt 文件。
- skill exposure。

Stage policy 不是业务 prompt，不应塞入投资逻辑。

## 4. Prompt 渲染边界

允许替换：

- ticker。
- company name。
- market。
- date range。
- currency。
- approved natural-language upstream report text。
- 简短真实性红线。

不允许替换：

- Python 写的新观点。
- provider attempt JSON。
- OpenViking refs。
- debug envelope。
- hard gate checklist。

## 5. CN_A 和 US 差异

CN_A 对齐 TradingAgents-CN，可直接包含完整前线报告和辩论历史。

US 对齐 original TradingAgents，不应把 CN_A 的材料边界强行套进去。特别是 research manager 的可见材料边界需要按 baseline 区分。

## 6. Debate worker 设计

Bull、bear、risk challenger、risk guardian、risk moderator 需要保持辩论感：

- 明确立场。
- 直接反驳。
- 最终 proposition。
- 风险和交易条件。

Truthfulness redline 只能约束不造假，不能让 debate worker 写成中性 memo。

## 7. Report polisher 设计

`report_polisher` 生成读者版最终报告。

它可以：

- 组织结构。
- 提升中文可读性。
- 汇总 approved worker material。

它不能：

- 改 PM 结论。
- 新增 unsupported target price。
- 发明图表或数据。
- 把缺数据写成成功。

## 8. Selection agents

Selection agents 用于候选评审，不属于正式报告 DAG。

要求：

- 能读取 candidate cache。
- 不把 CRYPTO 写成 A 股。
- manager/portfolio manager 等纯 reasoning worker 可不暴露工具。
- selection 结果需用户确认后才能转正式 report。

## 9. 已知限制

- Prompt alignment 不能只靠静态测试证明，需要 provider final prompt 和 LLM output 对比。
- 旧 prompt 审计资料已归档，后续迁移时需要从归档和 baseline 重新取证。
