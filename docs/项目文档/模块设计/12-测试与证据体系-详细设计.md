# 测试与证据体系模块详细设计

## 1. 单元测试

单元测试覆盖：

- 命令解析。
- DTO 投影。
- store 行为。
- guard 局部规则。
- 数据标准化。
- report repository。
- PDF 清理和验证。
- price alert 条件判断。
- selection cache 合同。

执行原则：

```text
先跑最小相关测试。
失败后查根因。
修复后跑同一测试。
再跑更宽的 scoped regression。
```

## 2. 合同测试

合同测试用于保护架构边界：

- 12 worker 顺序。
- stage policy 工具可见性。
- prompt profile fail closed。
- guard allowlist。
- UI forbidden surface。
- scheduled/alert API shape。
- provider payload capture fields。

合同测试失败意味着设计边界可能被破坏，不能用放宽测试绕过。

## 3. 集成测试

集成测试覆盖模块协作：

- `/report` 请求进入 report queue。
- workflow bridge 构造 RunRequest。
- artifacts 审批后进入 downstream material。
- selection refresh 写候选缓存。
- selection handoff 创建 report task。
- scheduled wake 创建报告任务。
- price alert scan 获取 quote 并通知。
- PDF 导出读取 saved report。

集成测试可用受控 fake provider，但必须明确标注，不得冒充 live provider。

## 4. Live runtime 测试

Live 测试必须：

1. 先通过 runtime preflight。
2. 使用 `scripts/start-control-runtime.sh -- <command>` 或复用已健康 runtime。
3. 捕获真实 provider final payload。
4. 捕获模型可见 tool schema。
5. 捕获 worker output。
6. 检查 OpenViking material/receipt。
7. 保存或引用 evidence。

OpenClaw runtime seam 改动还必须：

```text
edit src
  -> focused source/unit tests
  -> pnpm build
  -> restart control runtime
  -> focused live proof
  -> inspect fresh provider payload
```

## 5. UI 真实浏览器测试

UI 验收使用 MCP 控制真实 Chrome。

覆盖：

- 打开应用。
- 普通聊天。
- `/report` 任务。
- `/select` 任务。
- 队列状态。
- 历史报告。
- 报告问答。
- worker 聊天。
- 设置页面。
- 渠道状态。
- PDF 导出。

截图和浏览器状态用于证明用户路径，不证明 provider 数据真实性。

## 6. Provider payload 审查

provider payload 审查字段：

- run id。
- dispatch id。
- worker id。
- stage。
- market profile。
- final messages。
- visible tool schema。
- model/provider/request id。
- runtime marker。

审查重点：

- 没有控制面协议泄漏进模型提示词。
- 工具 schema 符合 stage policy。
- downstream worker 只看到批准材料。
- prompt 和 market profile 匹配。

## 7. Artifact 证据审查

审查：

- L1 report body。
- L2 metadata。
- material id。
- uri/hash/receipt。
- approved manifest。
- failure record。

失败 artifact 不得进入 downstream prompt 或 final report。

## 8. 数据证据审查

审查：

- DataNeed。
- ProviderCallSpec。
- provider attempts。
- raw rows。
- normalized rows。
- data gap。
- chart asset。
- indicator analysis。

如果报告声称图表存在，必须有图表资产或明确缺失原因。

## 9. 证据保存和归档

本轮文档重整把旧文档归档到 `docs/项目文档/归档/原有文档/`。

后续测试证据建议按运行任务放在受控 evidence 目录，并在测试报告中引用关键路径。临时调试文件不应长期混在项目文档根目录。

## 10. 审计输出

审计报告应包含：

- 文档覆盖清单。
- 文档与代码一致项。
- 不一致项。
- 未验证项。
- 需要 live runtime 的项。
- 需要人工确认的项。
