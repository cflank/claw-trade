# 测试与证据体系模块测试计划

## 1. 测试目标

验证测试体系本身能覆盖项目关键边界，避免把静态代码、mock 输出或旧证据当作当前真实行为。

## 2. 测试分类检查

| 分类 | 检查 |
| --- | --- |
| 单元测试 | 每个核心模块有局部规则测试 |
| 合同测试 | 架构红线有合同测试 |
| 集成测试 | 跨模块流程有测试 |
| live 测试 | provider payload 和 runtime 行为可验证 |
| UI 测试 | 真实浏览器路径可验收 |
| 文档审计 | 文档与代码一致性可复查 |

## 3. Runtime preflight 测试

验证：

- `runtime.env` 存在时先检查现有 runtime。
- OpenViking `1933/health` 或 `1933/healthz` 可达。
- OpenClaw gateway `18789/health` 可达。
- 必要环境变量 unset。
- 需要 clean runtime 时使用脚本 command mode。
- 不使用 invest sidecar。

## 4. Provider payload 测试

验证：

- 每个 worker dispatch 有 provider payload。
- payload 中有 worker id/stage/run id/dispatch id。
- tool schema 与 stage policy 一致。
- downstream prompt 不含未批准控制面协议。
- static render 不能被测试当作 provider payload。

## 5. Collect-first 测试报告检查

每个批量测试报告必须包含：

```text
Collect-first compliance:
- batch scope
- completed items
- failures collected
- early-stop exception used
- exception evidence
- batch fix grouping
```

缺失该段时，批量测试报告不完整。

## 6. UI 验收检查

验证：

- UI-facing workflow 有真实 Chrome 验收记录。
- 截图或浏览器状态能证明路径。
- headless、mock、静态输出未被当作最终 UI 验收。

## 7. 文档审计检查

验证：

- 文档中的每个模块能在代码中找到对应目录或文件。
- 文档中的流程图不与代码边界矛盾。
- 文档没有声称本轮已做 live 验收。
- 文档没有把旧归档方案写成当前事实。
- 文档没有使用绝对化合规结论。

## 8. 不通过条件

- 用 mock/fake 输出声称 live 通过。
- 缺 provider payload 却声称 prompt alignment 已验证。
- UI 功能未用真实 Chrome 验收却声称用户流程完成。
- 文档把“代码存在”写成“当前运行已验证”。
- 批量测试第一项失败后无 collect-first 说明。
