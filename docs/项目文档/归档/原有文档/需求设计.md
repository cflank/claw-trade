# claw-trade 需求设计

## 1. 文档定位

本文是 `docs/` 下的统一需求入口：它归并当前产品目标、边界、验收口径和停止条件。已删除的 legacy 文档不再作为产品路径或实施依据。

证据文件不合并：`docs/evidence/` 保留 TradingAgents-CN 基准抓取材料和后续对比证据。

## 2. 产品目标

claw-trade 的目标是生成可信、有报告感、面向中文读者的投资研究报告。

报告必须：

- 对齐 TradingAgents / TradingAgents-CN 的工作流和表达方式。
- 由真实 OpenClaw worker 生成，而不是 Python 代写。
- 使用真实数据源和真实工具证据。
- 保留 market、fundamental、news、social 四个 frontline worker 的覆盖。
- 后续继续支持 bull/bear/research manager/trader/risk/portfolio manager 的完整 12-worker 决策链。
- 最终报告由 portfolio manager 拥有投资结论；Python 只负责调度、校验、落盘和导出。
- 对 prompt、角色声线、辩论风格、交易建议表达和报告结构，原版对齐是第一优先级；不得为了“更审慎”“更合规”“更安全”或“更像备忘录”而偏离 baseline。
- 真实性要求只防止编造和越权，不改变 analyst 的角色强度。证据支持的强观点、BUY/HOLD/SELL、final proposition、风险判断、目标情景和直接反驳都属于报告内容，不是待消除的风险。

## 3. 用户入口

正式产品入口是 chat 中的 `/report` 命令。

普通聊天不能自动进入投资报告工作流。报告工作流启动后，claw-trade 按固定阶段唤醒 OpenClaw worker。

当前测试在 UI `/report` 尚未完成前，默认以 `report_command` 语义模拟报告入口；如果测试普通聊天流，必须显式标注不是报告工作流。

## 4. 核心用户场景

### 4.1 单股票 A 股研究报告

用户给出 A 股代码，例如 `600519.SH`，系统生成包含以下内容的中文研究报告：

- 技术面观察。
- 基本面分析。
- 新闻和宏观/行业背景。
- 社交和舆情热度。
- 多空辩论。
- 研究经理汇总。
- 交易计划。
- 风险辩论。
- 组合经理最终结论。
- 可用图表资产。

### 4.2 与 TradingAgents-CN 对齐验证

同一标的分别跑 TradingAgents-CN 和 claw-trade，比较：

- final provider prompt。
- LLM back / raw output。
- worker report。
- 最终 report。

对比目标不是逐字相同，而是保证：

- worker prompt 主体尽量贴近 CN。
- 运行层控制信息不污染 prompt。
- 报告有自然研究报告感。
- 信息覆盖和推理深度不低于 CN 的核心部分。
- debate worker 保留 TradingAgents / TradingAgents-CN 的强观点辩论室风格，而不是被改写成审慎合规 memo。
- guard 和 prompt 约束不能压低 baseline 允许的推荐、反驳、风险表达和角色声线。

### 4.3 frontline 四 worker 数据验证

对 market、fundamental、news、social 单独验证：

- 工具是否真实可见。
- provider 是否真实调用。
- 数据是否进入 worker 可读材料。
- worker 是否输出自然语言报告。
- 既有 worker 报告校验是否只拦截造假和越权，不拦截正常报告表达。

## 5. 范围

### 5.1 当前范围

- CN_A profile。
- frontline 四 worker。
- control plane 到 OpenClaw 单 worker runtime。
- OpenViking L1/L2 approved material。
- MongoDB 作为缓存和结构化资料存储。
- Tushare 主源和矩阵增强源。
- 最终报告导出和图表复制。
- Provider payload、visible tools、first response、tool calls、raw output 等运行证据捕获。

### 5.2 后续范围

- 完整 12-worker 全链路 fresh live gate。
- UI `/report` 入口。
- HK、CRYPTO profile 明确策略。
- 生产部署容量评审。
- 更完整的社交文本情绪源。

### 5.3 不做的事

- 不让 Python 写报告、评级、目标价、PM 决策。
- 不用 mock、stub、fake、dummy、placeholder、假成功。
- 不用隐藏 fallback 假装 provider 成功。
- 不把 MongoDB 当 approved artifact 权威。
- 不把 OpenViking L2 写入失败伪装成成功。
- 不把 provider 原子能力暴露给后续 worker。
- 不把调试用 JSON 塞进 worker 间主传递链。
- 不把 portfolio manager 最终裁决权、truthfulness guard 或安全边界扩展成 prompt 风格禁令。
- 不禁止 baseline 已允许且证据支持的 trading recommendation、final proposition、目标情景、风险判断或强辩论语气。

## 6. Worker 需求

### 6.1 frontline

frontline 必须包含：

- `market_analyst`
- `fundamental_analyst`
- `news_analyst`
- `social_analyst`

每个 worker 的主输入应是面向分析任务的自然语言 prompt，而不是工程清单或调试协议。

worker 可以调用本阶段允许的工具，然后提交自然语言 report。后续 worker 继承的是已批准完整 L1 report 正文；artifact ref / capability 只用于追踪、校验和必要时深读 L2，不继承未批准的工具原子结果。

### 6.2 后续阶段

后续阶段固定为：

- `bull_researcher`
- `bear_researcher`
- `research_manager`
- `trader`
- `risk_challenger`
- `risk_guardian`
- `risk_moderator`
- `portfolio_manager`

流程由 claw-trade 决定，LLM 不能决定下一个 worker。

frontline 四个 worker 完成后，流程直接进入投资辩论：先运行 `bull_researcher`，bull 材料批准后再运行 `bear_researcher`。这里不新增一个总 gate；worker 自己的既有报告校验在各自出报告时已经完成。

## 7. 数据需求

### 7.1 通用要求

所有数据源必须真实调用，失败要暴露原因，不能补假数据。

对 worker 来说，材料应尽量是自然语言可读内容。内部为了工具协议、缓存、审计或 provider 调试可以保留结构化文件，但不能把这些结构当作 worker 间主传递链。

### 7.2 Tushare 主源

CN_A 数据以 Tushare 为主源，覆盖 market、fundamental、news 等可覆盖字段。临时私有 Tushare endpoint 必须通过配置注入，不写死在代码。

配置项：

- `TUSHARE_TOKEN`
- `TUSHARE_HTTP_URL`
- `CN_A_TUSHARE_HTTP_URL`

如果 token 或私有 endpoint 配置不正确，必须报明确认证/连接问题，不得降级成假成功。

### 7.3 Provider 矩阵

矩阵源默认打开。provider 失败不等于整体失败；只要真实记录每次尝试、失败原因和最终质量状态即可。

增强源包括但不限于：

- Tushare。
- AkShare。
- Eastmoney。
- Bocha。
- Tavily。
- Jina。
- NewsNow。
- MiniMax 国内 endpoint。

缺 key 时 provider 应报告认证缺失，不应伪造空数据成功。

### 7.4 Market 数据

market 需要：

- K 线、价格、成交量。
- 均线和技术指标。
- 技术结构图或指标图。
- 图表本地资产。

图表不进入 worker 主传递链，但最终报告必须复制可用图片并引用报告内资产路径。

### 7.5 Fundamental 数据

fundamental 需要：

- 估值：PE、PB、PS、股息率等。
- 财务报表：利润表、资产负债表、现金流。
- 关键指标：ROE、毛利率、净利率、营收、净利润、经营现金流。
- EPS/TTM EPS 口径说明。
- provider provenance。

如果估值核心数据和财务/现金流至少一组齐全，可以视作 complete；否则按 partial 或 failed 处理。

### 7.6 News 数据

news 需要：

- 公司直连新闻。
- 行业和宏观背景新闻。
- 来源、时间、链接或可追踪出处。
- 去重、排序、相关性判断。

如果某只股票本身没有近期公司新闻，可以正常输出“暂无强相关公司新闻”，但必须说明是 provider 查到为空还是 provider 能力失败。

### 7.7 Social 数据

social 需要：

- 关键词热度。
- 热度排名。
- 讨论文本或文本源缺口说明。
- 雪球、股吧等来源在可用时接入。

如果只有关键词热度，没有真实文本情绪源，就写热度报告，不给情绪指数或价格预测。

换句话说：没有文本证据时，不写情绪指数，不写价格预测。

## 8. 报告需求

### 8.1 worker report

worker report 可以包含分析建议、目标价框架、评级倾向和交易条件，但必须是该 worker 的观点，最终投资结论仍归 PM。

禁止：

- 没有证据却写确定事实。
- 编造数据源。
- 编造图表。
- 编造新闻。
- 编造 PE/PB/ROE/目标价。

不禁止：

- 有依据地提出目标价区间。
- 有依据地提出买卖条件。
- 有依据地给出风险收益判断。

### 8.2 final report

最终报告必须：

- 面向读者。
- 有完整研究报告结构。
- 包含可用图表。
- 不暴露工具日志、JSON、URI、机器字段。
- 不把 provider 调试信息写进正文。

最终报告生成后，临时图片可以清理；如果同步清除图片，也必须清理 OpenViking 中对应引用，避免悬空引用。

## 9. 证据需求

每次验证必须能证明：

- 实际发给 LLM 的 final provider request。
- 当轮可见工具 schema。
- worker id、stage、run id、dispatch id。
- first response。
- tool calls。
- raw output。
- OpenViking write receipt。
- approved manifest。

renderer 输出、exporter 输出、手工重建 prompt 都不能代替 provider payload。

## 10. 验收标准

### 10.1 单 worker 验收

每个 frontline worker 验收需要：

- final prompt 已捕获。
- LLM back 已捕获。
- report 已捕获。
- visible tools 正确。
- 未暴露非本阶段工具。
- 无 fake/fallback。
- report 有报告感。
- 与 TradingAgents-CN 基准差异有明确解释。

### 10.2 full chain 验收

完整报告验收需要：

- 所有实现任务完成。
- OpenClaw build 已重跑。
- runtime 已重启。
- fresh live run 使用新 dist。
- 所有既有 worker 报告校验无 Critical/Important。
- final report 包含图片资产。
- PM 最终结论未被 Python 改写。

### 10.3 Git 同步验收

如果改了 `third_party/openclaw/src/**` 运行行为，必须：

- 在 `third_party/openclaw` 执行 `pnpm build`。
- 提交并推送 OpenClaw 子仓库。
- 在 claw-trade 提交更新后的子模块指针。
- 再推送 claw-trade 主仓库。

## 11. 停止条件

出现以下情况必须停止并问人类：

- 需要改变 OpenClaw / claw-trade / OpenViking 权限边界。
- 需要改变 PM 最终裁决权。
- 需要让 Python 写投资结论、评级或目标价。
- 需要添加 fallback 或绕过失败。
- 需要关闭矩阵源或选择新的 provider 策略。
- provider、MongoDB、OpenViking、OpenClaw runtime 环境缺失，继续会导致假成功。
- 同一类 gate 聚焦修复后仍失败两次。
- HK 或 CRYPTO prompt 策略不明确。
