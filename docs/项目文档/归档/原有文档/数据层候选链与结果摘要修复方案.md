# 数据层候选链与结果摘要修复方案

状态：核心实现已落地，已通过聚焦单元/合同/集成测试；尚未做 frontline 或 full-chain live 验收。

## 1. 要解决的问题

这次不是修某一个 Coinglass 或 Tushare 接口，而是修数据层的通用调用方式。

当前根因：

1. 数据源接口目录已经放开了一部分能力，但 planner 把同一个业务数据项下的所有可用接口都展开成待调用列表。
2. scheduler 仍然按“全部候选可执行”处理，导致一个需求排出十几个甚至几十个接口。
3. executor 虽然有成功即停逻辑，但在此之前计划和调度已经膨胀，限流预算、任务时间、审计结果都会被污染。
4. 成功结果没有被摘要好。资金费率、净流量、AHR999、交易所余额这类数据成功返回后，只被摘要成“多少行、有哪些字段”，没有变成报告可直接使用的最新读数。
5. 粒度检查过硬。比如 CVD 返回小时级数据时，被当成不匹配，直接进入缺口，而不是作为带粒度说明的可用数据。

## 2. 总原则

数据源能力要完整释放，但不能把所有接口一次性撒出去。

正确流程：

```text
worker 只请求业务数据项
  -> 数据层找到项目必需数据项
  -> 数据层找到已经绑定的真实 provider API
  -> planner 生成候选链或组合组
  -> scheduler 只放行当前应该尝试的接口
  -> executor 逐个尝试，成功即停，失败才兜底
  -> summarizer 把成功数据变成报告可读数
```

worker 不知道 provider、path、api_name、api_id、url、token、header，也不传字段清单。

## 3. 候选链和组合组

### 3.1 候选链

候选链用于“一个来源成功就够”的数据。

适用数据：

- K线
- 实时价
- 盘口
- 资金费率
- OI
- 多空比
- CVD
- 清算数据
- 清算地图
- 交易所净流量
- AHR999
- 链上活跃度
- ETF 流入流出
- 估值指标
- A股资金流
- A股板块资金
- 港股、美股行情类指标

行为：

```text
优先源接口成功并通过业务字段校验 -> 停止，不再调用低优先级源
优先源失败、空结果、权限不足、超时或字段不够 -> 记录证据 -> 尝试下一源
```

例子：

```text
crypto.open_interest
  chain 1: Coinglass OI
  chain 2: Binance OI
  chain 3: 其它已绑定免费源 OI
```

不能再出现一个 OI 请求一次排出几十个真实接口。

### 3.2 组合组

组合组用于“多个接口互补才完整”的数据。

适用数据：

- 财报三表：利润表、资产负债表、现金流量表。
- 事件类：公告、新闻、宏观日历、监管日历、项目公告。
- 社交/舆情：多个来源可共同构成证据池。

行为：

```text
同一优先来源内的互补接口可以都执行
同一优先来源已经满足需求后，低优先级来源不再执行
如果高优先级来源只返回部分组件，则只补缺失组件，不重复打已经满足的组件
```

### 3.3 机器合同

不能只靠排序或 provider 名字隐含表达候选关系。必须把候选链和组合组写进数据层模型。

`NeedPlan` 必须表达：

- `execution_groups`：当前需求的执行组列表。
- `planned_calls`：完整候选清单，只作审计和后续兜底库存。
- `initial_scheduled_calls`：本轮允许真实尝试的调用，只能包含每条候选链的头部候选和当前来源组内必要互补组件。
- `deferred_calls`：还没允许出网的候选，不能产生限流预约，不能产生 provider attempt。

`ProviderCallSpec` 必须增加或等价表达：

- `business_api_id`：项目业务数据项编号，例如 `crypto.open_interest`、`cn_a.order_book`。
- `execution_group_id`：候选链或组合组 ID。
- `execution_group_kind`：`fallback_chain` 或 `composition_group`。
- `source_group_id`：同一真实来源组，例如 `coinglass`、`tushare`、`binance`。
- `fallback_order`：同一候选链里的尝试顺序。
- `component_id`：组合组里的互补组件，例如 `income_statement`、`balance_sheet`、`cashflow_statement`。
- `satisfaction_contract_id`：业务成功标准 ID。
- `standard_output_contract_id`：标准输出合同 ID。

这些字段是内部审计和调度字段，不能出现在 worker 工具入参里。

### 3.4 调度闭环

采用 executor 驱动的候选链推进，不让 scheduler 猜执行结果。

流程：

```text
planner 生成完整候选链/组合组
  -> scheduler 只放行 initial_scheduled_calls
  -> executor 执行当前候选
  -> executor 用标准输出合同判断成功/失败
  -> 成功：关闭同一 fallback_chain，低优先级候选不再进入 scheduler
  -> 失败：把 attempt 结果交回 scheduler，scheduler 放行同链下一候选
  -> 组合组：只补当前来源组缺失 component
```

`scheduled_calls` 只能表示“已经允许尝试的调用”，不能继续表示“所有可能候选”。

`planned_calls` 可以保留完整候选用于审计，但未进入 `scheduled_calls` 的候选：

- 不能预约限流。
- 不能写 provider attempt。
- 不能计入真实调用次数。
- 不能污染 final report 的数据源调用统计。

executor 回传 scheduler 的 `attempt_state` 必须至少包含：

- `plan_id`
- `execution_group_id`
- `call_id`
- `attempt_outcome`
- `contract_satisfied`
- `satisfied_component_ids`
- `missing_component_ids`
- `gap_reason`

scheduler 只能根据这些字段放行下一候选，不能重新按 provider、字段名、worker、`data_type` 或相似语义猜测。

## 4. 成功标准

HTTP 200 不等于业务成功。

每个业务数据项必须有最小可用输出。

成功标准必须落到 normalizer 后的标准输出合同，不能靠字段名相似度猜。

标准输出合同来源：

```text
项目必需数据项
  -> standard_output_contract_id
  -> required_fields
  -> optional_fields
  -> freshness_rule
  -> granularity_rule
  -> unit/口径
```

planner 只绑定 `standard_output_contract_id`。executor/summarizer 只按这个合同验收和摘要。

`standard_output_contract` 必须用 `all_of` 和 `any_of_groups` 表达必需字段组。

executor/summarizer 不得用字段名归一化、`data_type` 语义相等、或任一 required field 命中来判定业务满足。

最低成功标准：

| 数据项 | 标准输出合同 | 最小可用读数 |
| --- | --- |
| K线 | `ohlcv_bar.v1` | `timestamp`、`open`、`high`、`low`、`close`、`volume`、`source` |
| 实时价 | `realtime_quote.v1` | `timestamp`、`last_price`、`source` |
| 盘口 | `order_book.v1` | `timestamp`、`bid_price_1` 或 `bids`、`ask_price_1` 或 `asks`、`source` |
| 资金费率 | `funding_rate.v1` | `timestamp`、`funding_rate`、`contract` 或 `exchange`、`source` |
| OI | `open_interest.v1` | `timestamp`、`open_interest`、`contract` 或 `exchange`、`source` |
| 多空比 | `long_short_ratio.v1` | `timestamp`、`long_short_ratio`、`ratio_scope`、`source` |
| CVD | `cvd.v1` | `timestamp`、`cvd` 或 `buy_volume`+`sell_volume`、`granularity`、`source` |
| 清算 | `liquidation.v1` | `timestamp`、`liquidation_value` 或 `liquidation_quantity`、`side`、`source` |
| 清算地图 | `liquidation_heatmap.v1` | `price` 或 `price_range`、`liquidation_value`、`window` 或 `timestamp`、`source` |
| 净流量 | `exchange_netflow.v1` | `timestamp`、`netflow` 或 `inflow`+`outflow`、`asset`、`source` |
| 交易所余额 | `exchange_balance.v1` | `timestamp`、`balance`、`asset`、`source` |
| AHR999 | `ahr999.v1` | `timestamp`、`ahr999`、`source` |
| 链上活跃度 | `onchain_metric.v1` | `timestamp`、`metric_name`、`metric_value`、`source` |
| 财报 | `financial_statement.v1` | `period`、核心科目、`statement_type`、`source` |
| 新闻/公告/事件 | `structured_event.v1` | `title`、`event_date` 或 `published_at`、`event_type`、`source`、`url` 或 `raw_ref` |

字段不够时，结果不是“provider 没能力”，而是：

```text
接口返回成功，但未达到当前业务数据项的最小输出合同
```

## 5. 结果摘要修复

### 5.1 当前错误

现在成功数据经常只变成这种摘要：

```text
94 行，字段覆盖 标的代码、价格、volume_usd、资金费率。
```

这对 worker 没用。worker 需要能直接写进报告的读数。

### 5.2 修改目标

所有成功结果必须输出：

- 最新有效读数。
- 对应时间。
- 单位或口径。
- 来源。
- 如果是序列数据，说明样本范围和最新一条。
- 如果是多来源组合，说明每个关键读数来自哪个来源。

### 5.3 示例

资金费率应该摘要成：

```text
资金费率：0.003678%，时间 2026-06-15 12:00 UTC，交易所 Binance，来源 Coinglass。样本覆盖最近 94 条。
```

交易所净流量应该摘要成：

```text
交易所净流量：-1234 BTC，时间 2026-06-15，来源 Coinglass。负值表示净流出。
```

AHR999 应该摘要成：

```text
AHR999：0.82，时间 2026-06-15，来源 Coinglass。
```

交易所余额应该摘要成：

```text
交易所余额：2,845,000 BTC，时间 2026-06-15，来源 Coinglass。口径：交易所总余额。
```

不能只说“有 5613 行”。

### 5.4 实现位置

重点修改：

新增或调整：

- 从结果行里找最新有效行。
- 按业务数据项选择关键字段。
- 保留时间字段，不再从摘要字段里排除关键时间。
- 输出 `latest_value_summary`。
- 模型可见摘要优先展示 `latest_value_summary`，再展示行数和字段覆盖。

`latest_value_summary` 至少包含：

- `value`
- `time`
- `unit_or_scope`
- `source`
- `granularity`
- `sample_range`

需要覆盖的数据项：

- `crypto.funding_rate`

## 6. 粒度处理

不能默认把“小时级”当成失败。

规则：

1. worker 明确要求实时盘口、实时成交、实时价格时，粒度必须满足实时。
2. worker 只是请求报告分析用的 CVD、OI、资金费率、净流量时，小时级或日级可以作为可用数据。
3. 摘要必须写明粒度。
4. 如果粒度低于理想值，只能记录质量限制，不能直接变成缺口。

示例：

```text
CVD：小时级数据可用，最新值 xxx，时间 xxx，来源 Coinglass。限制：不是 tick 级。
```

## 7. 限流处理

限流只统计真实出网请求，不统计计划候选。

要求：

1. 同一真实来源共用一个限流桶。
2. 任意连续 60 秒真实 HTTP 不超过配置值。
3. 计划里出现候选不代表已经调用。
4. 高优先级源成功后，低优先级候选不能产生 attempt。
5. 如果等待会超过当前任务 deadline，返回 `rate_limited_by_tool_budget`，并进入缺口证据。
6. SDK 内部 HTTP 不可见的 provider 必须进入风险清单；不能声称已经完成子请求级滑动窗口限流。

### 8.1 planner

### 8.2 scheduler

文件：

- `src/claw_trade/data_gateway/coordination/scheduler.py`

修改：

## 9. 测试要求

### 9.1 单元测试

必须新增或修改：

- planner 测试：`crypto.open_interest` 不再生成几十个同级 scheduled calls。
- planner 测试：`cn_a.realtime_quote` 不再同时调用所有可替代来源。
- composition 测试：财报三表仍允许互补接口。
- summarizer 测试：资金费率成功结果必须输出最新资金费率、时间、来源。
- summarizer 测试：净流量成功结果必须输出最新净流量、时间、来源。
- granularity 测试：报告用小时级 CVD 不直接判缺口。
- rate limit 测试：限流统计真实 HTTP attempt，不统计未执行候选。
- contract 测试：同一需求在 report/select/ui_probe/maintenance 下候选链一致，只有审计标签不同。
- contract 测试：worker 工具入参不含 provider、path、api_name、api_id、fields、params。
- contract 测试：事件类 raw 成功但缺少结构化字段时，返回 parser_missing，不伪装完整事件。

### 9.2 集成测试

必须覆盖：

- BTC frontline：OI、资金费率、多空比、CVD、清算、净流量、AHR999、交易所余额。
- A股 frontline：K线、实时价、盘口、资金流、板块资金、公告或新闻。
- 美股 frontline：K线、实时价、财报、公司新闻、事件日历。
- 港股 frontline：K线、实时价、财报、公司新闻。
- 没有付费源时，能进入免费源兜底。
- 付费源成功时，低优先级源不再出网。

### 9.3 验收标准

通过标准：

1. 同一替代型业务数据项不会一次排出十几个或几十个真实接口。
2. 成功结果在 worker 可见摘要里有最新读数。
3. final report 不再把成功的资金费率、净流量、AHR999 写成缺失。
4. 任意连续 60 秒真实 HTTP 不超过配置值。
5. 低优先级候选没有被调用时，不计入 provider attempt。
6. 缺口原因能追到真实根因：凭证缺失、权限不足、远端空结果、接口错误、字段不足、解析缺失、限流预算不足。
7. `planned_calls_count` 可以大于 1，但 `scheduled_calls_count` 和真实 attempt 必须只反映已经放行的候选。
8. worker 可见摘要必须包含最新值、时间、来源；资金费率、净流量、AHR999、交易所余额不能只显示行数。

## 10. 禁止事项

- 禁止重新引入 worker/provider 白名单。
- 禁止让 worker 知道 provider、path、api_name、api_id。
- 禁止用“接口目录没登记”说 provider 没能力；只能说项目绑定没完成。
- 禁止因为一次测试失败就删除接口能力。
- 禁止只修 BTC，不同步检查 A股、港股、美股。
- 禁止用 full-chain 反复试错代替单元和集成修复。
- 禁止成功数据只报行数，不报可用读数。

## 11. 实施顺序

1. 修 planner：候选链和组合组。
2. 修 scheduler/executor：逐个尝试，成功即停，失败兜底。
3. 修业务成功标准：最小输出合同。
4. 修 summarizer：成功结果变成报告可用读数。
5. 修粒度策略：报告分析可接受非实时粒度并标注限制。
6. 补测试：先单元，再 frontline，再 full-chain。

full-chain 只能在前 5 步和对应测试完成后跑。
