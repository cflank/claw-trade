# 微信单账号与报告转发完整修复方案

状态：方案，尚未实施本轮新增修改。日期：2026-09-24。

## 目标与依据

完成代码修复、已有账号数据修复和真实微信验收。成功标准是目标机只运行用户选择的一个微信账号，确认卡可收到、历史报告可手动转发，故障时页面说明原因。

依据为 9 月 23 日目标机核查，实施前重新确认现状：

- 普通扫码追加账号，只清理相同微信 userId 的旧记录；已存两个账号属于不同用户。
- 1.0.3 修改了后续扫码入口和确认卡失败反馈，但升级保留了共享账号数据；没有执行换号事务。
- 报告列表按微信是否连接、能否发文件决定可转发；前端为 false 时直接隐藏按钮。
- 网页手动转发携带报告历史 originContextId，后台据此选择旧账号和收件人，换号后可能继续命中旧账号。
- 现有替换流程支持多个旧账号；取消后恢复原账号集合，并不保证恢复到可发送的单账号状态。设置页当前却统一提示旧连接已恢复。

证据：`docs/evidence/wechat-confirmation-root-cause-20260923.md`、`docs/evidence/production-1.0.3-deployment-20260923.md`。

## 1. 处理目标机已有双账号

复用现有安全换号流程，作为本次交付的必做操作，不再只部署程序就结束。

1. 核对实时账号索引、已存凭据、配置、运行实例、换号状态和最近入站记录。9/23 已知旧号为 `3c297f8f3d56…`，近期使用账号为 `6e3b9f603c3a…`；不能只按文件日期决定删哪个。
2. 确认无运行报告/文件投递；备份微信状态、相关配置及投递绑定，备份放在正常账号扫描范围之外并限制读取权限。
3. 在设置页通过现有重新连接流程，让用户用准备保留的微信扫码一次。由现有 begin/login/commit 处理旧实例暂停、新凭据验证、唯一账号索引提交和旧凭据/聊天令牌清理。
4. 扫码后从所选微信发一条消息，建立新的聊天投递上下文。不能假定旧聊天令牌在换号后依然有效。
5. 验证 registered/stored/configured/enabled/running 五组账号均只有同一个账号，默认账号相同、活动登录会话为零，旧账号不在运行列表。
6. 再做重启验证，确认旧账号不会重新加载；备份中的凭据不算活动账号。

选择理由：现有插件提交实现已包含停止、提交、清理、恢复能力，复用它比新增“启动时自动删号”或另一套迁移接口更小、更可验证。代价是用户需要扫码一次并发送一条消息。不会凭时间戳自动决定账号，也不伪造登录回执跳过现有事务。

## 2. 统一后续扫码入口

保留 1.0.3 已有修复，重点补全验证，不重写已完成的代码：

- 无账号才走首次登录；已有一个或多个账号时，启用、重新连接、刷新二维码统一进入已有替换流程。
- 页面缓存落后时，以后台读取的账号状态为准；账号读取失败显示错误，不继续普通扫码。
- 首次扫码已经写入新账号、页面仍在轮询本次登录结果时，应正常完成首次登录，不能误判成需要再换号。
- 沿用现有锁、事务恢复和单账号发送检查，不允许通过随意挑一个账号或放宽发送检查来消除报错。
- 取消/超时恢复后，设置页先读取真实状态：原来是双账号，就说明“已恢复原状态，但多账号冲突仍需处理”；只有连接实际可用时才显示恢复成功。覆盖轮询完成、取消、手动恢复三个反馈入口。
- 不单凭 replacementRequired 判断连接故障：1.0.3 的正常已连接账号也可返回 true，表示下次扫码应走替换。恢复提示依据实时连接状态、发送能力和错误原因。

## 3. 报告转发按钮和收件人

- 正式报告历史的“转发到微信”按钮始终显示。
- 微信不可用时禁用发送，并显示具体原因及前往设置的入口：多账号、未连接、正在换号、缺少可投递聊天分别说明。不能只给一个无说明的灰按钮。
- 复用现有通道状态和能力信息；查询失败显示状态未取得，不当作可发送。状态恢复后刷新列表和按钮能力。
- 网页手动转发明确发送至当前绑定微信的有效接收会话，后台解析当前目标，不沿用报告历史 originContextId 里的旧账号。
- 当前账号和当前聊天必须一起解析，不能只替换旧 account_id 却保留旧 sender_id；旧收件人可能属于另一个微信用户。更新 `tests/unit/ui/test_report_pdf_download_route.py` 中原先锁定历史目标的断言，增加不同账号、不同收件人的回归样本。
- 自动通知、历史待发消息仍保留原接收目标，不能因换号静默改发给新用户。
- 没有有效接收会话时，提示先从要接收报告的微信发一条消息。点击发送后保留“发送中/成功/失败原因”，真实发送端仍执行现有账号检查。

这次针对已存在的正式报告转发入口；选股报告增加新的独立转发入口不混入本次修复。

## 4. 确认卡投递

保留 1.0.3 已实现行为并完成实测：发送失败写日志和工作台提示；下一条非确认/取消消息返回原完整确认卡；不会重复生成卡片或重复启动报告。区分明确失败和送达未知，后者不自动补发。没有生成卡片时不能提示已有卡片。

## 6. 验证与验收

先聚焦测试，再生产构建和真实验收：

- 账号：无账号首登、已有单账号换号、两个不同用户账号换号；成功后只剩一个运行账号。
- 入口：启用、重新连接、刷新二维码、旧页面状态、首次登录结果轮询。
- 中断：取消、二维码过期、登录失败、提交响应丢失、换号期间重启。恢复成功与仍有冲突必须分别显示；重复请求不重复提交。
- 转发：当前三份历史报告按钮可见；未连接/双账号时显示原因；恢复连接后可点；含旧账号来源的历史报告在手动操作时发送到当前绑定会话。
- 确认卡：成功、明确失败、送达未知、异常；后续消息取回原卡，确认只触发一次报告。
- 真实验收：使用已有 MCP 控制的 Chrome 操作生产页面；从所选微信完成扫码及消息交互，实际收到确认卡和一份历史报告 PDF。服务 200、mock 测试或组件渲染不能替代手机收到文件的证据。
- 重启后重复检查唯一账号和页面发送能力，确认旧账号没有被重新拉起。

若真实 Chrome 会话或手机配合暂不可用，报告“已部署/数据处理到哪一步、真实验收未完成”，不声称修复全部完成。

## 7. 发布与回滚

下一版按 `1.0.4` 组织：隔离本次源码差异，执行聚焦测试、前端构建、生产包 preflight/audit，提供未加密完整生产包与 SHA256。排除工作区无关未提交修改。

执行顺序：测试和打包 → 保留旧 release 与数据备份 → 空闲时切换版本 → 完成真实换号清理 → 收发与重启验收。账号清理完成是本次交付条件，不能继续留作一句“请重新连接”。

代码故障回滚 release；换号操作失败优先走已有事务恢复。二者分开：回滚代码不应自动覆盖已经成功切换的新账号；恢复旧账号备份也不等于已恢复单账号可发送，必须重新核查真实状态。账号归属不能确认或状态不符合既有替换条件时停止清理并指出具体缺失证据。
