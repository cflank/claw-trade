# claw-trade 交付与升级操作指南

这篇文档只讲一件事：怎么把 claw-trade 从发布机做成可交付的软件包，并在工控机上安装、授权、升级、回滚。

## 0. 先分清三个包

```text
普通生产包：Linux 上构建出来的 tar.gz，能安装运行，但还不是 Virbox 保护包。
Virbox 保护交付包：在普通生产包基础上，替换受保护运行时，并加密 .pyc、md、js 后重新打出的 tar.gz。
远程升级包：可以被目标机在线升级使用的 tar.gz，加了签名、manifest，并上传到 Cloudflare R2 的 stable/。
```

如果要给厂家测试或量产，默认交付 Virbox 保护交付包，不交付普通生产包。

## 0.1 最常用流程：代码改了以后重新出交付包

只改了业务代码、前端、prompt 或配置，没有更换许可 ID、DS 密码、Python/Node 运行时，目标就是重新做出一个给客户的 Virbox 保护包。

```bash
# 进入项目目录
cd /home/frank/src/claw-trade

# 看当前代码是不是你要交付的版本
git status

# 确认有初始数据包
ls -lh data/current-seed-*.tar

# 如果本次数据也更新了，先重新生成 seed；只改代码可以跳过这一步。
SEED_COLUMNAR_ROOT="$(find .runtime/factory-seeds -mindepth 2 -maxdepth 2 -type d -name normalized ! -path '*-test/normalized' | sort | tail -n 1)"
scripts/start-control-runtime.sh -- uv run python scripts/production/export_current_seed.py \
  --mongo-database claw_trade_a_share_factory_seed \
  --columnar-root "$SEED_COLUMNAR_ROOT" \
  --output data/current-seed-$(date -u +%Y%m%d).tar \
  --replace-output

# 先做普通生产包。这个只是中间产物，不直接给客户。
scripts/production/build_production_package.sh

# 再把普通包加工成 Virbox 保护交付包。这个才是给客户的包。
scripts/production/build_virbox_protected_delivery_package.sh
```

最后得到的是 D 盘上的这两个文件：

```text
/mnt/d/claw-trade-virbox/delivery-output/virbox-protected-时间/claw-trade-production-版本-时间.tar.gz
/mnt/d/claw-trade-virbox/delivery-output/virbox-protected-时间/claw-trade-production-版本-时间.tar.gz.sha256
```

交付给客户的就是这两个文件。`dist/production/` 下的普通包只是中间产物，不是最终交付包。

交付前校验：

```bash
cd /mnt/d/claw-trade-virbox/delivery-output/virbox-protected-时间
sha256sum -c claw-trade-production-版本-时间.tar.gz.sha256
```

不需要重新做 Virbox Protector 保护的情况：

```text
只改代码、prompt、前端、配置。
只改同一个许可 ID 的授权日期。
```

需要回到 3.1 重新做 4 个保护文件的情况：

```text
许可 ID 变了。
DS 密码或 API 密码变了。
Python/Node runtime 换了。
保护策略变了。
```

原因很简单：

```text
普通生产包里的 Python 代码虽然是 .pyc，不是 .py 明文，但这不等于正式加密。
agents 里的 prompt md 如果不加密，厂家拿到包后能直接看。
OpenClaw 入口和插件如果不加密，也会暴露关键逻辑。
```

## 1. 发布机准备

进入仓库：

```bash
cd /home/frank/src/claw-trade
```

看代码状态：

```bash
git status
git branch --show-current
```

确认：

```text
1. 当前分支和代码就是要交付的版本。
2. 要发布的修改已经提交或明确允许带上。
3. 前端能正常构建。
4. 数据种子已经准备好。
```

生产包里会放一个“初始数据文件”。

这个文件的作用是：新机器第一次安装后，系统可以直接恢复一批历史数据，不用从零开始下载。

打包脚本只认当前初始数据文件：

```text
data/current-seed-*.tar
```

当前仓库里有：

```text
data/current-seed-20260626.tar
```

这个包是当前默认交付数据包。除非本次交付专门生成了更新的 `data/current-seed-*.tar`，否则就用它。

它包含 A 股和加密币：

```text
CN_A：daily_bar、valuation_metric、financial_statement、financial_metric、capital_flow、news/social 等。
CRYPTO：daily_bar、valuation_metric、crypto_derivative_metric、crypto_onchain_metric、news/social 等。
```

旧的 `data/a-share-cn-required-300td-20260608.tar` 已经废弃，不再作为备用包，也不再作为打包 fallback。

所以，发布前要先检查有没有最新初始数据文件：

```bash
ls -lh data/current-seed-*.tar
```

如果这里没有文件，不要继续打包。先生成本次要交付的 `current-seed`，或者确认使用现有的 `current-seed-20260626.tar`。

### 1.1 制作新的数据种子

这个动作不是重新下载数据。

它做的是：把当前机器上已经存在的数据打成一个新 seed。

当前历史数据分两部分：

```text
1. Parquet 文件：真正的历史行情、估值、财务、新闻、加密币指标等数据。
2. Mongo 元数据：告诉系统这些 Parquet 文件是什么市场、什么数据集、什么时间范围、文件在哪里。
```

所以制作新 seed 时，必须同时导出这两部分。

`.runtime/dev-services/runtime.env` 不是仓库自带文件。它只在本地固定 runtime 运行期间生成；如果由启动脚本拉起服务，脚本退出时还会清掉它。

默认做法是直接用固定 runtime 包住导出命令：

```bash
SEED_COLUMNAR_ROOT="$(find .runtime/factory-seeds -mindepth 2 -maxdepth 2 -type d -name normalized ! -path '*-test/normalized' | sort | tail -n 1)"
test -n "$SEED_COLUMNAR_ROOT"
echo "using seed columnar root: $SEED_COLUMNAR_ROOT"

scripts/start-control-runtime.sh -- uv run python scripts/production/export_current_seed.py \
  --mongo-database claw_trade_a_share_factory_seed \
  --columnar-root "$SEED_COLUMNAR_ROOT" \
  --output data/current-seed-$(date -u +%Y%m%d).tar
```

如果同名文件已经存在，并且确认要覆盖：

```bash
SEED_COLUMNAR_ROOT="$(find .runtime/factory-seeds -mindepth 2 -maxdepth 2 -type d -name normalized ! -path '*-test/normalized' | sort | tail -n 1)"
test -n "$SEED_COLUMNAR_ROOT"
echo "using seed columnar root: $SEED_COLUMNAR_ROOT"

scripts/start-control-runtime.sh -- uv run python scripts/production/export_current_seed.py \
  --mongo-database claw_trade_a_share_factory_seed \
  --columnar-root "$SEED_COLUMNAR_ROOT" \
  --output data/current-seed-$(date -u +%Y%m%d).tar \
  --replace-output
```

不要省略 `--mongo-database` 和 `--columnar-root`。默认运行时数据根是 `.runtime/dev-services/data-gateway/normalized`，那是增量运行数据，不是干净 factory seed；直接导出它可能因为 A 股日线缺 `company_name` 被完整性检查拒绝。

只有在另一个终端已经启动了本地 runtime，并且 `.runtime/dev-services/runtime.env` 正在存在时，才需要手动加：

```bash
SEED_COLUMNAR_ROOT="$(find .runtime/factory-seeds -mindepth 2 -maxdepth 2 -type d -name normalized ! -path '*-test/normalized' | sort | tail -n 1)"
test -n "$SEED_COLUMNAR_ROOT"
echo "using seed columnar root: $SEED_COLUMNAR_ROOT"

uv run python scripts/production/export_current_seed.py \
  --env-file .runtime/dev-services/runtime.env \
  --mongo-database claw_trade_a_share_factory_seed \
  --columnar-root "$SEED_COLUMNAR_ROOT" \
  --output data/current-seed-$(date -u +%Y%m%d).tar
```

脚本成功后会生成两个文件：

```text
data/current-seed-YYYYMMDD.tar
data/current-seed-YYYYMMDD.tar.sha256
```

这个 `tar` 里面必须有：

```text
seed_manifest.json
mongo/raw_payloads.jsonl
mongo/provider_attempts.jsonl
mongo/dataset_manifests.jsonl
data/normalized/**/*.parquet
```

说人话：

```text
seed_manifest.json：这个 seed 的目录。
mongo/*.jsonl：数据库元数据。
data/normalized/**/*.parquet：真正的数据文件。
```

检查：

```bash
SEED="current-seed-$(date -u +%Y%m%d).tar"
tar -tf "data/${SEED}" | head
(cd data && sha256sum -c "${SEED}.sha256")
```

如果脚本报错 `missing Parquet`，不要继续打包。

这表示 Mongo 里记录了某个数据文件，但当前 Parquet 目录里找不到它。先修数据目录或重新跑数据导入，再重新制作 seed。

## 2. 制作普通生产包

执行：

```bash
scripts/production/build_production_package.sh
```

脚本会做这些事：

```text
1. 构建前端页面。
2. 复制 agents、openclaw_plugins、OpenClaw 运行文件。
3. 复制 Python 运行环境和依赖。
4. 把 src/claw_trade 编译成 .pyc，放进 app/python/claw_trade。
5. 复制数据种子。
6. 复制本地 MongoDB 运行时，如果 .runtime/mongodb/current 存在。
7. 执行生产包检查。
8. 生成 tar.gz 和 sha256。
```

成功后会得到类似：

```text
dist/production/claw-trade-production-0.1.4-20260629T114637Z.tar.gz
dist/production/claw-trade-production-0.1.4-20260629T114637Z.tar.gz.sha256
```

这里的 `dist/production` 是 WSL 里的仓库目录，不是 D 盘目录：

```text
WSL 路径：/home/frank/src/claw-trade/dist/production/
Windows 里看：\\wsl.localhost\Ubuntu\home\frank\src\claw-trade\dist\production\
```

包名里的版本来自：

```text
pyproject.toml
```

包名里的时间是构建时间。

检查普通包：

```bash
PKG="claw-trade-production-版本-时间.tar.gz"
python3.12 scripts/production/validate_production_archive.py "dist/production/${PKG}"
python3.12 scripts/production/audit_production_package.py "dist/production/${PKG}"
(cd dist/production && sha256sum -c "${PKG}.sha256")
```

这一步通过，只说明普通包结构合格。它还不是给厂家的保护包。

## 3. 制作 Virbox 保护交付包

实际流程是：

```text
普通生产包
-> 解包到 D 盘中转目录
-> 替换受保护 Python 和 Node
-> 用 DSProtector 加密 .pyc、OpenClaw 入口、插件 js、agents md
-> 修启动入口
-> 检查没有明文和 .ssp
-> 重新打 tar.gz
-> 上传目标 Ubuntu 真机安装验证
```

做完以后，厂家拿到的是：

```text
1. Python 解释器被 Virbox 保护。
2. Node 运行时被 Virbox 保护。
3. claw-trade Python 应用 .pyc 被 DS 加密。
4. agents 里的 prompt md 被 DS 加密。
5. OpenClaw 入口和插件 js 被 DS 加密。
6. .ssp 配置文件不进交付包。
```

### 3.1 准备 4 个保护文件

这 4 个文件不是 `claw-trade` 仓库生成的，是发布机上提前用
Windows Virbox 工具做出来的保护运行时和 DS 配置。

这一步只需要在保护配置变更、Python/Node 运行时变更、许可 ID 变更、
DS 密码变更时重新做。普通业务代码改动后，不需要重新生成这 4 个文件，
后面直接跑保护包脚本即可。

先确认当前 Virbox 保护参数：

```text
产品/许可：claw-trade 生产测试许可
许可 ID：16427
许可类型：软锁-本地许可
平台：Linux x86_64
DS：打开
DSProtector 配置：分别导出 python.ssp 和 node.ssp
```

这个许可 ID 要同时出现在三个地方：

```text
1. Virbox Protector 保护 Python 时的配置。
2. Virbox Protector 保护 Node 时的配置。
3. 目标机运行时配置 VIRBOX_LICENSE_ID。
```

如果许可 ID 换了，只改目标机 `VIRBOX_LICENSE_ID` 不够。Python、Node 都要用新许可 ID 重新保护，并重新生成 `python.ssp`、`node.ssp`。

保护配置记录名建议：

```text
claw-trade-python-linux-x86_64-ds-16427
claw-trade-node-linux-x86_64-ds-16427
```

API 密码、DS 密码、账号密码、完整授权码都只进 Virbox 工具或安全凭据库，不写进文档、不进 git、不放交付包。

不要依赖 Virbox GUI 一定有“模板”功能。不同版本可能叫“项目”“保护方案”，也可能只是一次性保护配置。按输入文件、输出位置、许可 ID、平台、DS 配置这几个字段核对即可。

#### 3.1.1 先准备普通生产包

先在 Linux/WSL 里打普通生产包：

```bash
scripts/production/build_production_package.sh
```

普通包里一定有：

```text
runtime/python/bin/python
runtime/openclaw/openclaw.mjs
```

Node 运行时要用 Linux x86_64 的 Node，版本必须满足 OpenClaw 要求。
当前 OpenClaw 入口要求 Node.js 22.12+。

如果普通包里没有 `runtime/node`，就从构建机准备一个 Node 22.12+
Linux 二进制作为 Virbox 输入。后面的保护包脚本会把保护后的
受保护 Node 放进交付包的 `runtime/node`。

检查构建机 Node：

```bash
node --version
command -v node
```

#### 3.1.2 做 Python 保护文件

在 Win11 上准备目录，例如：

```text
D:\claw-trade-virbox\resource-test\protect-python-ds\
```

从普通生产包里取这个文件：

```text
claw-trade-production-版本-时间/runtime/python/bin/python
```

把它作为 Virbox Protector 的待保护 Linux 程序。

在 Virbox Protector 里配置一次 Python 保护：

```text
配置记录名：claw-trade-python-linux-x86_64-ds-16427
输入文件：D:\claw-trade-virbox\resource-test\protect-python-ds\python
输出目录：D:\claw-trade-virbox\resource-test\protect-python-ds\protected
许可类型：软锁-本地许可
许可 ID：16427
平台：Linux x86_64
DS：打开
DS 配置输出：D:\claw-trade-virbox\resource-test\protect-python-ds\python.ssp
导入表保护：不选
压缩：不选
资源保护：不选
```

操作顺序：

```text
1. 从普通生产包复制 runtime/python/bin/python 到输入文件路径。
2. 在 Virbox Protector 里选择这个 Linux x86_64 程序。
3. 选择软锁-本地许可。
4. 填许可 ID：16427。
5. 打开 DS。
6. 填 API 密码和 DS 密码。
7. 如果 Virbox 支持保存项目或方案，就保存；不支持就记录本段参数。
8. 执行保护。
9. 确认生成 protected/python 和 python.ssp。
```

执行保护后，必须得到：

```text
D:\claw-trade-virbox\resource-test\protect-python-ds\protected\python
D:\claw-trade-virbox\resource-test\protect-python-ds\python.ssp
```

含义：

```text
protected/python：交付包里真正运行 Python 代码的解释器。
python.ssp：后面用 DSProtector 加密 .pyc 的配置文件。
```

#### 3.1.3 做 Node 保护文件

在 Win11 上准备目录，例如：

```text
D:\claw-trade-virbox\node-ds-test\
```

把 Linux Node 二进制作为 Virbox Protector 的待保护程序。

如果是在 WSL 里拿当前 Node，可以先复制出来：

```bash
mkdir -p /mnt/d/claw-trade-virbox/node-ds-test/input
cp "$(command -v node)" /mnt/d/claw-trade-virbox/node-ds-test/input/node
```

然后在 Virbox Protector 里配置一次 Node 保护。配置和 Python 保持同一套产品许可：

```text
配置记录名：claw-trade-node-linux-x86_64-ds-16427
输入文件：D:\claw-trade-virbox\node-ds-test\input\node
输出文件：D:\claw-trade-virbox\node-ds-test\input\protected\node
许可类型：软锁-本地许可
许可 ID：16427
平台：Linux x86_64
DS：打开
DS 配置输出：D:\claw-trade-virbox\node-ds-test\input\node.ssp
```

操作顺序：

```text
1. 从 WSL 复制 Linux Node 到 input/node。
2. 在 Virbox Protector 里选择这个 Linux x86_64 程序。
3. 选择软锁-本地许可。
4. 填许可 ID：16427。
5. 打开 DS。
6. 填 API 密码和 DS 密码。
7. 如果 Virbox 支持保存项目或方案，就保存；不支持就记录本段参数。
8. 执行保护。
9. 确认生成 input/protected/node 和 input/node.ssp。
```

执行保护后，必须得到：

```text
D:\claw-trade-virbox\node-ds-test\input\protected\node
D:\claw-trade-virbox\node-ds-test\input\node.ssp
```

含义：

```text
input/protected/node：交付包里真正运行 OpenClaw 的 Node。
node.ssp：后面用 DSProtector 加密 openclaw.mjs、插件 js、agents md 的配置文件。
```

#### 3.1.4 最终检查

WSL 里先生成 Virbox 状态 SDK 包，再检查 5 个文件：

```bash
techlab/virbox_probe/build_virbox_status_sdk.sh

ls -lh \
  .runtime/virbox-status-sdk/virbox-status-sdk-linux-x86_64.tgz \
  /mnt/d/claw-trade-virbox/resource-test/protect-python-ds/protected/python \
  /mnt/d/claw-trade-virbox/resource-test/protect-python-ds/python.ssp \
  /mnt/d/claw-trade-virbox/node-ds-test/input/protected/node \
  /mnt/d/claw-trade-virbox/node-ds-test/input/node.ssp
```

规则：

```text
protected/python 和 input/protected/node 会进最终交付包。
.runtime/virbox-status-sdk/virbox-status-sdk-linux-x86_64.tgz 会进最终交付包，用来读取 Virbox 授权状态。
python.ssp 和 node.ssp 只留在发布机，不进 git，不进交付包，不给客户。
```

### 3.1.5 推荐：用脚本制作保护包

有了上面 4 个文件以后，不需要一条条执行 3.2 到 3.10。

第一次先复制参数文件：

```bash
mkdir -p .runtime
cp scripts/production/virbox-protected-package.env.example .runtime/virbox-protected-package.env
```

然后只改这个文件：

```bash
vim .runtime/virbox-protected-package.env
```

默认参数已经按当前验证路径写好。通常只需要确认这些值：

```text
PROTECTED_PYTHON
PYTHON_SSP
PROTECTED_NODE
NODE_SSP
DSPROTECTOR
OUTPUT_DIR
```

`INPUT_ARCHIVE` 可以留空。留空时脚本自动选择 WSL 仓库目录里的最新普通生产包：

```text
/home/frank/src/claw-trade/dist/production/claw-trade-production-*.tar.gz
```

Windows 里看到的是：

```text
\\wsl.localhost\Ubuntu\home\frank\src\claw-trade\dist\production\claw-trade-production-*.tar.gz
```

这不是 `D:\...`，也不是 `/mnt/d/...`。如果普通生产包已经被你放到 D 盘，就显式传：

```bash
scripts/production/build_virbox_protected_delivery_package.sh \
  --input /mnt/d/你的目录/claw-trade-production-版本-时间.tar.gz
```

脚本流程：

```text
1. 从 WSL 的 dist/production 读取普通包。
2. 解到 WSL 的 .runtime/virbox-delivery-build。
3. 把要加密的 .pyc、.md、.js 临时放到 D 盘给 Windows DSProtector 处理。
4. 把加密结果拷回 WSL 解包目录。
5. 重新打 Virbox 保护包，输出到 D 盘 delivery-output。
6. 默认删除 WSL 解包目录和 D 盘临时加密目录。
```

这里没有用 `scp`，也没有网络上传。`/mnt/d/...` 是 Win11 本机 D 盘在 WSL 里的路径。

默认不会把 1.8G 普通包复制到 D 盘再解开。最终 1.8G 保护包是由 `tar` 直接写到 `/mnt/d/.../delivery-output/`，所以慢的是 WSL 写 Windows D 盘，不是 `scp`。

要保留解包目录排查问题时，加 `--keep-work`：

```bash
scripts/production/build_virbox_protected_delivery_package.sh --keep-work
```

以后制作保护包只运行：

```bash
scripts/production/build_virbox_protected_delivery_package.sh
```

校验脚本生成的 `.sha256` 时，要在输出目录里执行。`.sha256` 里面写的是相对文件名：

```bash
cd /mnt/d/claw-trade-virbox/delivery-output/virbox-protected-时间
sha256sum -c claw-trade-production-版本-时间.tar.gz.sha256
cd /home/frank/src/claw-trade
```

如果想用另一个参数文件：

```bash
scripts/production/build_virbox_protected_delivery_package.sh \
  --config /path/to/virbox-protected-package.env
```

脚本会做这些事：

```text
1. 解开普通生产包。
2. 替换受保护 Python 和 Node。
3. 用 python.ssp 加密 app/python/claw_trade 下的 .pyc。
4. 用 node.ssp 加密 OpenClaw 入口、agents md、OpenClaw 插件 js。
5. 创建 runtime/openclaw-protected。
6. 修启动脚本，让 UI/control 走受保护 OpenClaw。
7. 检查 .ssp 没进包。
8. 重新打 tar.gz 和 sha256。
```

后面的 3.2 到 3.10 是手工排查路径；正常交付优先用这个脚本。
如果你临时只想覆盖某个参数，也可以传 `--input`、`--output-dir` 等命令行参数；
日常不要这么用，太容易输错。

### 3.4 加密 Python .pyc

不要直接在 release 目录里边加密边覆盖。先输出到临时目录，全部成功后再覆盖。

Windows 版 DSProtector 实测不能稳定读取 `\\wsl.localhost\...` 这类 WSL UNC 路径。手工排查时，`WORK`、输入临时目录、输出临时目录都放在 `/mnt/d/...` 下，让 DSProtector 读取 Windows 盘路径。

```bash
DSP="/mnt/d/sw/senseshield/sdk/Tool/VirboxProtect/bin/dsprotector_con.exe"

PY_IN="${WORK}/_ds_python_in"
PY_TMP="${WORK}/_ds_python_out"

rm -rf "$PY_IN" "$PY_TMP"
mkdir -p "$PY_IN" "$PY_TMP"
```

加密范围：

```text
app/python/claw_trade/**/*.pyc
```

执行：

```bash
mkdir -p "$PY_IN/app/python"
cp -a "$RELEASE/app/python/claw_trade" "$PY_IN/app/python/claw_trade"
"$DSP" "$(wslpath -w "$PY_IN")" -c "$(wslpath -w "$PY_SSP")" -o "$(wslpath -w "$PY_TMP")" < /dev/null
```

覆盖回 release：

```bash
cp -a "$PY_TMP/app/python/claw_trade/." "$RELEASE/app/python/claw_trade/"
```

## 7. 制作远程升级包

远程升级包本质上也是生产包，但多了：

```text
1. 生产包签名。
2. manifest.json。
3. manifest.json 签名。
4. 上传到 Cloudflare R2 的 stable/。
```

如果产品要求 Virbox 保护，升级用的 tar.gz 也必须是第 3 节做出来的保护包。不要把普通生产包拿去签名发布。

### 7.1 给 tar.gz 签名

发布私钥只放发布机，不放目标工控机。

```bash
openssl pkeyutl -sign \
  -inkey update-signing-private.pem \
  -rawin \
  -in claw-trade-production-版本-时间.tar.gz \
  -out claw-trade-production-版本-时间.tar.gz.sig
```

### 7.2 生成 manifest.json

示例：

```json
{
  "product": "claw-trade",
  "channel": "stable",
  "version": "0.1.4",
  "arch": "linux-x86_64",
  "archive": "claw-trade-production-0.1.4-20260629T114637Z.tar.gz",
  "sha256": "这里填最终 tar.gz 的 sha256",
  "created_at": "2026-06-29T11:46:37Z",
  "min_current_version": "0.1.0",
  "notes": "release note"
}
```

字段要求：

```text
version：新版本号，必须高于目标机当前版本。
archive：只写文件名，不写路径。
sha256：必须是最终上传 tar.gz 的 sha256。
min_current_version：允许升级的最低当前版本。
```

计算 sha256：

```bash
sha256sum claw-trade-production-版本-时间.tar.gz
```

### 7.3 给 manifest 签名

```bash
openssl pkeyutl -sign \
  -inkey update-signing-private.pem \
  -rawin \
  -in manifest.json \
  -out manifest.json.sig
```

最终有 4 个文件：

```text
claw-trade-production-版本-时间.tar.gz
claw-trade-production-版本-时间.tar.gz.sig
manifest.json
manifest.json.sig
```

### 7.4 上传远程升级文件

打开 Cloudflare：

```text
R2 Object Storage -> claw-trade-delivery -> Upload
```

按这个顺序上传：

```text
1. claw-trade-production-版本-时间.tar.gz      -> stable/claw-trade-production-版本-时间.tar.gz
2. claw-trade-production-版本-时间.tar.gz.sig  -> stable/claw-trade-production-版本-时间.tar.gz.sig
3. manifest.json                              -> stable/manifest.json
4. manifest.json.sig                          -> stable/manifest.json.sig
```

不要先传 `manifest.json`。否则目标机可能先看到新版本，但包还没传完。

上传后在浏览器打开：

```text
https://download.cflank-trade.top/stable/manifest.json
https://download.cflank-trade.top/stable/manifest.json.sig
https://download.cflank-trade.top/stable/claw-trade-production-版本-时间.tar.gz
https://download.cflank-trade.top/stable/claw-trade-production-版本-时间.tar.gz.sig
```

确认显示的是新版本、新 archive、新 sha256。

```text
10. 每台机器都已绑定 Virbox 授权。
11. 新 Ubuntu 机器能一键安装。
12. http://127.0.0.1:5175/ 返回 200。
13. http://目标机IP:5175/ 能从 Win11 打开。
14. Virbox 授权码已经在目标机绑定成功。
15. 如果要远程升级，目标机有更新源和公钥。
16. 如果发布远程升级，上传的 4 个文件和 CDN 都已验证。
```

## 12. 常见问题

### 只创建了目录，没有真正安装 release

现象：

```text
/opt/claw-trade/current 不存在
/opt/claw-trade/releases 是空的
浏览器打不开
curl 127.0.0.1:5175 失败
```

处理：

```bash
curl -fsSL "${BASE}/install_from_r2_ubuntu.sh" | bash -s -- --base-url "${BASE}" --license-key-file "${LICENSE_KEY_FILE}"
```

不要只手工创建 `/opt/claw-trade` 目录。

### 包能装，但 UI 起不来

检查日志：

```bash
tail -n 120 /tmp/claw-trade-ui.log
tail -n 120 /tmp/claw-trade-control.log
```

检查端口：

```bash
ss -ltnp | grep 5175
```

### Win11 打不开目标机页面

先在目标机本机检查：

```bash
curl -fsS http://127.0.0.1:5175/ | head
ss -ltnp | grep 5175
```

如果本机正常，Win11 打不开，优先查目标机防火墙、IP 是否正确、UI 是否监听 `0.0.0.0:5175`。

### Virbox 授权一台机器成功，另一台机器不能用

这是正常的。

授权码软锁绑定机器指纹。换机器就要重新激活、转移或重新发码。

### 检查更新提示未配置

检查：

```bash
sudo grep CLAW_TRADE_UPDATE_BASE_URL /opt/claw-trade/shared/config/claw-trade.env
```

### 检查更新提示公钥不存在

检查：

```bash
ls -l /etc/claw-trade/update-signing-public.pem
```

### R2 已经上传，但目标机还是旧版本

打开：

```text
https://download.cflank-trade.top/stable/manifest.json
```

确认看到的是新 `version`、新 `archive`、新 `sha256`。

### 安装更新按钮不可用

先点：

```text
检查更新
```

只有检查到可安装新版本后，`安装更新` 才可用。

### 升级包校验失败

通常是：

```text
1. manifest 里的 sha256 不是最终 tar.gz 的 sha256。
2. tar.gz 签名对应的不是最终 tar.gz。
3. manifest.json 改过后没有重新签名。
4. archive 文件名写错。
5. 包名或顶层目录名不符合 claw-trade-production-版本-时间。
```

处理：

```text
重新计算 sha256。
重新签 tar.gz。
重新签 manifest.json。
重新上传 4 个文件。
重新刷新 CDN。
```

### Virbox 状态检查 SDK 缺失

如果日志提示 Virbox 状态检查 SDK 缺失，说明 UI 授权状态显示可能不可用。

这不等于 Virbox 保护运行时失效。受保护 Python、Node、DS 加密文件仍然按 Virbox 保护逻辑运行。

如果产品要求界面显示授权状态，就把 Virbox 状态检查 SDK 补进生产包，再重新构建和验证。
