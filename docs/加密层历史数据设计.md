# 加密层历史数据设计

状态：设计和执行口径，Phase 1 当前有效仓库已切到 Binance USDT-only 历史包、校验、清洗归一化和统一列式 normalized 导入；不代表 Phase 2-4 已完成。
日期：2026-06-07

## 1. 结论

加密市场需要新增本地历史数据包导入层，处理方式应对齐 A股预打包数据导入模式：先下载历史包，校验，清洗，归一化到统一数据仓库，再让 `/report` 优先读取本地仓库。

第一阶段不追求“全球加密全市场”。第一阶段目标是：

- Binance 当前 active 交易对历史行情包。
- 现货和 USD-M 合约的 `1d`、`1h` K线。
- BTC、ETH、SOL 作为首轮验收样本，不代表全量范围只做这三个币。
- 资产符号和交易对映射，例如 `SOL` -> `SOLUSDT`。
- 导入后写入 raw、attempt、manifest、normalized refs 证据链。

当前执行口径：

- 已完成：BTCUSDT、ETHUSDT、SOLUSDT 的 2025-01 spot / USD-M `1d`、`1h` 样本下载、checksum 校验、清洗归一化和本地仓库证明；最终 normalized 写入机制已统一到列式仓库。
- 已完成：Binance 当前 active 交易对 URL manifest 生成、实际下载、checksum 校验、清洗归一化和统一列式导入。原始全 quote 批次已被当前 USDT-only 批次取代；当前有效仓库只保留 USDT 交易对。
- 已完成：downloader 支持 `--all-symbols` 发现 Binance 当前 active 交易对；完整月份生成 monthly 包，非完整月份生成 daily 包。
- 已完成：当前原始包目录为 `data/crypto-history-full/binance/data`，只剩 USDT 包：32452 个 ZIP、32452 个 checksum、596 个 USDT symbol；非 USDT ZIP 为 0。该目录在项目 `data/` 下，不再放在 `.runtime` 下。
- 已完成：当前 USDT-only 列式仓库为 `data/crypto-history-full/normalized-columnar-usdt-only`，Mongo catalog 库为 `claw_trade_crypto_history_usdt_20260608`；Mongo `normalized_datasets` 为 0，normalized rows 写入 Parquet。
- 已完成：当前 active Parquet manifest 为 1921 个，active Parquet rows 为 8001515 行；BTCUSDT、ETHUSDT、SOLUSDT 的 spot `1d`/`1h` 仓库读回覆盖 2025-06-01 至 2026-06-06，日期/小时缺口为 0。
- 已完成：旧混合 Mongo 库已不存在；旧混合大结果 JSON 已删除，当前证据见 `docs/evidence/crypto-history-usdt-only-cleanup-20260608.md`。
- 已完成：真实 `/report BTC` 和 `/report SOL` provider-payload 证明已在当前项目内 USDT-only seed 仓库上重跑完成；最终有效证据为“运行时写库 + seed 只读库”隔离验收，见 `docs/evidence/live-crypto-seed-overlay-20260608/summary.md`。

后续再扩展到：

- 核心币池衍生品历史包。
- 链上和基本面历史包。
- 新闻和社交历史包。
- 盘口、tick、爆仓、资金费率、OI 等付费深度数据。

## 2. 为什么要改

近期 CRYPTO `/report` 测试显示，数据源并不是完全没有返回，而是返回结果无法稳定变成报告级材料：

- 一年历史覆盖不足。
- 快照、日线、小时线和事件流粒度不一致。
- 部分 provider 返回字段与仓库要求不匹配。
- Coinglass 部分接口成功，但多空比为空、期货盘口限流、部分历史价格/盘口被冷却跳过。
- 新闻和社交只有线索，缺少可引用材料。

结论是：加密报告不应依赖运行时临时拉一年数据。应先像 A股一样准备本地历史仓库，运行时只补最新增量。

## 3. 已有项目边界

本设计遵守现有架构边界：

- `claw-trade` 控制 workflow、数据仓库、证据链和报告导出。
- OpenClaw 只运行单 worker turn。
- OpenViking 只存 approved material 和证据，不当行情、新闻、社交或链上数据源。
- Python 不替 worker 写投资分析结论。
- 不新增 runtime guard，不通过硬门禁掩盖数据缺口。
- 数据源失败、权限不足、限流、字段缺失、覆盖不足都必须显式进入 evidence / data gaps。

A股已有可复用模式：

- `src/claw_trade/data_gateway/a_share_prepackaged_importer.py`
- `scripts/selection/import_a_share_prepackaged_to_mongo.py`
- 本地包导入后写 raw、attempt、manifest、normalized refs。

加密层应新增同类 importer，而不是绕过 data_gateway 或临时读取 CSV。

## 4. 数据源分层

### 4.1 第一阶段主源：Binance Public Data

定位：加密行情历史 seed 包主源。

用途：

- 现货 K线。
- USD-M 合约 K线。
- 后续可扩展成交和聚合成交。

当前第一版有效导入范围：

- spot 当前 active USDT 交易对 `1d`。
- spot 当前 active USDT 交易对 `1h`。
- USD-M futures 当前 active USDT perpetual 交易对 `1d`。
- USD-M futures 当前 active USDT perpetual 交易对 `1h`。

第一版不导：

- `1m` 全量。
- trades 全量。
- aggTrades 全量。
- order book / tick。
- options。

原因：

- `1m`、trades、tick 数据量过大，不适合第一阶段直接全量落库。
- 第一阶段目标是先解决 `/report` 里一年日线/小时线缺口。
- 盘口和 tick 应放入付费深度数据阶段。

来源依据：

- Binance Public Data repo 说明其数据以 daily/monthly 文件提供，支持 spot 和 futures，包含 Klines、Trades、AggTrades，并提供 checksum 校验。
- 文档说明支持 all symbols，新增 daily 数据次日可用，新增 monthly 数据每月初可用。
- URL: https://github.com/binance/binance-public-data

当前 downloader 生成规则：

- 完整月份使用 monthly 包。
- 不完整月份使用 daily 包，例如当前月或请求范围只覆盖月内几天时。
- 这样避免在当前月 monthly 包尚未发布时假装覆盖到今天。

Binance Kline 文件格式约束：

- 文件来自 Binance Klines API 的列顺序，但实际包可能带表头或不带表头；importer 不得硬假设某一种。
- spot 和 USD-M futures Klines 均按 12 列解析：`open_time`、`open`、`high`、`low`、`close`、`volume`、`close_time`、`quote_asset_volume`、`number_of_trades`、`taker_buy_base_asset_volume`、`taker_buy_quote_asset_volume`、`ignore`。
- spot 数据自 2025-01-01 起 timestamp 使用微秒；历史 spot 和 futures 样例存在毫秒口径。importer 必须按数值位数或显式来源识别毫秒/微秒，统一归一化为 UTC 时间。
- 第一阶段不导 COIN-M futures；若后续导入，COIN-M Klines 的第 8 列是 `base_asset_volume`，不能复用 USD-M 的 `quote_asset_volume` 语义。

URL pattern：

```text
spot monthly:
https://data.binance.vision/data/spot/monthly/klines/{SYMBOL}/{INTERVAL}/{SYMBOL}-{INTERVAL}-{YYYY-MM}.zip

spot daily:
https://data.binance.vision/data/spot/daily/klines/{SYMBOL}/{INTERVAL}/{SYMBOL}-{INTERVAL}-{YYYY-MM-DD}.zip

USD-M futures monthly:
https://data.binance.vision/data/futures/um/monthly/klines/{SYMBOL}/{INTERVAL}/{SYMBOL}-{INTERVAL}-{YYYY-MM}.zip

USD-M futures daily:
https://data.binance.vision/data/futures/um/daily/klines/{SYMBOL}/{INTERVAL}/{SYMBOL}-{INTERVAL}-{YYYY-MM-DD}.zip
```

checksum 规则：

- 每个 ZIP 同目录有 `.CHECKSUM` 文件。
- 校验算法是 SHA256。
- 下载器必须先校验 checksum，再允许 importer 消费该 ZIP。
- importer 必须在索引 ZIP 包时重新读取同名 `.CHECKSUM` 并复算 SHA256；没有 `.CHECKSUM` 或 checksum mismatch 的 ZIP 不能进入 import job。
- checksum 失败是阻断错误，不能降级成 warning。

## 5. Binance 全交易对不是加密全市场

设计上必须区分：

- Binance 全交易对历史包。
- 全球加密全市场历史包。

Binance 全交易对只代表 Binance 这个交易所，不代表 Coinbase、OKX、Bybit、Kraken、链上 DEX 或全部已下架资产。

第一阶段允许称为：

```text
Binance 全交易对历史行情包
```

不允许称为：

```text
加密全市场完整历史数据包
```

报告和证据必须明确 source scope，避免把单一交易所历史数据写成全市场事实。

## 6. 目标数据模型

### 6.1 行情数据

目标数据类型：

- `daily_bar`
- `intraday_bar`

核心字段：

- `market=CRYPTO`
- `dataset=daily_bar` 或 `intraday_bar`
- `granularity=daily` 或 `1h`
- `symbol_id=SOLUSDT`
- `base_asset=SOL`
- `quote_asset=USDT`
- `exchange=BINANCE`
- `timezone=UTC`
- `calendar=CRYPTO_24_7`
- `open`
- `high`
- `low`
- `close`
- `volume`
- `amount`
- `period_start`
- `period_end`
- `raw_refs`

provider lineage：

```json
{
  "provider_id": "local_crypto_prepackaged",
  "endpoint_id": "binance_public_data_import",
  "source": "binance_public_data",
  "market_segment": "spot",
  "remote_attempted": false,
  "raw_refs": ["raw:CRYPTO:local_crypto_prepackaged:<hash>"]
}
```

CRYPTO normalized row 必须写入 `DatasetRepository` 当前 normalized 仓库，不得绕过统一数据层。当前统一规则是：

- `DatasetRepository` 配置了 `NormalizedColumnarWarehouse` 时，normalized rows 写入 Parquet 分区，Mongo `dataset_manifests` 只保存 Parquet manifest/catalog。
- 出厂 seed Mongo catalog 只保存本地历史包 raw metadata、`local_seed_imported` provider attempts、seed import manifest 和 Parquet manifest/catalog。
- live/runtime 运行时证据必须写入运行时 Mongo 库；不能把 provider 增量、rate-limit、single-flight、cache 写回出厂 seed Mongo catalog。
- 运行时通过 `DATA_GATEWAY_SEED_MONGODB_URI` / `DATA_GATEWAY_SEED_MONGODB_DATABASE` 只读挂载 seed catalog，通过 `DATA_GATEWAY_MONGODB_URI` / `DATA_GATEWAY_MONGODB_DATABASE` 写运行时证据。
- Mongo 中的 catalog/attempt/manifest 不得保存大批量完整逐行 `dataset_refs`。超过阈值时只保存 `dataset_ref_count`、20 条样本、`dataset_refs_sha256` 和 `dataset_ref_prefixes`；完整行情行和可查询数据在 Parquet。
- 不能新增 CRYPTO 专用 collection、临时 CSV 索引或市场专用读取接口。
- 向上仍暴露统一 `Warehouse` / `DataAPI` 查询结果，由 worker 按 data pack / approved material 按需获取，不直接关心底层是 Parquet 还是 Mongo catalog。

等价于 A股 `_normalized_selection_record` 的 CRYPTO 行情行结构如下：

```json
{
  "dataset_ref": "dataset:daily_bar:CRYPTO:spot:SOLUSDT:daily:2026-06-06:2026-06-06",
  "dataset": "daily_bar",
  "market": "CRYPTO",
  "symbol_id": "SOLUSDT",
  "universe_ref": "binance_spot_all_symbols",
  "granularity": "daily",
  "period_start": "2026-06-06",
  "period_end": "2026-06-06",
  "field_set": ["amount", "base_asset", "close", "close_time", "date", "high", "interval", "low", "market_segment", "number_of_trades", "open", "open_time", "quote_asset", "quote_asset_volume", "symbol_id", "volume"],
  "exchange": "BINANCE",
  "currency": "USDT",
  "timezone": "UTC",
  "calendar": "CRYPTO_24_7",
  "base_asset": "SOL",
  "quote_asset": "USDT",
  "source_market_segment": "spot",
  "provider_lineage": {
    "provider_id": "local_crypto_prepackaged",
    "endpoint_id": "binance_public_data_import",
    "source": "binance_public_data",
    "market_segment": "spot",
    "remote_attempted": false,
    "raw_refs": ["raw:CRYPTO:local_crypto_prepackaged:<hash>"]
  },
  "schema_id": "crypto_binance_prepackaged_bar.v1",
  "quality_flags": [],
  "row": {
    "open": "100.0",
    "high": "101.0",
    "low": "99.0",
    "close": "100.5",
    "volume": "123.0",
    "amount": "12345.0",
    "quote_asset_volume": "12345.0",
    "number_of_trades": 456
  }
}
```

字段取值规则：

- `dataset` 只能是 `daily_bar` 或 `intraday_bar`。
- `dataset_ref` 必须显式包含 source market segment，例如 `dataset:daily_bar:CRYPTO:spot:SOLUSDT:daily:2026-06-06:2026-06-06`，避免 spot 和 USD-M futures 同币种同日期互相覆盖。
- `market` 固定为 `CRYPTO`。
- `provider_lineage.provider_id` 固定为 `local_crypto_prepackaged`。
- `provider_lineage.endpoint_id` 固定为 `binance_public_data_import`。
- `exchange` 固定为 `BINANCE`。
- `timezone` 固定为 `UTC`。
- `calendar` 固定为 `CRYPTO_24_7`。
- spot 行使用 `universe_ref=binance_spot_all_symbols`。
- USD-M futures 行使用 `universe_ref=binance_usdm_all_symbols`。
- `source_market_segment` 只能是 `spot` 或 `usdm_futures`。
- `currency` 使用 quote asset，例如 `USDT`、`USDC`、`FDUSD`。
- `amount` 对 spot 和 USD-M futures 第一阶段统一取 Binance Kline 的 `quote_asset_volume`。若未来接 COIN-M futures，必须另行定义 amount 口径，不能复用此规则。
- `schema_id` 第一阶段固定为 `crypto_binance_prepackaged_bar.v1`。

### 6.2 资产和交易对映射

用户输入通常是资产，例如 `BTC`、`ETH`、`SOL`。Binance 数据是交易对，例如 `BTCUSDT`、`ETHUSDT`、`SOLUSDT`。

需要新增资产映射层：

```text
BTC -> BTCUSDT
ETH -> ETHUSDT
SOL -> SOLUSDT
```

当前主交易对选择规则：

1. Phase 1 默认只选 `USDT`。
2. 用户输入裸资产时映射为 `{asset}USDT`。
3. 用户输入显式非 USDT 交易对时，先取 base asset，再映射回 `{base}USDT`。
4. 非 USDT 交易对不得进入当前本地历史仓库。
5. 若后续需要 USDC、FDUSD、USD 或 BTC/ETH 计价对，必须作为新范围单独批准，不能混进当前 USDT-only 仓库。

当多个交易所或多个 quote 同时存在时，不能静默覆盖，必须记录选择依据。

维护机制：

- Phase 1 使用显式 seed allowlist 作为验收入口：`BTC`、`ETH`、`SOL`。
- downloader 同时保存 Binance symbol discovery manifest，记录 symbol、base asset、quote asset、market segment、status、as_of。
- 当前已验收的 `/report` 裸资产映射只覆盖 `BTC`、`ETH`、`SOL` 这组 Phase 1 seed allowlist。
- 代码已提供从 download manifest 生成候选交易对的工具函数，但 report runtime 尚未把“任意 Binance active 裸资产”接到 discovery manifest 和流动性排序源。
- asset mapping 不长期维护手写表；后续正式支持任意 active 裸资产时，必须从 discovery manifest 生成候选交易对，再按 quote 优先级和流动性选择主交易对。
- `BTC -> BTCUSDT` 这类表只允许作为文档样例和小样本验收固定输入，不允许成为长期唯一映射源。

### 6.3 核心币池

核心币池不应写死为 BTC/ETH。

第一批验收：

- BTC
- ETH
- SOL

第二批扩展：

- BNB
- XRP
- DOGE
- ADA
- AVAX
- LINK
- TON
- TRX
- DOT
- LTC

后续应按流动性自动生成 Top N，而不是长期维护手写列表。

迁移路径：

- Phase 1：只用 `BTC/ETH/SOL` 作为固定 proof，不声称覆盖核心币池。
- Phase 2：新增 `crypto_core_universe_manifest`，从 Binance spot / USD-M futures discovery manifest 和 24h ticker 成交额中生成 Top N。
- Top N 排序至少记录 `quote_volume`、`source_market_segment`、`as_of` 和入选阈值。
- 手写第二批列表只能作为候选观察清单；正式导入范围以 `crypto_core_universe_manifest` 为准。

## 7. 新增组件

### 7.1 下载器

建议新增：

```text
scripts/crypto/download_binance_public_data.py
```

职责：

- 发现 Binance spot / futures 可用交易对。
- 生成 daily/monthly ZIP URL。

CLI 参数至少包括：

```text
--output-root

--checksum-required
--force
--ignore-missing
--progress-every <n>
--output-json <path>
```

不负责：

- 写 Mongo。
- 写报告。

职责：

- 解析 Binance CSV。
- 处理毫秒/微秒 timestamp 差异。
- 归一化交易对、资产、quote、exchange、UTC 时间。
- 通过统一 `DatasetRepository` 写 normalized rows；当前默认写入 `NormalizedColumnarWarehouse` 的 Parquet 分区。
- 写 raw package record。
- 写 provider attempt record。
- 写 dataset manifest。
- 支持 replace-existing，但必须显式确认维护范围。

CLI 参数至少包括：

```text
--spot-root <path>
--futures-root <path>
--trade-date YYYY-MM-DD
--import-run-id <id>
--start-date YYYY-MM-DD
--end-date YYYY-MM-DD
--symbol SOLUSDT
--symbol-file <path>
--symbol-manifest <download-manifest.json>
--max-symbols <n>
--market-segment spot|usdm_futures
--interval 1d|1h
--replace-existing
--confirm-replace-existing
--audit-only
--output-json <path>
--mongo-uri <uri>
--mongo-database <name>
--columnar-root <path>
```

`--replace-existing` 第一次使用时必须要求 `--confirm-replace-existing`。当前代码的真实语义是：

- legacy Mongo normalized rows：只能删除同一 `symbol_id`、同一 `granularity`、同一 `source_market_segment`、`provider_lineage.provider_id=local_crypto_prepackaged`、`provider_lineage.endpoint_id=binance_public_data_import`、`provider_lineage.market_segment=<当前导入 segment>` 的 CRYPTO normalized rows。不得删除其它 provider、其它市场或同 symbol 的其它 market segment 数据。
- 列式 normalized rows：不做范围删除；新写入相同 `dataset_ref` 时通过 Parquet manifest supersession 让旧 manifest 失效。若要删除整段列式历史或整批 Parquet 分区，需要另行设计列式 manifest 范围失效机制，不能把当前 `--replace-existing` 写成已支持列式范围删除。

不负责：

- 出网下载。
- 调实时 provider。
- 推断投资结论。

### 7.3 仓库读取优先级

`/report` 数据包读取时应遵守：

1. 先查本地 normalized warehouse。
2. 若本地仓库对请求 symbol 完全没有数据，必须写显式 data gap：`local_warehouse_empty`。兼容现有数据层时，其 `reason` 可使用 `warehouse_missing`，但 `gap_code`、`human_readable` 或 attempt metadata 必须保留 `local_warehouse_empty`，不能只留下泛化的 provider fallback 结果。
3. 若本地仓库有部分数据但覆盖不足，必须写 `date_range_missing`，并记录 `expected_start`、`expected_end`、`actual_start`、`actual_end`、`missing_ranges`。
4. 只有在本地缺口已经写入 evidence / data gaps 后，才允许走 provider 增量补数据。
5. provider 成功或失败都写 evidence。
6. provider 补数不能抹掉证据链里的本地缺口事实：attempt / evidence 中仍要能看到初始 `local_warehouse_empty` 或 `date_range_missing`。但若远端 provider 已经补齐该请求的可用 rows，最终 `DataResult` 和读者报告不应继续显示 `local_warehouse_empty`，否则会把“已补齐”误报成“仍缺本地数据”。Phase 1 验收本地 seed 包时，`/report BTC` 和 `/report SOL` 仍必须证明命中 `local_crypto_prepackaged`，不能用远端 provider 成功代替本地仓库成功。
7. 本地和远端口径冲突时，记录 conflict，不静默覆盖。
8. 用户输入裸资产代码时，CRYPTO 报告链路必须先映射到本地主交易对，例如 `BTC` -> `BTCUSDT`、`SOL` -> `SOLUSDT`。显示货币为 USD 不等于本地仓库要查 `BTCUSD` 或 `SOLUSD`。
9. 报告可见的 market `daily_bar` / `intraday_bar` 第一阶段只使用 spot 行；USD-M futures 行保留在仓库和审计证据中，但不能混进现货市场图表和现货行情行。

## 9. 错误处理

必须显式记录：

- 文件不存在。
- checksum mismatch。
- CSV schema mismatch。
- timestamp 单位无法判断。
- 空文件。
- 交易对无法解析。
- 资产映射冲突。
- 覆盖区间不足。
- 重复 bar。
- 同一 period 多条冲突记录。
- 已下架交易对缺失。
- replace-existing 未确认。

已下架交易对规则：

- Phase 1 默认只发现和下载当前 active 的 Binance spot / USD-M futures 交易对。
- 如果本地包目录出现已下架或 discovery manifest 中不可见的交易对，importer 默认跳过该交易对，并在 CLI/audit result 里写 `delisted_symbol_skipped` warning。被跳过的交易对没有 dataset manifest，不能伪造导入记录。
- 被跳过的已下架交易对不得计入 coverage、Top N 或 `/report` 本地命中证明。
- 若用户要求覆盖已下架交易对完整历史，触发停止条件，必须另行批准范围、来源和验收口径。

禁止：

- checksum 失败后继续当成功。
- 交易对无法解析时猜测资产。
- 本地包覆盖不足时写成全量覆盖。
- 下载失败后假装源不可用但不写 attempt。
- 用 Binance 全交易对替代全球加密全市场声明。

## 10. 验收计划

### 10.0 `date_range_missing` 验收定义

`date_range_missing` 不是新增临时字段，而是数据层已有的缺口原因：`GapReason.DATE_RANGE_MISSING`。

在本设计中，Phase 1 只用它验收 CRYPTO 行情历史覆盖，不用它验收新闻、社交、基本面或链上覆盖。

计量口径：

- 来源一：`DataResult.gaps[].reason == "date_range_missing"`。
- 来源二：`DataResult.freshness.coverage_by_request[]` 中的 `expected_start`、`expected_end`、`actual_start`、`actual_end`、`missing_ranges`。
- CRYPTO 没有交易所休市日，`daily_bar` 使用 UTC calendar day，而不是 A股交易日。
- `/report` 默认一年范围按请求的精确日期范围计量，例如 `2025-06-06` 到 `2026-06-06`；如果是闰年或请求跨度变化，以实际 `expected_start` / `expected_end` 为准。
- `daily_bar` 的 `date_range_missing_count` 是请求 UTC 日期集合中没有任何本地 bar 覆盖的日期数量。
- `intraday_bar` 的覆盖计量使用 UTC 小时桶；第一阶段 live proof 只要求记录小时覆盖摘要，不要求小时缺口降为 0。

Phase 1 目标值：

- `BTCUSDT`、`ETHUSDT`、`SOLUSDT` 的 spot `daily_bar` 在 `/report` 请求的一年范围内，`date_range_missing_count=0`。
- `/report BTC` 和 `/report SOL` 的 market data pack 必须显示 `local_crypto_prepackaged` 的本地 seed evidence。
- 若远端 provider 补齐后没有 `date_range_missing`，但本地 `local_crypto_prepackaged` 仍为空或不完整，Phase 1 验收仍失败。

## 11. 停止条件

遇到以下情况必须停下来问人：

- 第一版要求下载 1m 全量、trades 全量或 tick 全量。
- 需要覆盖已下架交易对完整历史。
- 要购买或接入 Tardis、Kaiko、CoinAPI、Glassnode、Santiment、The Tie、LunarCrush。
- 要把 Binance 全交易对称作“加密全市场”。
- 需要删除或替换已有 CRYPTO normalized rows。
- 需要修改 OpenClaw runtime。
- 需要新增 runtime guard 或改变 worker prompt 风格。
