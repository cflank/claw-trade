# 加密层历史数据设计

状态：设计草案，未代表代码已完成。
日期：2026-06-07

## 1. 结论

加密市场需要新增本地历史数据包导入层，处理方式应对齐 A股预打包数据导入模式：先下载历史包，校验，清洗，归一化到统一数据仓库，再让 `/report` 优先读取本地仓库。

第一阶段不追求“全球加密全市场”。第一阶段目标是：

- Binance 全交易对历史行情包。
- 现货和 USD-M 合约的 `1d`、`1h` K线。
- BTC、ETH、SOL 作为验收样本。
- 资产符号和交易对映射，例如 `SOL` -> `SOLUSDT`。
- 导入后写入 raw、attempt、manifest、normalized refs 证据链。

后续再扩展到：

- 核心币池衍生品历史包。
- 链上和基本面历史包。
- 新闻和社交历史包。
- 盘口、tick、爆仓、资金费率、OI 等付费深度数据。

## 2. 为什么要改

近期 CRYPTO `/report` 测试显示，数据源并不是完全没有返回，而是返回结果无法稳定变成报告级材料：

- 一年历史覆盖不足。
- 快照、日线、小时线和事件流粒度不一致。
- 部分 provider 返回字段与仓库要求不匹配。
- Coinglass 部分接口成功，但多空比为空、期货盘口限流、部分历史价格/盘口被冷却跳过。
- 新闻和社交只有线索，缺少可引用材料。

结论是：加密报告不应依赖运行时临时拉一年数据。应先像 A股一样准备本地历史仓库，运行时只补最新增量。

## 3. 已有项目边界

本设计遵守现有架构边界：

- `claw-trade` 控制 workflow、数据仓库、证据链和报告导出。
- OpenClaw 只运行单 worker turn。
- OpenViking 只存 approved material 和证据，不当行情、新闻、社交或链上数据源。
- Python 不替 worker 写投资分析结论。
- 不新增 runtime guard，不通过硬门禁掩盖数据缺口。
- 数据源失败、权限不足、限流、字段缺失、覆盖不足都必须显式进入 evidence / data gaps。

A股已有可复用模式：

- `src/claw_trade/data_gateway/a_share_prepackaged_importer.py`
- `scripts/selection/import_a_share_prepackaged_to_mongo.py`
- 本地包导入后写 raw、attempt、manifest、normalized refs。

加密层应新增同类 importer，而不是绕过 data_gateway 或临时读取 CSV。

## 4. 数据源分层

### 4.1 第一阶段主源：Binance Public Data

定位：加密行情历史 seed 包主源。

用途：

- 现货 K线。
- USD-M 合约 K线。
- 后续可扩展成交和聚合成交。

第一版只导：

- spot 全交易对 `1d`。
- spot 全交易对 `1h`。
- USD-M futures 全交易对 `1d`。
- USD-M futures 全交易对 `1h`。

第一版不导：

- `1m` 全量。
- trades 全量。
- aggTrades 全量。
- order book / tick。
- options。

原因：

- `1m`、trades、tick 数据量过大，不适合第一阶段直接全量落库。
- 第一阶段目标是先解决 `/report` 里一年日线/小时线缺口。
- 盘口和 tick 应放入付费深度数据阶段。

来源依据：

- Binance Public Data repo 说明其数据以 daily/monthly 文件提供，支持 spot 和 futures，包含 Klines、Trades、AggTrades，并提供 checksum 校验。
- 文档说明支持 all symbols，新增 daily 数据次日可用，新增 monthly 数据每月初可用。
- URL: https://github.com/binance/binance-public-data

### 4.2 第二阶段免费补充源

#### Coin Metrics Community

定位：BTC、ETH 等资产的基础链上指标和社区数据。

用途：

- 网络指标。
- 部分市场指标。
- BTC/ETH 链上历史补充。

注意：

- Community 数据是免费子集，不等于完整 Network Data Pro。
- 资产和指标集合可能变化。

URL: https://github.com/coinmetrics/data

#### Kraken Historical CSV

定位：BTC/USD 等重点交易对的交易历史交叉校验源。

用途：

- 对 Binance 价格历史做交叉验证。
- BTC/USD 现货成交历史补充。

URL: https://support.kraken.com/articles/360047543791-downloadable-historical-market-data-time-and-sales-

#### CoinGecko / CoinMarketCap

定位：币种基本面、供应量、市值、FDV、成交量和 OHLCV 补充。

用途：

- `valuation_metric`。
- `market_cap`。
- `fdv`。
- `circulating_supply`。
- `total_supply`。
- 跨交易所聚合价格和成交量。

注意：

- 更适合 API 回填，不是纯离线包。
- 免费额度和历史粒度有限，不能替代 Binance 行情 seed 包。

### 4.3 第三阶段付费深度源

这些源不应默认免费使用，也不应在第一阶段硬依赖。

| 数据源 | 适合补什么 | 设计判断 |
|---|---|---|
| Coinglass | 资金费率、OI、多空比、爆仓、净流、AHR999 | 已接入但当前不稳定；适合继续做实时/补充源。若要做历史 seed，需要确认套餐、限额、导出能力和许可 |
| Tardis.dev | tick、盘口、资金费率、OI、爆仓、quotes、order book snapshots | 最适合补本次 CRYPTO 最大缺口；完整历史通常需要付费 |
| Kaiko | L1/L2、交易、盘口、深度、流动性、云交付、标准化格式 | 适合机构级长期产品化 |
| CoinAPI Flat Files | 压缩 CSV、S3、OHLCV、trades、quotes、limit book | 适合批量历史下载和离线仓库 |
| Glassnode | MVRV、SOPR、活跃地址、链上和衍生品指标 | 深度链上主候选，通常付费 |
| Santiment | 链上、开发、社交、情绪历史 | 社交和链上增强源 |
| The Tie | 新闻、情绪、解锁、开发和链上基本面 | 新闻/社交历史增强源 |
| LunarCrush | 社交热度、情绪、topic time-series | 社交指标增强源 |

## 5. Binance 全交易对不是加密全市场

设计上必须区分：

- Binance 全交易对历史包。
- 全球加密全市场历史包。

Binance 全交易对只代表 Binance 这个交易所，不代表 Coinbase、OKX、Bybit、Kraken、链上 DEX 或全部已下架资产。

第一阶段允许称为：

```text
Binance 全交易对历史行情包
```

不允许称为：

```text
加密全市场完整历史数据包
```

报告和证据必须明确 source scope，避免把单一交易所历史数据写成全市场事实。

## 6. 目标数据模型

### 6.1 行情数据

目标数据类型：

- `daily_bar`
- `intraday_bar`

核心字段：

- `market=CRYPTO`
- `dataset=daily_bar` 或 `intraday_bar`
- `granularity=daily` 或 `1h`
- `symbol_id=SOLUSDT`
- `base_asset=SOL`
- `quote_asset=USDT`
- `exchange=BINANCE`
- `timezone=UTC`
- `calendar=CRYPTO_24_7`
- `open`
- `high`
- `low`
- `close`
- `volume`
- `amount`
- `period_start`
- `period_end`
- `source_ref`

provider lineage：

```json
{
  "provider_id": "local_crypto_prepackaged",
  "endpoint_id": "binance_public_data_import",
  "source": "binance_public_data",
  "remote_attempted": false,
  "raw_refs": ["raw:CRYPTO:local_crypto_prepackaged:<hash>"]
}
```

### 6.2 资产和交易对映射

用户输入通常是资产，例如 `BTC`、`ETH`、`SOL`。Binance 数据是交易对，例如 `BTCUSDT`、`ETHUSDT`、`SOLUSDT`。

需要新增资产映射层：

```text
BTC -> BTCUSDT
ETH -> ETHUSDT
SOL -> SOLUSDT
```

主交易对选择规则：

1. 优先 `USDT`。
2. 其次 `USDC`。
3. 其次 `FDUSD`。
4. 其次 `USD`。
5. 最后再考虑 BTC/ETH 计价对。

当多个交易所或多个 quote 同时存在时，不能静默覆盖，必须记录选择依据。

### 6.3 核心币池

核心币池不应写死为 BTC/ETH。

第一批验收：

- BTC
- ETH
- SOL

第二批扩展：

- BNB
- XRP
- DOGE
- ADA
- AVAX
- LINK
- TON
- TRX
- DOT
- LTC

后续应按流动性自动生成 Top N，而不是长期维护手写列表。

## 7. 新增组件

### 7.1 下载器

建议新增：

```text
scripts/crypto/download_binance_public_data.py
```

职责：

- 发现 Binance spot / futures 可用交易对。
- 生成 daily/monthly ZIP URL。
- 下载指定 market、granularity、date range。
- 下载并校验 checksum。
- 记录下载 manifest。
- 支持 dry-run。
- 支持 max-symbols / symbol allowlist，用于小样本验收。

不负责：

- 写 Mongo。
- 写报告。
- 调 OpenClaw。

### 7.2 导入器

建议新增：

```text
src/claw_trade/data_gateway/crypto_prepackaged_importer.py
scripts/crypto/import_crypto_prepackaged_to_mongo.py
```

职责：

- 审计本地包目录。
- 校验文件完整性。
- 解析 Binance CSV。
- 处理毫秒/微秒 timestamp 差异。
- 归一化交易对、资产、quote、exchange、UTC 时间。
- 写 normalized rows。
- 写 raw package record。
- 写 provider attempt record。
- 写 dataset manifest。
- 支持 replace-existing，但必须显式确认维护范围。

不负责：

- 出网下载。
- 调实时 provider。
- 推断投资结论。

### 7.3 仓库读取优先级

`/report` 数据包读取时应遵守：

1. 先查本地 normalized warehouse。
2. 本地覆盖不足时，再走 provider 增量补数据。
3. provider 成功或失败都写 evidence。
4. 本地和远端口径冲突时，记录 conflict，不静默覆盖。

## 8. 数据流

```text
Binance Public Data
  -> download_binance_public_data.py
  -> local ZIP + CHECKSUM + download manifest
  -> crypto_prepackaged_importer.py
  -> DatasetRepository
  -> raw payload metadata
  -> normalized rows
  -> provider attempt
  -> dataset manifest
  -> /report data pack warehouse check
  -> market_analyst L1 report
```

## 9. 错误处理

必须显式记录：

- 文件不存在。
- checksum mismatch。
- CSV schema mismatch。
- timestamp 单位无法判断。
- 空文件。
- 交易对无法解析。
- 资产映射冲突。
- 覆盖区间不足。
- 重复 bar。
- 同一 period 多条冲突记录。
- 已下架交易对缺失。
- replace-existing 未确认。

禁止：

- checksum 失败后继续当成功。
- 交易对无法解析时猜测资产。
- 本地包覆盖不足时写成全量覆盖。
- 下载失败后假装源不可用但不写 attempt。
- 用 Binance 全交易对替代全球加密全市场声明。

## 10. 验收计划

### 10.1 单元测试

覆盖：

- Binance URL 生成。
- checksum 校验。
- spot/futures Kline CSV 解析。
- 毫秒/微秒 timestamp 处理。
- `SOLUSDT` -> `base_asset=SOL`、`quote_asset=USDT`。
- `1d` -> `daily_bar`。
- `1h` -> `intraday_bar`。
- manifest 写入。
- raw/attempt/normalized refs 生成。
- replace-existing 需要显式维护确认。

### 10.2 小样本集成测试

导入：

- BTCUSDT
- ETHUSDT
- SOLUSDT

覆盖：

- spot `1d`
- spot `1h`
- USD-M futures `1d`
- USD-M futures `1h`

断言：

- normalized refs 使用 `dataset://normalized/...`。
- warehouse 可查到一年日线。
- `/report BTC` 和 `/report SOL` 优先命中本地仓库。
- 数据缺口从 `date_range_missing` 降低。

### 10.3 live proof

在固定 runtime 下跑：

- `/report BTC`
- `/report SOL`

检查：

- provider attempts。
- report-prefetch。
- market analyst L1。
- 最终 reader report。
- 缺口说明是否真实。
- 是否仍把 Google 或搜索源当成主要事实源。

## 11. 停止条件

遇到以下情况必须停下来问人：

- 第一版要求下载 1m 全量、trades 全量或 tick 全量。
- 需要覆盖已下架交易对完整历史。
- 要购买或接入 Tardis、Kaiko、CoinAPI、Glassnode、Santiment、The Tie、LunarCrush。
- 要把 Binance 全交易对称作“加密全市场”。
- 需要删除或替换已有 CRYPTO normalized rows。
- 需要修改 OpenClaw runtime。
- 需要新增 runtime guard 或改变 worker prompt 风格。

## 12. 分期实施

### Phase 1：Binance 行情 seed 包

目标：

- Binance spot + USD-M futures 全交易对 `1d`、`1h`。
- BTC/ETH/SOL 小样本验收。
- 本地 normalized warehouse 可优先命中。

交付：

- downloader。
- importer。
- CLI。
- 单测。
- 小样本集成测试。
- BTC/SOL live proof。

### Phase 2：核心币池衍生品

目标：

- BTC/ETH/SOL 起步。
- 扩展 Top N 高流动性币。
- Coinglass 继续做实时/补充源。
- 若购买 Tardis/Kaiko/CoinAPI，则导入付费历史包。

交付：

- derivative metric normalized schema 对齐。
- funding rate。
- open interest。
- long/short ratio。
- liquidation。
- taker buy/sell。
- futures/spot netflow。

### Phase 3：链上和基本面

目标：

- Coin Metrics Community 导入 BTC/ETH。
- CoinGecko/CoinMarketCap 补市值、供应量、FDV。
- DefiLlama 补 TVL、DEX、Perps、ETF/CEX 透明度。
- SOL 使用独立 Solana 口径，不照搬 BTC MVRV/SOPR。

### Phase 4：新闻和社交历史

目标：

- 官方公告和交易所公告入库。
- 新闻搜索只做发现，不直接当事实。
- The Tie/LunarCrush/Santiment 作为付费增强。
- Alternative.me 只作为市场级情绪，不冒充社交舆情。
