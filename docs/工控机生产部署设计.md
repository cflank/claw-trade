# 工控机生产部署设计

日期：2026-06-21
状态：辩论评审后修订稿

## 目标

把 claw-trade 部署成 Ubuntu x86 工控机上的生产级一体机产品：

- 客户不能登录 Ubuntu 系统；
- 开机后自动进入产品界面；
- 客户设备上不交付源码仓库、测试文件和 `.git` 历史；
- 每台设备使用唯一授权码；
- 未授权、过期或被吊销时不能生成报告或刷新数据；
- 支持签名更新、失败回滚、最小本地救援和小批量量产。

第一版目标是**可交付、可授权、可启动、可更新、可救回、不会暴露源码**。第一版不承诺防住 root、拆盘、USB 启动、内存 dump、动态调试或定向专业逆向。

## 第一版交付合同

第一版只交付以下能力：

- 无源码生产包安装到 `/opt/claw-trade`；
- systemd 启动产品运行时、UI、更新器和 kiosk；
- kiosk 自动打开产品 UI；
- Virbox 授权状态控制报告生成和数据刷新；
- 客户 API KEY 本机安全保存，日志和诊断包脱敏；
- 单一 stable 通道签名 release 包更新；
- 原子安装、健康检查、失败回滚；
- 本地诊断包导出；
- 本地最小救援页；
- 黄金镜像或硬盘克隆量产；
- OpenClaw 报告路径验收。

第一版明确不交付：

- `.clawpack` 加密资源包；
- native loader；
- Virbox Protector 深度加固；
- factory/support endpoint；
- 出站 factory agent；
- sealed 状态；
- 产线注册后台；
- 完整安全恢复模式产品化；
- 多更新通道资格矩阵；
- 自研远程运维或远程命令能力；
- MAAS 或复杂产线平台。

这些能力进入“后续增强清单”，不得阻塞第一版交付。

## 已确定决策

- 授权权威：Virbox 云授权平台。
- 授权模型：一台设备一个唯一授权码。
- 续期频率：每天心跳一次。
- 离线宽限期：30 天。
- 授权失效后的表现：锁定报告生成和数据刷新；保留设置、授权修复、网络诊断、日志导出、手动签名更新和恢复出厂。
- 客户系统权限：客户不能登录 Ubuntu，只能看到产品界面和受控浏览器。
- 外部网页访问：允许访问任意网站，但不能暴露系统文件、终端、服务目录、开发者工具或本地管理端口。
- 远程更新：OSS/COS 静态更新包 + 本机签名 updater；第一版不自建更新后台。
- 量产方式：黄金镜像或硬盘克隆 + 首次启动本地自检 + 诊断/验收包导出。
- 硬件目标：Ubuntu x86 工控机。

## 威胁模型

第一版防护目标：

- 防普通客户误看、误改源码和运行目录；
- 防直接复制源码仓库；
- 防未授权设备生成报告或刷新数据；
- 防未签名更新包和降级更新；
- 防客户 API KEY 出现在前端、日志、诊断包或更新包中；
- 防普通浏览器/kiosk 逃逸到 shell、文件管理器或服务目录。

第一版不承诺：

- 防客户拆盘读取；
- 防客户从 USB 启动；
- 防客户获得 root 后读取进程内存；
- 防客户动态调试、hook Python 或 patch 授权判断；
- 防专业团队做定向逆向；
- 防授权设备运行时的 prompt、模板或报告材料被 root 级攻击者 dump。

后续如需要提高静态提取和普通逆向成本，再进入 `.clawpack`、native loader、Virbox Protector、Secure Boot、磁盘加密、TPM 绑定、BIOS/UEFI 密码、禁 USB 启动、机箱封签等增强阶段。增强阶段仍只能承诺提高成本，不能承诺绝对防破解。

## 总体架构

```text
Virbox 云授权平台
-> 每台设备一个授权码
-> 本机 Virbox runtime 校验授权
-> claw-trade 后端读取授权状态
-> 授权有效：开放报告生成和数据刷新
-> 授权无效：仅开放设置/授权/诊断/恢复/手动签名更新
-> systemd 启动产品服务
-> kiosk 浏览器打开产品 UI
```

claw-trade 仍控制工作流状态机、报告调度、artifact authority 和导出。OpenClaw 仍只负责单个 agent turn runtime。生产打包不能把 worker 调度、投资逻辑、prompt 改写、报告结论 authority 放到 systemd 脚本、updater、kiosk 或授权适配层。

## 生产安装包

客户机器上不能存在开发仓库：

```text
/home/frank/src/claw-trade/
  .git/
  src/
  web/research-ui/src/
  agents/
  tests/
  docs/
```

生产安装形态：

```text
/opt/claw-trade/
  releases/<version>/
    app/
    web/dist/
    runtime/
    bin/
  current -> releases/<version>
  shared/
    config/
    data/
    logs/
    license/
    reports/
    updates/
```

release 目录随版本更新。`shared/` 保存运行期状态，更新不得覆盖。

设备上不放：

- 源码仓库；
- `.git`；
- 测试文件；
- 开发脚本；
- `.env.local`；
- `uv` 临时开发环境；
- `pnpm` 构建环境；
- 签名私钥；
- 客户 API KEY；
- 更新包签名私钥。

客户 API KEY 的边界：

- 黄金镜像、release 包和更新包不预置客户 API KEY；
- 客户在运行期通过设置页粘贴的 API KEY 允许保存在设备上；
- 运行期 API KEY 只保存在 `/opt/claw-trade/shared/config` 或实施计划明确的等价受保护目录；
- 第一版 API KEY 保存合同是权限保护和脱敏，不承诺抗 root 或离线拆盘读取；
- API KEY 文件或 secrets store 只能由后端专用服务用户读取，目录权限、文件权限和备份/导出规则必须在实施计划中明确；
- 前端不能直接读取明文 API KEY；
- 更新不能覆盖运行期 API KEY；
- 恢复出厂设置会清空运行期 API KEY；
- 日志、诊断包、崩溃输出不得包含明文 API KEY。

## 生产运行时合同

第一版必须提供生产入口命令，不能直接使用开发脚本作为 systemd `ExecStart`。

目标入口：

```text
/opt/claw-trade/current/bin/claw-trade-control
/opt/claw-trade/current/bin/claw-trade-ui
/opt/claw-trade/current/bin/claw-trade-updater
/opt/claw-trade/current/bin/claw-trade-kiosk
```

允许实现时调整命令名，但必须满足同等合同：

- 从 `/opt/claw-trade/current` 启动；
- 不依赖开发仓库路径；
- 不依赖 `uv run`；
- 不依赖 `pnpm build`；
- 不读取 `.env.local`；
- 不动态构建前端；
- 不动态安装插件；
- 日志写入 `/opt/claw-trade/shared/logs` 或 journald；
- 配置读取 `/opt/claw-trade/shared/config`；
- 数据写入 `/opt/claw-trade/shared/data`、`reports`、`license`、`updates` 等受控目录。

最小 systemd 服务：

- `claw-trade-control.service`：启动 OpenViking、OpenClaw gateway、Mongo/运行时依赖和 control runtime。
- `claw-trade-ui.service`：启动 FastAPI UI 后端并托管已编译前端。
- `claw-trade-updater.timer` + `claw-trade-updater.service`：每天检查 stable 更新。
- `claw-trade-kiosk.service`：打开全屏产品 UI。

每个 unit 必须在实施计划中明确：

- `User` / `Group`；
- `WorkingDirectory`；
- `ExecStart`；
- `EnvironmentFile`；
- 端口和绑定地址；
- 依赖顺序；
- 健康检查；
- 重启策略；
- 停止顺序；
- 日志位置；
- 失败后用户可见状态。

客户-facing kiosk 用户不能拥有 shell、sudo、文件管理器，也不能访问 `/opt/claw-trade`。

## 授权合同

Virbox 负责激活、设备绑定、每日续期、吊销、过期和功能模块授权。

claw-trade 只消费授权状态，不自建授权权威。第一版需要把 Virbox 状态映射为：

- 已激活；
- 未激活；
- 宽限期内；
- 超过宽限期过期；
- 被吊销；
- Virbox runtime 不可用；
- 网络不可用。

授权状态由后端决定，前端只能展示结果，不能决定授权是否有效。

授权有效：

- 允许报告生成；
- 允许数据刷新；
- 允许更新检查；
- 允许设置和诊断。

授权无效、超过宽限期或被吊销：

- 禁止报告生成；
- 禁止数据刷新；
- 禁止调用核心 OpenClaw 报告工作流；
- 保留授权页、网络诊断、日志导出、手动导入签名更新包和恢复出厂设置。

更新成功不能被当作授权修复。更新后仍以 Virbox 授权状态为准。

## OpenClaw 边界验收

生产包必须证明：

- `/report` 仍由 claw-trade 控制工作流顺序；
- 12 个 TradingAgents worker 仍通过 OpenClaw wake 执行；
- OpenClaw 仍是单 agent turn runtime；
- 后续 worker 不退回 direct LLM 或 Python materializer 路径；
- provider payload capture、tool schema capture、worker/stage/run/dispatch evidence 仍可取得；
- updater、systemd、kiosk、授权适配层不改写 worker prompt、报告结论或 PM 决策。

如果生产打包改变 OpenClaw runtime 行为，必须遵守现有 OpenClaw 运行时验证要求：build、restart、fresh live proof、provider payload inspection。

## kiosk 和浏览器边界

客户可以访问任意外部网站，但该能力只存在于受控浏览器界面，不等于可以访问 Ubuntu 桌面。

这里的“任意外部网站”只指公网网页访问，不包括 `127.0.0.1`、`localhost`、`::1`、局域网管理地址、本机产品后端 API、授权接口、更新接口或恢复接口。外部网页不能访问或触发这些本机/内网管理面。

第一版必须定义并验收：

- 禁止打开终端；
- 禁止打开文件管理器；
- 禁止访问 `/opt/claw-trade`；
- 禁止浏览器扩展安装；
- 禁止开发者工具；
- 禁止远程调试端口；
- 禁止 `file://` 访问本地文件；
- 禁止危险外部协议唤起本地程序；
- 下载目录必须受控，下载的可执行文件不能运行；
- 上传文件时不能暴露服务目录；
- 弹窗、多窗口、多标签不能逃逸 kiosk；
- 产品 UI 和外部网页浏览必须隔离会话、profile 或权限边界；
- 本地 API 必须有鉴权、来源校验和 CSRF 防护，不能被普通外部网页触发状态变更；
- 证书错误、代理设置、浏览器崩溃后重启策略明确；
- 允许剪贴板用于粘贴 API KEY，但不得把 API KEY 写入日志。

优先使用 Ubuntu kiosk/session、浏览器 policy、systemd 和 Linux 权限。第一版不自研桌面壳。

## 远程更新

第一版只支持单一 stable 通道。

对象存储里放静态 release 文件：

```text
updates/stable/
  manifest.json
  manifest.json.sig
  claw-trade-1.2.3.tar.zst
  claw-trade-1.2.3.tar.zst.sig
```

设备 updater 流程：

```text
每日定时器
-> 拉取 manifest
-> 校验 manifest 签名
-> 检查版本、架构、产品通道
-> 检查授权状态
-> 检查磁盘空间
-> 下载 archive 到 shared/updates
-> 校验 hash 和签名
-> 解压到 /opt/claw-trade/releases/<version>.staging
-> 运行 preflight
-> 原子切换 current symlink
-> 重启服务
-> 健康检查
-> 成功后标记版本可用
-> 失败时回滚到上一可用版本
```

第一版更新规则：

- 只安装签名有效的 manifest 和 archive；
- hash 不匹配时拒绝安装；
- 默认拒绝降级；
- 安装前检查磁盘空间；
- 安装到新目录，不覆盖当前版本；
- `current` 切换必须原子；
- 至少保留上一个可用版本；
- 断电后必须能继续启动上一可用版本或完成回滚；
- 健康检查失败必须回滚；
- 更新不得覆盖 `shared/config`、`shared/data`、`shared/license`、`shared/reports`、`shared/logs`；
- schema 或数据格式变更必须有兼容检查；不兼容时拒绝更新或明确迁移/回滚策略；
- 未授权设备可以手动导入签名完整包，但不能因此解锁报告生成。

远程更新禁止：

- 执行远程 shell 脚本；
- 安装未签名文件；
- 让前端决定更新资格；
- 保存签名私钥到设备；
- 覆盖客户 API KEY、授权状态、报告、日志或本地数据。

第一版不做：

- bootstrap/repair/security/revocation 多通道矩阵；
- 远程命令；
- 自建更新后台；
- 设备远程任务拉取。

后续增强再处理签名密钥轮换、私钥泄露应急、对象存储回滚防护、最低安全版本、构建 provenance 和透明发布记录。

## 本地救援和恢复

客户不能登录 Ubuntu，因此第一版必须提供最小本地救援能力。

最小救援页能力：

- 查看授权状态；
- 重新激活或更换授权码；
- 网络诊断；
- 导出脱敏诊断包；
- 手动导入签名更新包；
- 恢复出厂设置；
- 查看当前版本和上一可用版本。

救援页不开放：

- shell；
- 任意命令执行；
- 文件管理器；
- 报告生成；
- 数据刷新；
- OpenClaw worker 调度。

恢复出厂设置不是重装 Ubuntu，而是重置 claw-trade 应用状态。

用户从设置页触发恢复出厂：

```text
设置页请求
-> 二次确认
-> 停止报告任务
-> 导出诊断包
-> 清空客户 API KEY、报告、缓存、队列和用户设置
-> 保留 Virbox 激活状态、更新公钥、当前稳定版本
-> 重建默认配置
-> 重启服务
```

启动失败恢复第一版只要求：

```text
服务启动健康检查失败
-> 启动失败计数 +1
-> 连续 3 次失败：回滚到上一个 release
-> 回滚失败：进入最小救援页
```

完整独立安全恢复模式后续再做。

## API KEY、日志和诊断包

第一版必须满足：

- API KEY 不进镜像；
- API KEY 不进 release 包；
- API KEY 不进更新包；
- API KEY 不进前端响应；
- API KEY 不进日志；
- API KEY 不进诊断包明文；
- 恢复出厂清空 API KEY；
- 日志导出默认脱敏；
- 崩溃输出默认脱敏；
- 授权码、设备标识、报告内容按敏感信息处理；
- 诊断包默认只包含脱敏配置摘要、版本、服务状态、健康检查结果、更新状态和脱敏日志；
- 授权码默认只显示后 4 位或等价不可反推片段；
- 设备标识默认哈希化或只显示厂商可关联的短标识；
- 报告正文、provider payload、客户 API KEY、完整授权码和原始日志片段默认不进入诊断包；
- 如排障必须导出报告正文或 provider payload，必须由用户在本机界面单独确认，并继续脱敏 API KEY 和授权码。

第一版依赖 Linux 文件权限、专用服务用户和后端进程边界保护运行期 secrets，不把它表述为抗 root 或抗拆盘加密。TPM、硬件密钥、外部 KMS、native 密钥派生属于后续增强。

## 量产部署

第一版小批量量产使用黄金镜像或硬盘克隆：

```text
claw-trade-factory-image-<date>.img.zst
claw-trade-factory-image-<date>.img.zst.sig
factory-provision USB 或硬盘拷贝机流程
本地自检脚本
本地验收/诊断包
设备序列号记录表
```

镜像包含：

- Ubuntu x86；
- kiosk 和 systemd 配置；
- claw-trade 生产运行时，不含源码仓库；
- Virbox runtime；
- updater；
- 本地自检脚本；
- 公共验签密钥；
- 默认配置。

镜像不包含：

- 客户 API KEY；
- 授权激活状态；
- 签名私钥；
- 源码仓库和 `.git`。

第一版量产流程：

```text
烧录黄金镜像
-> 首次启动
-> 本地自检
-> 导出验收/诊断包
-> 记录设备序列号和授权码
-> 交付客户
```

不依赖 factory/support endpoint、sealed 状态、出站 factory agent 或产线注册后台。硬件固定、产量中等时，Clonezilla 或硬盘拷贝机是最快路径。硬件型号变化时，再考虑 Ubuntu Autoinstall + cloud-init。MAAS 后续再评估。

## 实施前置验证门

进入第一版实施前，先完成这些验证门：

1. Virbox Linux x86 验证门：
   - 验证 Virbox SDK/API 能在 Ubuntu x86 服务进程中读取激活、过期、吊销和宽限状态；
   - 验证 Python/FastAPI 后端能稳定调用该状态；
   - 失败时停止实施，重新选择授权底座。
2. 生产运行包验证门：
   - 验证干净 Ubuntu/VM 可以从 `/opt/claw-trade/current` 启动；
   - 验证不依赖开发仓库、`uv`、`pnpm`、`.env.local`。
3. updater 验证门：
   - 验证签名失败、hash 不匹配、磁盘不足、断电中断、降级和健康检查失败都会拒绝安装或回滚；
   - 验证更新不覆盖 `shared/` 数据。
4. kiosk 验证门：
   - 验证客户不能打开终端、文件管理器、源码路径或服务目录；
   - 验证外部网页访问不能逃逸到本地系统。
5. API KEY/日志验证门：
   - 验证前端不能读取明文 API KEY；
   - 验证日志和诊断包脱敏。
6. OpenClaw 边界验证门：
   - 验证生产包报告路径仍通过 OpenClaw worker；
   - 验证 provider payload/tool schema/runtime evidence 仍可取得。

任一验证门失败时，必须回到设计评审，不能用 mock、stub、fake、fallback 冒充生产能力。

## 验收标准

授权：

- 未激活设备只能进入设置/授权修复/诊断界面；
- 已激活设备可以生成报告；
- 被吊销设备不能生成报告；
- 超过 30 天宽限期的过期设备不能生成报告；
- 前端不能伪造授权有效状态。

生产运行：

- 设备从 `/opt/claw-trade/current` 启动；
- systemd unit 用户、目录、端口、环境、日志和健康检查明确；
- 不依赖开发仓库、`uv`、`pnpm`、`.env.local`；
- 开机自动打开产品 UI；
- 客户不能打开终端、文件管理器、源码路径或服务目录。

更新：

- 签名有效的 stable 更新能安装并重启成功；
- 损坏包、未签名包、hash 不匹配包会被拒绝；
- 默认拒绝降级；
- 磁盘空间不足会拒绝安装；
- 健康检查失败会回滚；
- 断电后能启动上一可用版本或完成回滚；
- 更新不覆盖客户 API KEY、授权、报告、日志或本地数据。

救援：

- 本地救援页能修复授权、诊断网络、导出脱敏日志、手动导入签名更新包、恢复出厂；
- 无授权或救援状态下不能生成报告；
- 恢复出厂会清空客户 API KEY、报告、缓存、队列和用户设置，并保留 Virbox 激活状态和当前稳定版本。

安全：

- API KEY 不出现在前端、日志、诊断包明文中；
- 浏览器不能通过下载、`file://`、扩展、devtools、远程调试端口、危险协议、本地管理端口或内网管理地址逃逸；
- 外部网页不能触发本机产品后端 API、授权接口、更新接口或恢复接口的状态变更；
- 诊断包默认不包含报告正文、provider payload、客户 API KEY、完整授权码和原始日志片段；
- 生产包不包含源码、测试、`.git`、开发脚本和签名私钥；
- 文档和销售口径不承诺防 root、拆盘或专业逆向。

OpenClaw 边界：

- `/report` 仍由 claw-trade 控制流程；
- 12 个 worker 仍由 OpenClaw wake；
- 不存在 Python 直调 LLM 替代路径；
- provider payload/tool schema/runtime evidence 可验证。

量产：

- 黄金镜像烧录后无需人工应用配置；
- 本地自检可生成验收包；
- 设备序列号和授权码可登记；
- 首批设备不依赖自建 factory/support 后台。
