# 港股总体设计

状态：总体设计，实施中。HK profile 已按 2026-05-15 人工指令打开运行入口；live provider payload 和真实 provider attempt 验证仍需完成。

## 1. 结论

港股应作为独立的 `HK` profile 支持，而不是并入 `CN_A`，也不能静默套用 `US` 或 `CN_A` 的 prompt、工具、数据源和验收口径。

推荐框架是：

```text
claw-trade 控制同一条 12-worker TradingAgents 工作流
HK profile 拥有独立 prompt / stage policy / tool schema / 数据证据
OpenClaw 只执行单个 worker turn
Artifacts 只传递 approved L1 自然语言报告
PM 仍拥有最终投资决策
```

TradingAgents-CN 的港股实现可作为参考，但不能原样照搬。它主要采用“统一中文 prompt + 统一工具内部分支 + 股票代码识别”的方式处理 A 股、港股、美股；本项目边界更严格，要求 HK profile 独立批准、工具证据可追踪、失败不能被隐藏 fallback 掩盖。

## 2. 当前项目现状

已确认事实：

- `claw-trade` 已能在输入层识别 HK：4/5 位数字会推断为 `HK`，显式 `market=HK` 也会进入 `HK` profile。
- 普通港股默认货币为 `HKD`，显示符号为 `HK$`；具体柜台货币仍以标的/交易柜台和 provider evidence 为准。
- 当前 profile 策略中 `HK` 已批准进入运行路径。
- worker 的 `STAGES.yaml` 已有 HK 配置，HK 前线复用统一数据需求工具，后续 worker 无模型可见工具。
- 项目规则明确要求：HK prompt strategy 不明确时必须 fail explicitly，不得 fallback 到 US 或 CN_A。
- Tushare Pro 可以作为港股专业数据接口纳入 HK 数据源设计，但必须按接口权限、字段覆盖、更新频率、币种口径和 provider evidence 单独验收。

推断：

- 现有 A 股和美股链路的 workflow、artifact、provider payload capture、report export 机制可以复用到港股。
- 港股的主要新增工作不在 DAG，而在 profile、prompt、stage-scoped tool policy、数据服务层和验收证据。

未知：

- Tushare Pro 在本项目实际账号下的港股接口权限、调用频率、字段覆盖和更新稳定性。
- Tushare Pro 与 AkShare、Yahoo Finance、HKEXnews 等来源之间的字段差异、币种差异和复权口径差异。
- 港股新闻、财务、情绪数据的最低可用覆盖率。
- 真实 live run 中每个 worker 的 HK prompt 是否能保持 TradingAgents / TradingAgents-CN 的报告感和辩论感。

## 3. 设计原则

### 3.1 HK 是独立市场 profile

HK 不是 `CN_A` 的子集，也不是中文市场的别名。

必须独立定义：

- prompt profile：`HK`
- market：`HK`
- default currency：`HKD`
- default currency_symbol：`HK$`
- counter currency：由具体交易柜台和 provider evidence 决定；普通港股默认为 HKD，人民币双柜台或其他多币种情况必须由标的/柜台证据支持。
- ticker display / provider symbol mapping
- stage-visible tools
- frontend / CLI 输入语义
- live 验收矩阵

不允许：

- HK 没 prompt 时套 CN_A。
- HK 没工具时套 US。
- 港股数据失败时生成“看起来完整”的假覆盖。
- 把港股报告写成 A 股制度语境。

### 3.2 共用 TradingAgents 工作流，不另造 DAG

港股仍走现有 12-worker 顺序：

```text
frontline:
  market_analyst
  fundamental_analyst
  news_analyst
  social_analyst

investment_debate:
  bull_researcher
  bear_researcher

investment_decision:
  research_manager

trade_decision:
  trader

risk_debate:
  risk_challenger
  risk_guardian
  risk_moderator

portfolio_decision:
  portfolio_manager
```

`claw-trade` 继续拥有 workflow state machine、dispatch、artifact authority、hard gates 和 export。OpenClaw 继续只负责单个 worker turn。

### 3.3 Prompt 是 agent 配置，不是 Python 业务逻辑

每个 worker 必须有批准后的 `agents/<worker>/prompts/HK.md`。

HK prompt 应从 TradingAgents / TradingAgents-CN 的角色、语气、报告结构、辩论感出发，再加入港股必要语境。不能把自然语言 prompt 改成工程 checklist。

HK prompt 必须覆盖：

- 普通港股默认港币计价和 `HK$` 输出；若是人民币双柜台或其他多币种柜台，必须按真实柜台货币输出。
- 港交所交易语境，包括交易时段、收市竞价、停复牌、交易单位、流动性和成交额语境。
- 港股没有 A 股式每日涨跌停的默认语境；但不能写成“没有任何波动控制”，应在证据相关时考虑 VCM、报价规则和交易时段限制。
- 港股通、南向资金、H 股、红筹、双重上市、中概回港等仅在标的或证据相关时使用。
- 估值、PE/PB/ROE、目标价、股价区间必须由工具证据支持。
- 若数据缺失，说明缺失证据和影响，不编造。

HK prompt 不应加入：

- “更保守”“避免建议”“不要给买卖结论”这类非 baseline 风格限制。
- RuntimeTarget、ReportSubmission、artifact URI/hash、provider payload、OpenViking/OpenClaw 协议字段。
- JSON/debug/cache/provider attempts 作为主要 worker-facing material。

### 3.4 工具按 worker 和 stage 暴露

HK 不应另造一套模型可见工具名。前线四个 worker 复用统一数据需求工具，由数据层按 `market=HK` 和数据需求生成 provider 调用。

```text
market_analyst       -> claw_request_data
fundamental_analyst  -> claw_request_data
news_analyst         -> claw_request_data
social_analyst       -> claw_request_data
```

后八个 TradingAgents-CN / original 风格的推理 worker 若 baseline 是纯 LLM reasoning over upstream reports，则不向模型暴露 OpenViking 读写工具。Python 可以把 approved L1 自然语言报告正文放入 prompt variables，但不能总结、压缩或改写。

### 3.5 多源可用，但不能隐藏 fallback

港股数据可以使用多源组合，但每一次尝试都必须进入 evidence：

```text
provider_attempts:
  - provider
  - api
  - input_symbol
  - status
  - failure_reason
  - observed_rows / observed_items
  - freshness
  - source_refs
  - quality
```

允许“按优先级尝试多个 provider”，但不允许“失败后悄悄换源并让报告看起来像单一可靠成功”。读者报告可以不展示全部尝试细节，但审计证据必须保留。

### 3.6 Tushare 作为港股专业 provider

Tushare Pro 应纳入 HK profile 的第一梯队专业数据源，而不是仅作为备用爬取源。它可以承担港股基础列表、日线行情、财务指标、港股通/沪深港通相关数据等结构化数据来源。

设计要求：

- Tushare provider 必须有独立 provider id，例如 `tushare_pro_hk`，不能混在通用 A 股 Tushare 工具里。
- Tushare 的 `ts_code` 应作为 provider symbol 的一种正式格式，例如 `00700.HK`；不要在工具内部静默把港股代码改成 A 股或美股格式。
- Tushare 返回的 `trade_unit`、`curr_type`、财务指标币种、报告期、更新时间、接口权限和调用失败原因必须进入 evidence。
- Tushare 可作为 market/fundamental/stock-connect 类数据的优先 provider；AkShare、Yahoo Finance、HKEXnews、Google News 等可作为互补来源，但每次尝试都要记录 provider attempts。
- Tushare 不替代 HKEXnews。公告、业绩公告、盈利警告、停复牌、配售、回购、关联交易等监管披露仍应优先追溯到 HKEXnews 或公司公告原文。
- 如果 Tushare 接口因权限、积分、频率、字段缺失或返回空数据失败，不能静默换源后输出完整成功报告。

## 4. 输入与标的解析

输入层目标：

```text
用户输入:
  0700
  00700
  0700.HK
  00700.HK
  market=HK + ticker=700/0700/00700

内部 identity:
  raw_ticker
  display_ticker
  canonical_ticker
  profile=HK
  market=HK
  default_currency=HKD
  default_currency_symbol=HK$
  counter_currency
```

需要区分三类代码：

- `display_ticker`：报告中展示给读者的代码，例如 `00700.HK`。
- `canonical_ticker`：workflow 和 artifact 使用的统一代码。
- `provider_symbol`：各数据源需要的格式，例如 Tushare Pro 使用 `00700.HK`，AkShare 可能要 5 位数字，Yahoo Finance 可能要 `0700.HK`。

设计要求：

- 标的解析只做身份规范化，不做业务分析。
- 不能把 5 位港股误判为 A 股。
- 不能把 `HK` 输入失败后改为 `US`。
- 普通港股默认 HKD，但实际柜台货币必须从 provider evidence 或交易所资料确认；不要把人民币柜台硬改成 HK$。
- 所有 worker prompt、tool calls、artifact refs、final report 必须保留精确标的。

## 5. 前线数据服务

### 5.1 Market

目标：提供港股行情、技术指标、成交量、趋势判断和图表/指标证据。

最低数据：

- OHLCV。
- 日期范围和交易日数量。
- 当前价或最近收盘价。
- 成交量/成交额。
- 交易单位、币种、复权口径、数据更新时间和是否延迟。
- 停牌/复牌状态、异常缺口、低流动性或成交额不足的提示。
- 常用技术指标：均线、MACD、RSI、布林带，具体指标以 baseline 和现有 market worker 需要为准。
- 图表或指标面板引用；若应生成但缺失，必须有 root cause。

候选数据源：

- Tushare Pro 港股行情接口，例如 `hk_daily`；若使用实时日 K、复权因子或分钟级接口，必须先验证权限和字段口径。
- AkShare 港股历史行情。
- Yahoo Finance 港股历史行情。
- 其他 provider 需单独批准。

失败规则：

- 行情为空不能生成成功市场数据结果。
- 指标缺失不能伪造数值。
- 图表缺失不能只写模糊提醒；要记录根因。
- Tushare 权限不足、频率限制或字段缺失必须作为 provider failure 进入 evidence，不能被 AkShare/Yahoo 成功结果覆盖掉。

### 5.2 Fundamental

目标：提供港股公司基本信息、财务摘要和估值材料。

最低数据：

- 公司名称、交易所、行业/板块。
- 货币口径。
- 交易单位、上市状态、上市日期、ISIN 等基础身份信息。
- 最近财报或财务指标的日期。
- PE/PB/ROE 等估值指标；没有证据时不得写具体值。
- market cap、收入、利润、现金流等字段按 provider 覆盖能力定义。
- 数据来源和更新时间。

候选数据源：

- Tushare Pro 港股列表和财务指标接口，例如 `hk_basic`、`hk_fina_indicator`，以及已验证权限的港股财报接口。
- HKEXnews / 公司公告 / 财报 PDF，用于校验关键财报、业绩公告、盈利警告、停复牌、配售、回购、关联交易等监管披露。
- AkShare 港股财务指标。
- Yahoo Finance 公司信息/财务。
- 其他第三方数据源需单独批准。

失败规则：

- 不支持的 provider 字段不能由 Python 或 LLM 补齐。
- 若只拿到公司基础信息，fundamental report 必须明确“估值/财务证据不足”，不得写完整估值结论。
- Tushare 财务指标不能替代原始公告校验；重大结论依赖业绩、盈利警告、停复牌或公司行动时，必须引用 HKEXnews 或公司公告原文。

### 5.3 News

目标：覆盖公司新闻和市场/宏观背景新闻。

最低数据：

- 公司相关新闻。
- HKEXnews / 公司公告中的重大披露，例如业绩公告、盈利警告、停复牌、配售、回购、关联交易、董事或审计事项。
- 香港市场/中国宏观/全球风险中与该标的相关的新闻。
- 来源、标题、发布时间、URL 或可追踪引用。
- 相关性判断和 rejected evidence。

候选数据源：

- HKEXnews 和公司公告源，作为监管披露的一等来源。
- Google News 港股中文/英文搜索。
- 东方财富/新浪等中文财经源，如果能证明覆盖港股标的。
- Tushare 已验证的大模型语料、公告或资讯接口可作为结构化索引或补充来源，但不能替代公告原文。
- 其他新闻 provider 需单独批准。

失败规则：

- 不能把 A 股新闻误当港股公司新闻。
- 不能凭 ticker 搜索到的弱相关内容直接进入 approved evidence。
- 若只有宏观新闻、没有公司新闻，必须在 report 中说明覆盖缺口。
- 如果发现 HKEXnews 有重大公告而新闻 provider 未覆盖，news report 必须以公告事实为准，不得用新闻缺失得出“无重大事件”结论。

### 5.4 Social

目标：提供港股投资者情绪和讨论热度证据。

第一阶段可以弱于 market/fundamental/news，但必须诚实：

- 可以先支持新闻情绪、热度线索、关键词、相关标的线索。
- 不要求第一阶段做到完整社交平台正文级覆盖。
- 必须禁止虚构雪球、股吧、微博、香港论坛、券商观点或 KOL 表态。
- Tushare 若提供已批准的新闻、研报或热度类结构化数据，可作为情绪线索来源；但不能把结构化索引直接写成“投资者普遍情绪”。

候选范围：

- 新闻情绪和搜索热度线索。
- 东方财富/雪球等中文平台中确实覆盖港股的内容。
- Tushare 已验证权限的数据接口中与港股新闻、研报、公告索引或热度相关的材料。
- 香港本地财经媒体或论坛只在有真实 provider 时启用。

失败规则：

- 没有正文级社交证据时，不得写“散户普遍认为”“KOL 集体看多/看空”。
- 可输出“social evidence limited”，但不能假装已完整覆盖。

## 6. 下游 worker 材料边界

下游 worker 读取的是 approved L1 自然语言报告，不是 raw payload。

允许：

- 将 market/fundamental/news/social 的 approved L1 正文内联到 CN/original baseline 期待的位置。
- 保留 artifact refs 作为审计和 deeper-read handle。

不允许：

- 把 provider attempts、cache object、raw JSON、URI/hash、manifest protocol 文本放进主 worker-facing prompt。
- Python 总结、压缩或改写前线 worker 的业务结论。
- 后八个 worker 使用 direct LLM 或 Python materializer 路径。

## 7. PM 与导出

PM 仍然拥有最终投资决策。

导出层只做：

- reader-facing report 组织。
- 图表和 worker appendix 机械落盘。
- 审计证据引用。

导出层不得：

- 改写 PM rating。
- 把真实柜台货币硬改成 `$`、`HK$` 或其他未经证据支持的货币符号。
- 添加 unsupported target price。
- 用 exporter 补写投资结论。

## 8. 与 TradingAgents-CN 的取舍

可借鉴：

- 同一条 TradingAgents 工作流支持 A 股、港股、美股。
- 通过股票代码识别市场。
- 港股行情和财务使用 Tushare Pro、AkShare、Yahoo Finance 等多源尝试。
- 中文报告、中文投资建议、港股本地语境。

不能照搬：

- 统一工具里隐藏多市场逻辑，导致 provider evidence 不清。
- 把 Tushare 写成万能工具，在工具内部静默切换 A 股、港股、美股逻辑。
- HK prompt 未独立批准就复用中文统一 prompt。
- 社交情绪缺失时输出看起来完整的情绪分析。
- 货币冲突，例如前面识别 HKD，后面又要求港股使用美元。
- 失败后默认 fallback 并继续生成完整报告。

本项目采用更严格的 profile 和 evidence 边界，是为了保证报告可追踪、可验收、可比较。

## 9. 阶段性验收

建议第一个验收标的选择高流动性港股，例如：

- `00700.HK` 腾讯控股
- `09988.HK` 阿里巴巴

第一阶段验收目标：

```text
Profile:
  HK runtime profile approved by human instruction on 2026-05-15.
  Live provider payload and provider attempt evidence still required.
  Tushare Pro HK provider contract verified when used.

Workflow:
  12 workers all OpenClaw-woken.
  No direct_llm or Python materializer path.

Provider payload:
  captured final prompt
  captured HK visible tool schema
  captured worker/stage/profile/run/dispatch evidence

Frontline:
  market/fundamental/news/social each emits canonical L1 report
  each L1 report has evidence or explicit failure reason
  Tushare attempts include interface name, ts_code, fields, freshness, permissions/failure reason

Downstream:
  later workers receive approved natural-language L1 materials
  no raw/debug/protocol payload enters prompt

Final report:
  uses HKD/HK$ by default, or the proven counter currency when not HKD
  does not call HK an A-share or US stock
  does not invent PE/PB/ROE/target price/news/sentiment/chart success
  does not ignore trading unit, liquidity, halt/resumption, or material announcements when evidence exists
```

验收顺序：

1. 静态 profile / stage policy contract。
2. Tushare Pro HK provider contract tests：`hk_basic`、`hk_daily`、`hk_fina_indicator` 等已启用接口的权限、字段、币种、更新时间和失败证据。
3. focused DataNeed / data result tests for HK market/fundamental/news/social。
4. provider payload prompt/tool-schema proof。
5. single HK fresh live run。
6. report export and worker appendix check。

## 10. Stop Conditions

出现以下情况必须停止并请求人工确认：

- 想让 HK 套 CN_A 或 US prompt。
- HK 数据源策略不明确却要批准 profile。
- Tushare 接口权限、字段或更新口径未验证却要把它当作成功 provider。
- 港股工具失败后想继续生成完整成功报告。
- 社交/新闻缺证据却要写完整舆情或新闻覆盖。
- 想用 mock、stub、fake、fallback 绕过验收。
- 想让 Python 改写 PM 港股结论或评级。
- provider payload 不能证明真实 HK prompt 和 HK tool schema。
- 同一 gate category 经 focused fix 后连续失败两次。

## 11. 推荐实施顺序

本文不是实施计划，但推荐后续按以下顺序拆任务：

1. HK profile approval：已按 2026-05-15 人工指令打开运行入口。
2. HK prompt migration：12 个 worker 的 `prompts/HK.md` 从 baseline 证据出发迁移。
3. Tushare Pro HK provider contract：确认 token/权限、接口清单、字段 schema、币种、更新时间、频率限制和失败证据。
4. HK data services：market / fundamental / news / social 四条 frontline 数据服务。
5. HKEXnews / 公司公告链路：补足监管披露、财报原文、停复牌和重大公司行动证据。
6. HK stage policy：每个 worker 只暴露当前 stage 需要的 HK tools。
7. HK artifact contracts：L1 report、manifest、provider attempts、quality、reader_brief。
8. HK focused tests：profile、tool policy、data tool schema、guard truthfulness。
9. HK live proof：post-build/runtime fresh run、provider payload、final report。

## 12. 成功标准

港股支持可宣布完成的最低标准：

- HK profile 从 fail explicitly 变为 approved 有明确人工批准来源。
- 12 worker 全部走 OpenClaw。
